## Quick Summary
Covers how OLM-managed operator updates work: update channels (per-provider naming/policies), automatic vs. manual approval, inspecting Subscription/InstallPlan resources for pending updates, how incompatible operators can block cluster upgrades, version-locking via mirrored catalogs, and uninstalling operators.

## Key Concepts
- **Operator provider updates** — providers release new operator versions (bug fixes, features); OLM applies these updates; new versions can also introduce bugs/incompatibilities — admins should define update policies balancing adoption vs. stability.
- **Update policy levers** — (1) automatic vs. manual OLM approval per installed operator, (2) choice of update channel to follow, (3) custom catalogs curating which operator versions are available.
- **Operators installed outside OLM** — providers may distribute operators via Helm charts or plain YAML manifests instead of OLM/catalogs; OLM does **not** manage these — they are **not updated** during cluster upgrades or by OLM.
- **Operator update channel** — providers can define multiple channels (e.g. `stable`/`candidate`, or major-version-based like `v1`/`v2`) with different publishing policies; lets users balance new-feature adoption speed vs. stability, or manage major-version migration paths.
- **Channel naming conventions vary by provider** — Red Hat operators often use `stable`, `fast`, `candidate`, or versioned names (e.g. `stable-4.18`); community operators might use `alpha`, `beta`, `preview`, `latest`.
- **Switching channels** — editing a Subscription to change channel; does **not** itself trigger an update unless the new channel has a later version available **and** the operator is set to automatic updates; may cause unwanted results — always check operator docs first.
- **installPlanApproval (Subscription field)** — `Automatic` or `Manual`; set via the install wizard or directly in the Subscription resource spec.
- **Subscription resource fields (update-relevant)** — `channel`, `installPlanApproval`, `name`, `source`, `sourceNamespace`, `startingCSV`; status includes `currentCSV` (latest available version in channel), `installedCSV` (currently running version), `installPlanRef` (reference to the InstallPlan), and `state: UpgradePending` when an update awaits action.
- **InstallPlan resource fields** — `spec.approval` (Manual/Automatic), `spec.approved` (true/false), `spec.clusterServiceVersionNames` (target CSV version); `status.phase: RequiresApproval` when manual approval is pending.
- **Approving a manual update** — patch the InstallPlan's `spec.approved` field to `true` (via CLI `oc patch` or web console "Preview InstallPlan" → "Approve").
- **Operator/cluster version compatibility** — operators can declare a list of OpenShift versions they're compatible with; if an installed operator is incompatible with the target OpenShift version, the **CVO blocks the cluster upgrade**.
- **Upgradeable=False condition** — cluster enters a non-upgradeable state with reason `IncompatibleOperatorsInstalled` when an installed operator isn't compatible with the target version; resolution: update the operator to a compatible version, or uninstall it and reinstall after the cluster upgrade.
- **Version-locking operators** — to prevent unintended updates (even under automatic mode), use a **mirrored catalog** containing only approved operator versions.
- **Uninstalling operators** — via web console (Installed Operators → ⋮ → Uninstall Operator) or CLI (delete the Subscription and CSV); uninstalling **can leave residual operator resources** on the cluster — always check operator documentation for required cleanup steps.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc get clusteroperator` | Reviews installed cluster operator versions (mentioned as an inspection method) | — |
| `oc get sub web-terminal -n openshift-operators -o yaml` | Shows a Subscription's channel, approval mode, current/installed CSV, and install plan reference | `-n`, `-o yaml` |
| `oc get installplan install-72vnw -n openshift-operators -o yaml` | Shows an InstallPlan's approval state and target CSV version | `-n`, `-o yaml` |
| `oc patch installplan install-72vnw --type merge --patch '{"spec":{"approved":true}}'` | Approves a pending manual operator update | `--type merge`, `--patch` |

## Config / YAML Snippets
Subscription showing a pending manual update:
```yaml
spec:
  channel: fast
  installPlanApproval: Manual
  name: web-terminal
  source: do280-catalog-redhat
  sourceNamespace: openshift-marketplace
  startingCSV: web-terminal.v1.5.1
status:
  conditions:
  - lastTransitionTime: "2022-11-24T13:46:21Z"
    reason: RequiresApproval
    status: "True"
    type: InstallPlanPending
  currentCSV: web-terminal.v1.6.0        # Latest available version in the channel
  installPlanGeneration: 2
  installPlanRef:
    apiVersion: operators.coreos.com/v1alpha1
    kind: InstallPlan
    name: install-72vnw                    # Reference to the install plan resource
    namespace: openshift-operators
  installedCSV: web-terminal.v1.5.1        # Currently installed version
  state: UpgradePending
```

InstallPlan requiring approval:
```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: InstallPlan
spec:
  approval: Manual                # Whether updates must be approved
  approved: false                   # Whether THIS update is approved
  clusterServiceVersionNames:
  - web-terminal.v1.6.0               # The updated (target) version
  generation: 2
status:
  phase: RequiresApproval
```

## Comparisons
| Aspect | Automatic (installPlanApproval) | Manual (installPlanApproval) |
|---|---|---|
| Update behavior | OLM applies updates as they become available in the channel | OLM creates an InstallPlan but requires explicit approval |
| Admin action | None needed | Must patch `spec.approved: true` or approve via web console |
| Best for | Trusted/well-tested publishing channels, or curated custom catalogs | Environments needing controlled, reviewed updates |

| Aspect | OLM-managed operators | Manually installed operators (Helm/YAML) |
|---|---|---|
| Update mechanism | Managed via Subscription + catalog channel | Not managed by OLM at all |
| Updated during cluster upgrade | Yes (per subscription settings) | No — must be updated manually |

## Exam Tips / Gotchas
- Operators installed via **Helm charts or raw YAML** (not via OLM/catalog) are **not managed or updated by OLM**, including during cluster upgrades — must be updated manually.
- Switching an operator's update **channel** does **not** by itself trigger an update — only if the new channel has a later version **and** the subscription is set to automatic approval.
- **CVO blocks cluster upgrades** if any installed operator is incompatible with the target OpenShift version — condition: `Upgradeable=False`, reason `IncompatibleOperatorsInstalled`.
- To resolve an incompatible-operator block: update the operator to a compatible version, **or** uninstall it and reinstall post-upgrade.
- To **version-lock** an operator (prevent unwanted updates even under Automatic mode), use a **mirrored catalog** containing only approved versions.
- **Uninstalling an operator can leave residual resources** on the cluster — always consult the operator's documentation for proper cleanup steps.
- Review/install any needed compatibility-fixing operator updates **before** initiating a cluster update.

## Glossary
- **Update channel**: named stream of operator versions with a specific publishing/update policy.
- **installPlanApproval**: Subscription field controlling Automatic vs. Manual operator update approval.
- **currentCSV**: Subscription status field showing the latest available version in the channel.
- **installedCSV**: Subscription status field showing the currently installed operator version.
- **InstallPlan**: OLM resource representing a pending/approved operator install or update.
- **Upgradeable=False**: cluster condition blocking upgrade due to an incompatible installed operator.
- **Mirrored catalog**: a curated, locally-hosted catalog used to control/lock which operator versions are available.
