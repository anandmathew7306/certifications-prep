## Quick Summary
Covers OpenShift's Over-the-Air (OTA) update system: update channels (candidate/fast/stable/eus), their support status and recommended use, upgrade paths, how to change channels, pausing machine health checks during updates, the OTA architecture (CVO, telemetry), and step-by-step cluster updates via web console and CLI.

## Key Concepts
- **Over-the-Air (OTA) updates** — software distribution system managing controller manifests, cluster roles, and other resources to update a cluster to a target version; enables using new features/fixes with minimal downtime; managed via the Red Hat Hybrid Cloud Console (console.redhat.com/openshift), with cluster images hosted at quay.io.
- **Skipping intermediate versions** — OTA allows updating directly between non-adjacent z-stream versions (e.g. 4.18.1 → 4.18.3, skipping 4.18.2).
- **Persistent internet requirement** — starting OpenShift 4.10, OTA requires a persistent internet connection (disconnected clusters need a separate update procedure).
- **Update channel** — represents an upgrade path; controls update frequency/stability; named as `<tier>-<major>.<minor>` (e.g. `candidate-4.18`, `fast-4.18`, `stable-4.18`, `eus-4.18`).
- **Candidate channel** — delivers updates for testing feature acceptance in the **next** OpenShift version; **not supported by Red Hat** unless the update is also listed in fast/stable; best suited to dev/pre-production.
- **Fast channel** — delivers updates as soon as Red Hat declares general availability (GA); **supported**; best suited to development/QA environments; customers joining the Red Hat connected customers program get registered to this channel.
- **Stable channel** — updates from fast channel that pass additional Red Hat SRE/support monitoring and validation; **supported**; best suited to production; if an operational issue is found in a fast-channel update, that specific update is **skipped** in stable.
- **Extended Update Support (EUS) channel** — starting OCP 4.8, all even-numbered minor releases (4.8, 4.10, 4.12, 4.14, 4.16, 4.18) are EUS releases; `stable-4.x` and `eus-4.x` channels are identical until the cluster enters the EUS phase.
- **Support status** — `candidate-4.x`: supported **only if** also listed in fast/stable; `fast-4.x`, `stable-4.x`, `eus-4.x`: all fully supported.
- **Recommended channel switching** — switch **only** from stable → fast for reliable support continuity; switching to/from candidate is possible but **not recommended** (candidate is for feature-acceptance testing, not production reliability).
- **Machine Health Check pausing** — during upgrades, nodes may become temporarily unavailable; the machine health check could misidentify them as unhealthy and reboot them — pause health checks before updating (not required on single-node installations) using the `cluster.x-k8s.io/paused` annotation; remove the annotation after the update completes.
- **OTA client-server architecture** — Red Hat hosts cluster images + update infrastructure; a "watcher" detects new images pushed to Quay; the Cluster Version Operator (CVO) receives update status from the watcher, updates cluster components via their operators, then updates OLM-managed components.
- **Telemetry / Telemeter** — Prometheus-based component reporting anonymized cluster operator state data to Red Hat, used to advise administrators on potential new releases; Red Hat plans to extend updated-operator coverage to ISV operators in the future.
- **Machine Config Operator (update role)** — applies desired machine state to nodes; handles rolling node upgrades; uses CoreOS Ignition as the configuration format.
- **Operator Lifecycle Manager (update role)** — orchestrates updates to operators running in the cluster.
- **rpm-ostree** — technology used for transactional OS upgrades on nodes; updates delivered via container images; nodes pull the image, extract it, write packages to disk, modify the bootloader, then reboot — performed as a **rolling update** to minimize cluster capacity impact.
- **No rollback support** — rolling back a cluster to an earlier version is **not supported**; contact Red Hat support if an update fails to complete.
- **API removal warning** — if the next minor version removes APIs still in use, the cluster settings page warns: "This cluster should not be updated to the next minor version."
- **Update history** — CVO maintains a history of applied updates (newest first); each entry has a `State` of `Completed` (successful rollout) or `Partial` (failed/incomplete).

## Operators
- **Cluster Version Operator (CVO)** — drives the overall cluster update process; receives update status from Red Hat's image watcher; updates cluster components via their respective operators, then triggers OLM-managed component updates; reports blocking component status if an update fails to complete.
- **Machine Config Operator (MCO)** — applies desired machine state to nodes; handles rolling node upgrades using CoreOS Ignition.
- **Operator Lifecycle Manager (OLM)** — orchestrates updates to operators running in the cluster (during cluster updates, and generally).

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc patch clusterversion version --type="merge" --patch '{"spec":{"channel":"fast-4.18"}}'` | Changes the cluster's update channel | `--type="merge"`, `--patch` |
| `oc get machinehealthcheck -n openshift-machine-api` | Lists machine health check resources | `-n` |
| `oc annotate machinehealthcheck -n openshift-machine-api machine-api-termination-handler cluster.x-k8s.io/paused=""` | Pauses a machine health check before updating | `-n`, annotation `cluster.x-k8s.io/paused=""` |
| `oc annotate machinehealthcheck -n openshift-machine-api machine-api-termination-handler cluster.x-k8s.io/paused-` | Removes the pause annotation after updating | `-n`, trailing `-` removes the annotation |
| `oc get clusterversion` | Shows current cluster version and update status | — |
| `oc get clusterversion -o jsonpath='{.items[0].spec.channel}{"\n"}'` | Shows the current update channel | `-o jsonpath` |
| `oc adm upgrade` | Shows available/recommended updates for the current channel | — |
| `oc adm upgrade --to-latest=true` | Applies the latest available update | `--to-latest=true` |
| `oc adm upgrade --to=VERSION` | Applies a specific update version | `--to=` |
| `watch oc get clusterversion,clusteroperators` | Monitors update progress across CVO and cluster operators | — |
| `oc describe clusterversion` | Shows cluster version update history (Completed/Partial states) | — |

## Comparisons
| Channel | Support Status | Best suited for |
|---|---|---|
| candidate-4.x | Supported **only** if also listed in fast/stable | Development, pre-production (feature-acceptance testing) |
| fast-4.x | Supported | Development, QA (and production, though stable is preferred) |
| stable-4.x | Supported | Production |
| eus-4.x | Supported | Production (long-term/EUS-tracking clusters) |

|---|---|---|

| Monitoring | Cluster Settings page shows update status | `watch oc get clusterversion,clusteroperators` / `oc describe clusterversion` |

## Exam Tips / Gotchas
- **Rolling back a cluster update is NOT supported** — if an update fails to complete, contact Red Hat support (don't attempt manual rollback).
- Red Hat **does not support** updates listed **only** in the candidate channel.
- Switching channels: **only stable → fast is recommended**; switching to/from candidate is possible but **not recommended**.
- **EUS channels (`eus-4.x`) are identical to `stable-4.x`** for the same even-numbered minor version until the cluster reaches the EUS phase — switching to EUS then means `stable-4.x` **stops receiving z-stream updates** until the next EUS version is available.
- Pausing machine health checks (via `cluster.x-k8s.io/paused` annotation) is **not required for single-node installations**.
- **Update all OLM-managed operators to the target version first**, before initiating the OpenShift cluster update itself.
- During the update process, the cluster **might be briefly inaccessible** — if logged out, wait a few seconds and log back in.
- A cluster update is considered finished when `PROGRESSING` shows `False` and the reported `VERSION` matches the target.
- If the **next minor version removes APIs** still relevant to the cluster, a warning is shown: "This cluster should not be updated to the next minor version."
- `oc describe clusterversion` history: `Completed` = successful rollout, `Partial` = failed/incomplete.

## Glossary
- **OTA (Over-the-Air) updates**: OpenShift's software distribution system for cluster/OS updates.
- **Update channel**: named stream (tier-major.minor) representing supported upgrade paths.
- **EUS (Extended Update Support)**: designation for even-numbered minor releases with extended support channels.
- **CVO**: Cluster Version Operator — drives the cluster update process.
- **Telemeter**: Prometheus-based component reporting anonymized cluster state to Red Hat for update guidance.
- **rpm-ostree**: technology for transactional OS upgrades on RHEL CoreOS nodes.
- **Ignition**: configuration format used by the Machine Config Operator for node configuration during updates.
