## Quick Summary
Covers why OpenShift adds Project/ProjectRequest resources on top of Kubernetes namespaces, how to plan and create a customized project template (roles, quotas, limit ranges, network policies) applied to every new project, how to point the cluster at that template, and how to manage/restrict the self-provisioner role that lets users create their own projects.

## Key Concepts
- **Namespace metadata security implications** — policy controllers may use namespace labels to restrict capabilities; if users could freely modify namespace metadata, they could override security measures.
- **Namespace listing limitation (Kubernetes RBAC)** — RBAC cannot grant permission to list only a subset of namespaces — allowing a user to "list their namespaces" requires granting them permission to list **all** namespaces (namespaces are cluster-wide resources); listing and viewing individual resources are **separate** permissions.
- **Project (OpenShift resource type)** — added by the OpenShift API server; querying projects lists namespaces, filters to those visible to the requesting user, and returns them in project format — solving the namespace-listing granularity problem.
- **ProjectRequest (OpenShift resource type)** — when a project request is created, the OpenShift API server creates a namespace **from a template**, letting cluster administrators customize new-namespace creation (permissions, quotas, limit ranges, etc.) — enabling safe self-service namespace creation.
- **Project template contents** — can include any namespaced resource: Roles/RoleBindings (default: grants `admin` role to the requesting user), ResourceQuotas/LimitRanges (ensuring new projects have resource limits; consider adding LimitRanges to reduce per-workload configuration effort; consider ClusterResourceQuotas if users creating many projects to bypass per-namespace quotas is a concern), NetworkPolicies (enforcing organizational network isolation).
- **oc adm create-bootstrap-project-template** — generates a starter template matching OpenShift's default project-creation behavior (creates the Project + a RoleBinding granting `admin` to the requester); uses the same template mechanism as `oc new-app`.
- **Default project template parameters** — `PROJECT_NAME` (required), `PROJECT_DISPLAYNAME`, `PROJECT_DESCRIPTION`, `PROJECT_ADMIN_USER`, `PROJECT_REQUESTING_USER`; `${VARIABLE}` syntax is replaced at project-request time.
- **Weak quota key validation** — resources like quotas in project templates are **not strictly validated**; a typo (e.g. `count/pod` instead of `count/pods`) creates the quota resource but it has **no actual effect** — silently non-functional.
- **Recommended template-authoring workflow** — create a test namespace → create/test the intended resources until behavior is correct → export as YAML (`oc get ... -o yaml`) → clean up (remove `creationTimestamp`, `status`, etc.) → replace the namespace name with `${PROJECT_NAME}` → add to the bootstrap template's object list → always verify actual project creation behavior afterward.
- **Extracted resource definitions may be imperfect** — beyond irrelevant fields (timestamps, status), controllers may add annotations to live resources that are unsuitable for template definitions — review carefully.
- **project-request template resource location** — created in the **openshift-config** namespace via `oc create -f template.yaml -n openshift-config`.
- **projects.config.openshift.io/cluster resource** — cluster config resource whose `spec.projectRequestTemplate.name` field points to which template (default name: `project-request`) is used for new project requests; changing it triggers a **rollout of the apiserver deployment** in `openshift-apiserver` (during which API requests may behave unexpectedly); reverting to the default template = setting `spec: {}` (empty mapping).
- **self-provisioner cluster role** — grants the ability to create projects; bound **by default** to **all authenticated users** via the `self-provisioners` ClusterRoleBinding.
- **Namespace-permission bypass caveat** — users with direct namespace-creation permissions can create namespaces that **bypass the project template entirely**.
- **rbac.authorization.kubernetes.io/autoupdate annotation** — protects roles/bindings (like `self-provisioners`) from unwanted modification; when set to `true` (default), the API server automatically restores the resource on restart, undoing manual edits, unless the annotation is explicitly set to `false` first.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc adm create-bootstrap-project-template -o yaml > template.yaml` | Generates a starter project template matching default OpenShift behavior | `-o yaml` |
| `oc get limitrange,resourcequota -o yaml` | Lists resources in YAML for extracting into a template | `-o yaml` |
| `oc create -f template.yaml -n openshift-config` | Creates the project template resource in the openshift-config namespace | `-n openshift-config` |
| `oc describe clusterrolebinding.rbac self-provisioners` | Inspects the self-provisioners cluster role binding | — |
| `oc annotate clusterrolebinding/self-provisioners --overwrite rbac.authorization.kubernetes.io/autoupdate=false` | Disables auto-restoration of the self-provisioners binding, allowing manual edits | `--overwrite` |
| `oc patch clusterrolebinding.rbac self-provisioners -p '{"subjects": null}'` | Removes all subjects from the self-provisioners binding (disabling self-provisioning) | `-p` |
| `oc edit clusterrolebinding self-provisioners` | Edits the self-provisioners binding subjects (e.g. change group) | — |
| `oc adm policy remove-cluster-role-from-group` | Removes a cluster role from a group — removes the binding entirely if it's the last subject | — |

## Config / YAML Snippets
Default (bootstrap) project-request template:
```yaml
apiVersion: template.openshift.io/v1
kind: Template
metadata:
  name: project-request
objects:                          # Resources OpenShift creates in new namespaces
- apiVersion: project.openshift.io/v1
  kind: Project                     # The project resource
  metadata:
    name: ${PROJECT_NAME}
    annotations:
      openshift.io/description: ${PROJECT_DESCRIPTION}
      openshift.io/display-name: ${PROJECT_DISPLAYNAME}
      openshift.io/requester: ${PROJECT_REQUESTING_USER}
  spec: {}
  status: {}
- apiVersion: rbac.authorization.k8s.io/v1
  kind: RoleBinding                  # Grants admin role to the requesting user
  metadata:
    name: admin
    namespace: ${PROJECT_NAME}
  roleRef:
    apiGroup: rbac.authorization.k8s.io
    kind: ClusterRole
    name: admin
  subjects:
  - apiGroup: rbac.authorization.k8s.io
    kind: User
    name: ${PROJECT_ADMIN_USER}
parameters:                          # Parameters available to the template
- name: PROJECT_NAME
- name: PROJECT_DISPLAYNAME
- name: PROJECT_DESCRIPTION
- name: PROJECT_ADMIN_USER
- name: PROJECT_REQUESTING_USER
```

Example extracted resources to add to a template (LimitRange + ResourceQuota):
```yaml
- apiVersion: v1
  kind: LimitRange
  metadata:
    name: example
    namespace: example        # Replace with ${PROJECT_NAME} before adding to template
  spec:
    limits:
    - type: Container
      defaultRequest:
        cpu: 250m
        memory: 256Mi
      default:
        cpu: 500m
        memory: 512Mi
      min:
        cpu: 125m
        memory: 128Mi
      max:
        cpu: "1"
        memory: 1Gi
- apiVersion: v1
  kind: ResourceQuota
  metadata:
    name: example
    namespace: example        # Replace with ${PROJECT_NAME} before adding to template
  spec:
    hard:
      count/pods: "1"
```

Setting the cluster's project request template:
```yaml
apiVersion: config.openshift.io/v1
kind: Project
metadata:
  name: cluster
spec:
  projectRequestTemplate:
    name: project-request      # Default name; points to your custom template
```

Reverting to the default (built-in) project template:
```yaml
apiVersion: config.openshift.io/v1
kind: Project
spec: {}                       # Empty mapping = revert to original behavior
```

## Comparisons
| Aspect | Project | ProjectRequest |
|---|---|---|
| Purpose | Filtered, user-visible view of namespaces | Triggers namespace creation from a template |
| API server behavior | Lists namespaces, filters to visible ones, returns as "project" format | Creates a namespace using the configured project-request template |

## Exam Tips / Gotchas
- Listing namespaces the user can see vs. viewing a specific namespace are **separate RBAC permissions** — Kubernetes RBAC has no concept of "list a subset."
- Project template resource validation is **weak** — a quota key typo (e.g. `count/pod` vs `count/pods`) creates the object but it has **no effect** — always test actual behavior, not just successful creation.
- Users with direct namespace-creation permission can **bypass the project template entirely** by creating namespaces directly.
- Changing `projects.config.openshift.io/cluster`'s `spec.projectRequestTemplate` triggers an **apiserver deployment rollout** in `openshift-apiserver` — expect potentially unexpected API behavior during the rollout.
- The `self-provisioner` role is bound to **all authenticated users by default** via the `self-provisioners` ClusterRoleBinding.
- The `self-provisioners` binding has `rbac.authorization.kubernetes.io/autoupdate: true` by default — **edits will be automatically reverted** on API server restart unless you first set this annotation to `false`.
- **Use caution with** `oc adm policy remove-cluster-role-from-group` on protected bindings — it removes the **entire binding** when the last subject is removed, and re-establishing it afterward is a **lengthier process** than simply editing subjects; the removed permission also only persists until the API server restarts (since the binding would normally be auto-restored).
- Reverting to the default project template = setting `spec: {}` (empty mapping) on the cluster Project config resource.

## Glossary
- **Project**: OpenShift API resource providing a filtered, per-user view of namespaces.
- **ProjectRequest**: OpenShift resource type that triggers template-based namespace creation.
- **project-request template**: the default-named template (in `openshift-config`) used for new project creation.
- **self-provisioner**: cluster role permitting project creation.
- **rbac.authorization.kubernetes.io/autoupdate**: annotation controlling whether the API server auto-restores a role/binding on restart.
