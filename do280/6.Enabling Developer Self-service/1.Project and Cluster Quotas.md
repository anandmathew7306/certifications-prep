## Quick Summary
Covers Kubernetes/OpenShift ResourceQuota resources for limiting compute usage and object counts per namespace, how to create/inspect/troubleshoot them via CLI and web console, and OpenShift's ClusterResourceQuota for applying aggregate limits across multiple namespaces selected by labels.

## Key Concepts
- **Resource limits (workload-level)** — an upper bound on resources a workload is expected to use; prevents a malfunctioning/overloaded workload from consuming excessive resources and impacting others.
- **Resource requests (workload-level)** — declares minimum required resources; Kubernetes tracks these and blocks new workload deployment if the cluster lacks sufficient resources.
- **ResourceQuota** — namespace-scoped resource limiting the combined resource usage of all workloads within that namespace; unlike quota systems elsewhere that act on users/groups, Kubernetes quotas act on **namespaces**.
- **hard key (ResourceQuota spec)** — lists the desired hard limits for each named resource.
- **Limit quotas** (e.g. `limits.cpu`, `limits.memory`) — control the **maximum compute resources** all workloads in a namespace can collectively consume; interact with workload resource limits.
- **Request quotas** (e.g. `requests.cpu`, `requests.memory`) — control the **maximum resources workloads can reserve** collectively in a namespace; interact with workload resource requests; prevent one workload's excessive request from blocking requests in other namespaces.
- **pods quota** — limits the number of pods allowed in a namespace.
- **Object count quota** — limits the number of resources of a given type in a namespace (e.g. max 10 deployments); helps prevent backing-store bloat (impacting Kubernetes performance) and limits damage from accidental/malfunctioning resource creation; also relevant for resources affecting external systems (e.g. persistent volumes creating storage-provider entities).
- **count/resource_type syntax** — used for core API group resources (e.g. `count/pods`); use `oc api-resources --api-group="" --namespaced=true` to list core group resources.
- **count/resource_type.group syntax** — used for resources in non-core API groups (e.g. `count/deployments.apps`).
- **Legacy quota naming** — some originally-supported quota types don't use the `count/` syntax at all (e.g. `services` instead of `count/services`).
- **ClusterResourceQuota (CRQ)** — OpenShift resource applying an aggregate quota across **multiple namespaces** selected via a label selector; useful when a group manages many namespaces and admins need to cap their *total* combined usage (not per-namespace).
- **AppliedClusterResourceQuota** — auto-created in each namespace affected by a ClusterResourceQuota, since users may lack read access to the ClusterResourceQuota itself; lets project admins view quota usage that applies to their namespace.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc api-resources --api-group="" --namespaced=true` | Lists core-group namespaced resources (for `count/` quota naming) | `--api-group=""`, `--namespaced=true` |
| `oc create quota example --hard=count/pods=1` | Creates a resource quota limiting pod count (short name `quota` for `resourcequota`) | `--hard=` |
| `oc create resourcequota --help` | Shows help/examples for creating resource quotas without a full manifest | — |
| `oc get quota example -o yaml` | Shows a resource quota's spec and status (hard limits + used values) | `-o yaml` |
| `oc get quota` | Lists resource quotas with REQUEST/LIMIT columns | — |
| `oc get resourcequota` | Lists resource quotas (alternate full name) | — |
| `oc create deployment --image=nginx hello` | Example command that can fail immediately if it exceeds a quota | — |
| `oc get event --sort-by .metadata.creationTimestamp` | Shows namespace events, useful for diagnosing indirect quota failures | `--sort-by` |
| `oc create clusterresourcequota --help` | Shows help/examples for creating cluster resource quotas without a full manifest | — |
| `oc create clusterresourcequota example --project-label-selector=group=dev --hard=requests.cpu=10` | Creates a ClusterResourceQuota limiting total CPU requests across labeled namespaces | `--project-label-selector=`, `--hard=` |
| `oc describe AppliedClusterResourceQuota -n example-2` | Shows the cluster resource quota(s) applying to a specific namespace | `-n` (required — `--all-namespaces` does NOT work with this resource type) |

## Config / YAML Snippets
Namespace ResourceQuota (compute):
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: memory
  namespace: example
spec:
  hard:                      # Desired hard limits per named resource
    limits.memory: 4Gi
    requests.memory: 2Gi
  scopes: {}                  # Defines which namespace resources the quota applies to (not covered in depth)
  scopeSelector: {}
```

ResourceQuota equivalent to `oc create quota example --hard=count/pods=1`:
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: example
spec:
  hard:
    count/pods: "1"
```

ResourceQuota status output:
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: example
  namespace: default
spec:
  hard:
    count/pods: "1"
status:
  hard:
    count/pods: "1"          # Configured limit
  used:
    count/pods: "0"            # Current usage
```

ClusterResourceQuota definition:
```yaml
apiVersion: quota.openshift.io/v1
kind: ClusterResourceQuota
metadata:
  name: example
spec:
  quota:                       # Quota definition (hard nested INSIDE quota, unlike ResourceQuota where hard is directly under spec)
    hard:
      limits.cpu: 4
  selector:                     # Defines which namespaces the CRQ applies to
    annotations: {}
    labels:
      matchLabels:
        kubernetes.io/metadata.name: example
```

ClusterResourceQuota with status (aggregated across namespaces):
```yaml
apiVersion: quota.openshift.io/v1
kind: ClusterResourceQuota
metadata:
  name: example
spec:
  quota:
    hard:
      requests.cpu: "10"
  selector:
    annotations: null
    labels:
      matchLabels:
        group: dev
status:
  namespaces:                    # Per-namespace usage under the quota
  - namespace: example-3
    status:
      hard:
        requests.cpu: "10"
      used:
        requests.cpu: 500m
  - namespace: example-2
    status:
      hard:
        requests.cpu: "10"
      used:
        requests.cpu: 250m
  total:                          # Aggregated total across all matched namespaces
    hard:
      requests.cpu: "10"
    used:
      requests.cpu: 2250m
```

## Comparisons
| Aspect | Limit quota | Request quota |
|---|---|---|
| Interacts with | Workload resource **limits** | Workload resource **requests** |
| Controls | Max resources workloads can **consume** in a namespace | Max resources workloads can **reserve** in a namespace |
| Risk if unset | Combined workloads could consume enough to affect other namespaces | A single workload could reserve excessive resources, blocking other requests |

| Aspect | ResourceQuota | ClusterResourceQuota |
|---|---|---|
| Scope | Single namespace | Multiple namespaces (via label selector) |
| `hard` key location | Directly under `spec` | Nested inside `spec.quota` |
| Visibility to regular users | Directly viewable | May not have read access — view via `AppliedClusterResourceQuota` instead |
| Creation via web console | Administration → ResourceQuotas | Administration → CustomResourceDefinitions (cannot create CRQ from ResourceQuotas page, though it can display them) |

## Exam Tips / Gotchas
- After setting **any** compute quota, workloads **must** define the corresponding request/limit key (e.g. a `limits.cpu` quota requires workloads to set `resources.limits.cpu`).
- Excessive/overly strict quotas can cause **resource underutilization** and unnecessarily limit workload performance.
- **Resource quotas are extensible and Kubernetes cannot verify correctness** — e.g. `count/deployment=1` (singular, wrong) silently has **no effect**; the correct syntax is `count/deployments.apps` (plural + API group).
- To verify a quota is defined correctly: create it with an artificially low value in a test environment and confirm it actually blocks/limits something; check the quota's **used** value reflects real resources.
- Exceeding some quotas (e.g. object count on the resource being created directly, like a Deployment count quota) **fails immediately** with a clear error.
- Exceeding **other** quotas (e.g. a pod count quota when creating a Deployment) can cause the parent resource (Deployment) to appear to succeed while it **never becomes available** — check **namespace events** for the real failure reason (e.g. ReplicaSet `FailedCreate` due to exceeded pod quota).
- `--all-namespaces` **does NOT work** with `AppliedClusterResourceQuota` — you must specify `-n <namespace>` to view these.
- The ResourceQuotas page in the web console **can display** ClusterResourceQuota objects but **cannot be used to create them** — use CustomResourceDefinitions page or CLI instead.
- Resource quotas generate the **`kube_resourcequota`** metric, viewable via Observe → Metrics for planning/trend analysis.

## Glossary
- **ResourceQuota**: namespace-scoped resource limiting compute and/or object-count usage for that namespace.
- **ClusterResourceQuota (CRQ)**: OpenShift resource applying an aggregate quota across multiple namespaces via a label selector.
- **AppliedClusterResourceQuota**: auto-generated per-namespace view of a ClusterResourceQuota's applicability/usage, for users without direct CRQ read access.
- **count/resource_type**: quota key syntax for limiting object counts of core-group resources.
- **count/resource_type.group**: quota key syntax for limiting object counts of non-core-group resources.
- **kube_resourcequota**: metric generated by resource quotas, viewable in Observe → Metrics.
