## Quick Summary
Covers OpenShift's authentication/authorization resources (User, Identity, ServiceAccount, Group, Role, ClusterRole), how the OAuth server and identity providers work, initial cluster-admin access methods (kubeconfig X.509 cert, kubeadmin virtual user), and step-by-step configuration/management of the HTPasswd identity provider for a dev/test environment.

## Key Concepts
- **User** — an entity that interacts with the API server; permissions assigned via roles directly or via group membership.
- **Identity** — records successful authentication attempts from a specific user and identity provider; stores data about the authentication source.
- **Service Account** — allows applications to communicate with the API independently, without borrowing regular user credentials, preserving credential integrity.
- **Group** — a set of users; authorization policies can grant permissions to a group at once instead of per-user; OpenShift also provisions system/virtual groups automatically.
- **Role** — a project-level collection of policy rules defining permitted API operations on specified resource types.
- **Cluster Role** — a cluster-wide collection of policy rules; can control access at cluster and project levels across all projects.
- **Authentication vs authorization** — authentication layer identifies/authenticates the user; authorization layer (using RBAC policies) accepts/rejects the request based on privileges.
- **system:anonymous / system:unauthenticated** — virtual user/group assigned to requests without a valid access token or certificate.
- **OpenShift OAuth server** — run by the authentication operator; issues OAuth access tokens after validating identity via a configured identity provider; auto-creates identity and user resources on successful login.
- **Identity providers** — HTPasswd, Keystone, LDAP, GitHub/GitHub Enterprise, OpenID Connect; multiple providers (same or different kinds) can be configured on one OAuth custom resource.
- **kubeconfig file** — created during installation; embeds a never-expiring X.509 client certificate; enables cluster-admin CLI access without logging in, via `KUBECONFIG` env var or `--kubeconfig` option.
- **kubeadmin virtual user** — auto-created after installation, with cluster-admin privileges; password is dynamically generated and hashed in a `kubeadmin` secret in `kube-system`.
- **HTPasswd identity provider** — validates users against a secret containing an htpasswd file (username + hashed password); only a cluster administrator can modify the secret; not recommended for production, dev/test use only.
- **htpasswd file** — flat file with username:hashed-password entries, managed via the `htpasswd` utility (from the `httpd-tools` package).
- **htpasswd-secret** — secret storing the htpasswd file content, referenced by the OAuth custom resource's HTPasswd provider config; must use the `htpasswd=` key prefix.
- **OAuth custom resource (`oauth cluster`)** — cluster-wide config resource where identity providers are registered under `.spec.identityProviders`.
- **mappingMethod: claim** — default mapping method between provider identities and user objects; with this default, a user cannot log in via multiple different identity providers under one account.
- **cluster-admin role** — cluster-wide role granting full administrative privileges over any resource in the cluster.

## Operators
- **Authentication operator** — runs the OpenShift OAuth server; redeploys pods in the `openshift-authentication` namespace after HTPasswd secret updates.

## Config / YAML Snippets
OAuth custom resource with HTPasswd identity provider:
```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: my_htpasswd_provider      # Prefixed to provider usernames to form the identity name
    mappingMethod: claim              # Default; prevents logging in via multiple different providers
    type: HTPasswd                     # Type of identity provider
    htpasswd:
      fileData:
        name: htpasswd-secret            # Secret containing the htpasswd file
```

|---|---|---|

|---|---|---|

## Exam Tips / Gotchas
- The `-c` option in `htpasswd` **replaces all file content** if the file already exists — use only for initial file creation.
- The `htpasswd=` **key prefix is required** when creating/updating the HTPasswd secret (`--from-file htpasswd=/path`), unless the file itself is literally named `htpasswd`.
- Only a **cluster administrator** can modify the HTPasswd secret — regular users cannot change their own passwords under this provider.
- **HTPasswd is not recommended for production** — suitable only for development/proof-of-concept environments.
- After updating the HTPasswd secret, the **authentication operator redeploys** the OAuth pods in `openshift-authentication` — wait for new pods to be ready before verifying login.
- Deleting a user requires **more than removing them from the identity provider** — you must also delete the `user` resource AND the corresponding `identity` resource.
- **Never delete the kubeadmin user** without first configuring another user with cluster-admin privileges — if you delete the kubeadmin secret without another admin (or a saved kubeconfig), you **permanently lose administrative access** and must reinstall the cluster.
- With the default `mappingMethod: claim`, a user **cannot log in via multiple different identity providers**.
- User and Identity resources are **usually not created in advance** — OpenShift creates them automatically after a successful interactive OAuth login.

## Glossary
- **User**: OpenShift resource representing an entity that interacts with the API.
- **Identity**: OpenShift resource recording a successful authentication attempt and its provider.
- **Service Account**: account allowing applications to access the API without borrowing user credentials.
- **Role**: project-scoped set of API permission rules.
- **Cluster Role**: cluster-wide set of API permission rules.
- **OAuth access token**: credential issued by the OpenShift OAuth server after successful authentication.
- **htpasswd**: Apache HTTP Server utility for managing a flat file of username/hashed-password entries.
- **kubeadmin**: auto-created virtual cluster-admin user with a generated password.
- **mappingMethod**: OAuth identity provider setting controlling how provider identities map to user objects.
