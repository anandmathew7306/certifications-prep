## Quick Summary
Covers OpenShift's RBAC model — rules, roles, and bindings, at cluster vs. local (namespaced) scope — the default cluster roles, how to assign/remove them via `oc adm policy` and `oc policy`, the different user types (regular, system, service account), and basic group management.

## Key Concepts
- **RBAC (Role-based Access Control)** — technique for managing resource access; determines whether a user can perform actions within a cluster or project; authorization is a separate step from authentication.
- **Rule** — allowed actions for objects or groups of objects.
- **Role** — a set of rules; users and groups can be associated with multiple roles.
- **Binding** — assignment of users or groups to a role.
- **Cluster RBAC** — roles and bindings that apply across all projects.
- **Local RBAC** — roles and bindings scoped to a given project (namespaced); local role bindings can reference both cluster and local roles.
- **Two-level RBAC hierarchy** — cluster roles enable reuse across projects; local roles enable per-project customization; authorization evaluation uses both cluster role bindings and local role bindings together.
- **Namespaced role** — another term for a local role (scope local to a namespace).
- **User object** — represents a user who can be granted permissions via roles (directly or through group role bindings).
- **Regular users** — most interactive OpenShift users; represented by the `User` object; represent a person with platform access.
- **System users** — auto-created for infrastructure to securely interact with the API (e.g. cluster administrator, per-node user, router/registry users); names start with `system:` prefix (e.g. `system:admin`, `system:node:node1.example.com`); an anonymous system user handles unauthenticated requests by default.
- **Service accounts** — system users associated with projects; used by workloads to invoke Kubernetes APIs; some are auto-created at project creation; by default have **no roles** — roles must be granted explicitly; represented by the `ServiceAccount` object; names start with `system:serviceaccount:namespace:` prefix (e.g. `system:serviceaccount:default:deployer`).
- **Group** — a resource representing a set of users; used to assign permissions to multiple users at once.
- **self-provisioners cluster role binding** — by default associates the `self-provisioner` cluster role with the `system:authenticated:oauth` group, enabling members to create their own projects.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc adm policy add-cluster-role-to-user cluster-role username` | Adds a cluster role to a user | — |
| `oc adm policy add-cluster-role-to-user cluster-admin username` | Grants cluster-admin to a user | — |
| `oc adm policy remove-cluster-role-from-user cluster-role username` | Removes a cluster role from a user | — |
| `oc adm policy remove-cluster-role-from-user cluster-admin username` | Removes cluster-admin from a user | — |
| `oc adm policy who-can delete user` | Checks whether a user can perform an action on a resource | — |
| `oc policy add-role-to-user role-name username -n project` | Adds a (namespace-scoped) role to a user within a project | `-n` = project |
| `oc policy add-role-to-user basic-user dev -n wordpress` | Adds the basic-user role to the dev user, scoped to the wordpress project | `-n` |
| `oc adm groups new lead-developers` | Creates a new group | — |
| `oc adm groups add-users lead-developers user1` | Adds a user to a group | — |

## Comparisons
| RBAC Level | Description |
|---|---|
| Cluster RBAC | Roles and bindings that apply across all projects |
| Local RBAC | Roles and bindings scoped to a given project; can reference both cluster and local roles |

| Default Role | Description |
|---|---|
| admin | Manages all project resources, including granting other users access to the project |
| basic-user | Gets basic information about projects and users |
| cluster-admin | Superuser access to cluster resources; full control of all projects |
| cluster-status | Access cluster status information |
| cluster-reader | Can access/view most objects but cannot modify them |
| edit | Can create/change/delete common application resources (e.g. services, deployments); cannot act on management resources (limit ranges, quotas) or manage project access permissions |
| self-provisioner | Can create their own projects (via projectrequests resources) |
| view | Can view project resources but cannot modify them |

| User Type | Description | Name prefix |
|---|---|---|
| Regular user | Represents a person with platform access | — |
| System user | Auto-created for infrastructure API interaction | `system:` |
| Service account | System user tied to a project, used by workloads | `system:serviceaccount:namespace:` |

## Exam Tips / Gotchas
- **Authorization is a separate step from authentication.**
- `oc policy add-role-to-user` scopes the role binding to the **specified project namespace only** — even for a cluster role like `basic-user`, using this subcommand limits it to that one project.
- The `edit` role **cannot** act on management resources (limit ranges, quotas) and **cannot** manage project access permissions — it's constrained to common application resources.
- The `self-provisioner` cluster role is bound by default to the **`system:authenticated:oauth`** group — this is what lets authenticated users create projects.
- Service accounts have **no roles by default** — roles must be explicitly granted for workloads to use specific APIs.
- Customizing/fine-tuning default roles is **outside the scope of this course**.
- API requests with no or invalid authentication are treated as the **anonymous system user**.

## Glossary
- **Rule**: allowed actions for objects/groups of objects (building block of a role).
- **Role**: a set of rules (project-scoped, i.e. local).
- **Cluster Role**: a set of rules applicable cluster-wide.
- **Binding**: assignment of a user/group to a role.
- **ServiceAccount**: object representing a project-associated system user used by workloads.
- **system: prefix**: naming convention for OpenShift system users.
- **system:serviceaccount:namespace: prefix**: naming convention for service account users.
