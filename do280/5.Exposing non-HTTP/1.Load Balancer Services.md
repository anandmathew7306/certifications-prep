## Quick Summary
Covers why ingresses/routes can't expose non-HTTP/non-SNI protocols, Kubernetes Service types (ClusterIP, NodePort, LoadBalancer), how LoadBalancer services work differently in cloud vs. bare-metal/non-cloud environments, and how the MetalLB Operator provides load-balancing for non-cloud clusters (layer-2 ARP vs. layer-3 BGP modes).

## Key Concepts
- **Ingress/Route limitation** — expose only HTTP and TLS-encrypted services supporting SNI (virtual hosting); cannot expose text-based protocols (SMTP, POP3, IMAP) or binary protocols (SSH, LDAP, MySQL); non-HTTP services require a different resource, with more setup effort and possibly more IP addresses — ingresses/routes are still the **preferred** method when usable.
- **Service (Kubernetes resource)** — provides transparent access to a workload running across multiple pods; contains a selector (pods that run the service) and a list of ports.
- **ClusterIP** — internal-only service type; acts as an internal load balancer, forwarding traffic to healthy backend pods.
- **NodePort** — exposes a service on a static port on every node's IP (`<NodeIP>:<NodePort>`); routes external traffic to the internal cluster IP, which load-balances to healthy pods.
- **LoadBalancer** — automatically provisions an external load balancer (typically from a cloud provider), giving a single stable public IP; external traffic → load balancer → service's node port → internal routing to healthy pods.
- **Cloud vs. self-hosted LoadBalancer behavior** — on a cloud provider, the cloud controller manager uses the provider's APIs to configure the load balancer automatically (e.g. AWS Elastic Load Balancing, Azure Load Balancer, IBM Cloud load balancer); this cloud automation is **not available in self-hosted clusters**, where an operator like **MetalLB** is needed instead.
- **Non-cloud (bare metal) LoadBalancer behavior** — Kubernetes assigns the service an IP from a pool of external addresses that cluster administrators prepare; admins must configure these addresses to be routable to a cluster node; nodes receiving traffic for that external IP forward it to the associated pods/VMs.
- **MetalLB** — load balancer implementation for Kubernetes clusters not running on a cloud provider (bare metal, hypervisor-based); operates in two modes: Layer-2 (ARP, default) or Layer-3 (BGP).
- **Layer-2 (ARP) mode** — default MetalLB mode; uses gratuitous ARP packets to advertise the load balancer service IP; incoming traffic for a MetalLB-managed IP is forwarded to the node that advertised it.
- **Layer-3 (BGP) mode** — uses BGP to advertise load balancer service routes to BGP peers; requires configuring an Autonomous System (AS) number; router picks an advertising node, sends traffic there, and the CNI's service proxy distributes it to matching pods.
- **MetalLB custom resources** — `MetalLB` (main instance), `IPAddressPool` (range of IPs MetalLB can allocate), `L2Advertisement` (enables layer-2 ARP advertisement for a given IP pool); all created in the `metallb-system` project.

## Operators
- **MetalLB Operator** — installed via Operator Lifecycle Manager; provides load balancing for non-cloud (bare metal/hypervisor) OpenShift clusters; requires configuring an IP address pool and (for layer-2) L2Advertisement custom resources; creates resources in the `metallb-system` project — access to this project must be explicitly granted to non-cluster-admins to view MetalLB custom resources.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc get metallb -n metallb-system` | Shows the main MetalLB instance | `-n` |
| `oc get ipaddresspool -n metallb-system` | Shows the configured IP address pool(s) for MetalLB | `-n` |
| `oc get l2advertisement -n metallb-system` | Shows configured layer-2 advertisements | `-n` |
| `oc expose ... --type LoadBalancer` | Imperatively creates a LoadBalancer service | `--type LoadBalancer` |
| `oc get service` | Shows service details including EXTERNAL-IP once assigned | — |
| `oc get example-lb -o jsonpath="{.status.loadBalancer.ingress}"` | Retrieves the assigned load balancer IP from the resource status | `-o jsonpath` |

## Config / YAML Snippets
LoadBalancer service definition:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: example-lb
  namespace: example
spec:
  ports:
  - port: 1234            # Exposed port
    protocol: TCP
    targetPort: 1234
  selector:
    name: example            # Pod selector
  type: LoadBalancer          # LoadBalancer service type
```

## Comparisons
| Service Type | Scope | Mechanism |
|---|---|---|
| ClusterIP | Internal only | Acts as internal load balancer to healthy backend pods |
| NodePort | External | Exposes a static port on every node's IP; routes via cluster IP to healthy pods |
| LoadBalancer | External | Provisions an external load balancer with a stable public IP; routes via node port then internally to healthy pods |

| Aspect | Cloud Environment | Non-cloud (Bare Metal) Environment |
|---|---|---|
| Load balancer provisioning | Automatic via cloud controller manager and provider APIs (e.g. AWS ELB, Azure LB, IBM Cloud LB) | Manual — cluster admin prepares/configures a pool of external IP addresses and routes them to nodes |
| Requires extra operator | No | Yes — e.g. MetalLB |

| Aspect | Layer-2 (ARP) | Layer-3 (BGP) |
|---|---|---|
| Default | Yes | No |
| Mechanism | Gratuitous ARP packets advertise the service IP | BGP advertises routes to peer routers |
| Extra config required | — | Autonomous System (AS) number |
| Traffic distribution | Forwarded to the node that advertised the IP | Router picks an advertising node; CNI service proxy then distributes to matching pods |

## Exam Tips / Gotchas
- **Prefer ingresses/routes** to expose services whenever possible — non-HTTP exposure methods require more setup effort and potentially more IP addresses.
- Ingress/Route resources can only expose **HTTP** and **SNI-supporting TLS-encrypted** services — not SMTP/POP3/IMAP (text-based) or SSH/LDAP/MySQL (binary protocols).
- LoadBalancer services in **cloud environments** are automatically provisioned via the cloud controller manager; in **non-cloud/bare-metal environments**, this automation doesn't exist — an operator like **MetalLB** is required.
- Each Kubernetes LoadBalancer service creates a **separate load balancer** in cloud infrastructure — review per-load-balancer costs to estimate total network service cost.
- MetalLB's **layer-2 (ARP) mode is the default** when installed via the MetalLB Operator.
- Layer-3 (BGP) mode requires the administrator to configure an **Autonomous System (AS) number**.
- MetalLB custom resources (MetalLB, IPAddressPool, L2Advertisement) are created in the **`metallb-system`** project — non-admin access must be explicitly granted.
- After exposing a service via load balancer, **always verify connectivity** from intended network locations and test load balancing — some protocols may need further adjustment behind a load balancer.

## Glossary
- **SNI (Server Name Indication)**: TLS extension allowing virtual hosting for encrypted connections; required for a TLS service to be exposable via Ingress/Route.
- **ClusterIP**: Kubernetes Service type providing internal-only cluster access.
- **NodePort**: Kubernetes Service type exposing a static port on every node's IP.
- **LoadBalancer**: Kubernetes Service type provisioning an external load balancer with a stable public IP.
- **MetalLB**: load balancer implementation for non-cloud Kubernetes clusters.
- **IPAddressPool**: MetalLB custom resource defining the IP range available for LoadBalancer services.
- **L2Advertisement**: MetalLB custom resource enabling layer-2 (ARP) advertisement of load balancer IPs.
- **AS number (Autonomous System number)**: required configuration for MetalLB's layer-3 (BGP) mode.
