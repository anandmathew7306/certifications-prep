# Protecting Internal Traffic with TLS

## Outline
- Objectives
- Zero-trust Environments
- Securing Network Traffic

- Configuring Client Applications
- Rotating Certificates

## Quick Summary
Covers zero-trust principles, OpenShift's default encryption of control plane traffic (but not application traffic by default), securing external traffic via route TLS termination types, and securing internal traffic using the service-ca controller to auto-generate/sign service certificates, inject CA bundles into clients, and rotate certificates.

## Key Concepts
- **Zero-trust environment** — assumes every interaction starts untrusted; access limited to specifically allowed objects; communication must be encrypted; clients must verify server authenticity via a trusted CA.
- **Default OpenShift encryption** — Red Hat OpenShift encrypts network traffic between nodes and the control plane **by default** (stronger than default Kubernetes, which does not); however, **application traffic is not encrypted by default**, and apps don't necessarily verify each other's authenticity.
- **Route TLS termination types** — Edge (default: TLS terminates at ingress controller, unencrypted to pod), Passthrough (no termination at controller, pod decrypts), Re-encrypt (terminates at controller then re-encrypts to pod using a certificate — most secure type).
- **service-ca controller** — generates and signs service certificates for internal traffic; watches for services with a specific annotation and auto-creates a secret containing a signed cert/key pair.
- **service.beta.openshift.io/serving-cert-secret-name annotation** — applied to a Service to trigger the service-ca controller to generate a secret (named per the annotation value) in the same namespace, populated with `tls.crt` and `tls.key`.
- **Mounting the generated secret** — must be manually mounted as a volume into the application deployment; mount path/location is application-dependent.
- **service.beta.openshift.io/inject-cabundle=true annotation** — triggers the service-ca controller to inject its CA bundle into supported objects: ConfigMaps, API services, CRDs, mutating webhooks, validating webhooks.
- **CA bundle injection into ConfigMaps** — injected into the `service-ca.crt` key in the ConfigMap's `data` field; a **dedicated** ConfigMap must be used, since the controller **replaces all data** in the selected ConfigMap.
- **Service CA certificate validity/rotation** — valid for **26 months** by default; automatically rotated when validity falls below **13 months**; a **13-month grace period** follows rotation during which the original CA cert remains valid — pods trusting the original CA must be restarted during this window to pick up the new CA bundle.
- **Manual certificate rotation** — delete the secret containing a service certificate to force regeneration by the service-ca controller; delete the `signing-key` secret in `openshift-service-ca` to manually rotate the service CA certificate itself (this **immediately invalidates** the previous CA cert — all pods using service certs must be restarted).
- **Alternatives for internal TLS** — Red Hat OpenShift Service Mesh (encrypted service-to-service communication via mutual TLS/mTLS, plus advanced traffic management); cert-manager operator for Red Hat OpenShift (automates certificate lifecycle, can delegate signing to an external trusted service like Let's Encrypt, and manages renewal).

## Operators
- **service-ca controller** — generates/signs service certificates for internal traffic; injects CA bundles into annotated objects; manages certificate rotation.
- **cert-manager operator for Red Hat OpenShift** — automates certificate lifecycle; can delegate signing to external services (e.g. Let's Encrypt) and manage renewal.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc create route` | Creates encrypted routes from the CLI (see `--help` for termination options) | see `oc create route --help` |
| `oc annotate service hello service.beta.openshift.io/serving-cert-secret-name=hello-secret` | Triggers service-ca controller to generate a signed cert/key secret for a service | — |
| `oc create configmap ca-bundle` | Creates a dedicated ConfigMap to receive an injected CA bundle | — |
| `oc annotate configmap ca-bundle service.beta.openshift.io/inject-cabundle=true` | Triggers injection of the service-ca CA bundle into the ConfigMap | — |
| `oc delete secret hello-secret` | Manually rotates a specific service certificate (forces regeneration) | — |
| `oc delete secret/signing-key -n openshift-service-ca` | Manually rotates the service CA certificate itself (invalidates previous CA immediately) | `-n` |

## Config / YAML Snippets
Volume mount for a generated service certificate secret (NGINX deployment patch):
```yaml
spec:
  template:
    spec:
      containers:
        - name: hello
          volumeMounts:
            - name: hello-volume        # Volume name matching the volumes section
              mountPath: /etc/pki/nginx/  # Application-specific mount path
      volumes:
        - name: hello-volume
          secret:
            defaultMode: 420               # Read-write permissions the app recommends
            secretName: hello-secret          # Secret created via the serving-cert-secret-name annotation
            items:
              - key: tls.crt                    # Signed certificate key in the secret
                path: server.crt                   # App-specific destination filename
              - key: tls.key                     # Private key in the secret
                path: private/server.key             # App-specific destination path
```

## Comparisons
| Termination Type | TLS terminates at | Traffic to pod | Notes |
|---|---|---|---|
| Edge | Ingress controller | Unencrypted | **Default** type |
| Passthrough | Not terminated at controller | Encrypted (pod decrypts) | Pod handles decryption itself |
| Re-encrypt | Ingress controller (then re-encrypted) | Encrypted (with a cert, e.g. service cert) | **Most secure** termination type |

| Aspect | Kubernetes (default) | Red Hat OpenShift (default) |
|---|---|---|
| Node ↔ control plane traffic encryption | Not automatic | Automatically encrypted |
| Application traffic encryption | Not automatic | Also NOT automatic — must be configured |

## Exam Tips / Gotchas
- OpenShift encrypts **node ↔ control plane** traffic **by default** — this is stronger than default Kubernetes behavior — but **application traffic is NOT encrypted by default**.
- **Edge** is the **default** route TLS termination type; **Re-encrypt** is the **most secure**.
- The `inject-cabundle` annotation **replaces all existing data** in the target ConfigMap — always use a **dedicated** ConfigMap for the CA bundle to avoid data loss.
- Service CA certificate: **26-month validity**, auto-rotates when validity drops below **13 months**, followed by a **13-month grace period** where the old CA is still valid.
- During the CA rotation grace period, pods trusting the **original** CA certificate **must be restarted** to pick up the new CA bundle.
- Manually deleting the `signing-key` secret in `openshift-service-ca` **immediately invalidates** the previous service CA certificate — **all pods** using service certificates must be restarted for TLS to keep functioning.
- CA bundle injection annotation (`inject-cabundle=true`) can target: ConfigMaps, API services, CRDs, mutating webhooks, and validating webhooks.

## Glossary
- **Zero-trust environment**: security model assuming no interaction is trusted by default; requires explicit access and verified, encrypted communication.
- **service-ca controller**: OpenShift component that auto-generates/signs service certificates and injects CA bundles.
- **serving-cert-secret-name annotation**: triggers service-ca to generate a signed certificate secret for a Service.
- **inject-cabundle annotation**: triggers service-ca to inject its CA bundle into a supported object.
- **service-ca.crt**: the ConfigMap data key where the injected CA bundle is placed.
- **mTLS (mutual TLS)**: encryption scheme where both client and server verify each other's certificates (used by Service Mesh).
- **cert-manager operator**: automates certificate lifecycle management, including external CA delegation and renewal.
