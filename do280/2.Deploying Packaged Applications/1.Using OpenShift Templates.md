## Quick Summary
Covers OpenShift Templates — parameterized Kubernetes custom resources describing a set of related resources — including discovering/inspecting templates, instantiating them via `oc new-app` or `oc process`+`oc apply`, updating deployed template-based apps, and managing (copying, customizing, uploading) templates for production use.

## Key Concepts
- **Template** — a Kubernetes custom resource (OpenShift extension) describing a set of resource configurations; can have parameters and a set of labels applied to every generated object; can create any resource the user has permission to create in a project.
- **Cluster Samples Operator** — populates templates (and image streams) in the `openshift` namespace; template population can be opted out of or restricted at installation.
- **Template parameters** — allow deployment flexibility; can have a default `Value`, or be auto-`Generated` (e.g. `expression`) using a `From` regex-like pattern.
- **Object Labels** — labels applied to all resources a template creates.
- **oc process** — renders/transforms a template into a set of resource manifests using given parameter values; works on templates stored in files (`-f`) or in the cluster; requires write permission on the template's namespace.
- **--param-file** — passes parameter key=value pairs from a file instead of the command line; recommended to keep in version control for tracking production deployment parameters.
- **oc new-app --template** — convenient way to instantiate a template directly (creates live resources); suited for development/testing, not recommended for production-grade tracking.
- **Production template consumption pattern** — `oc process` (render to YAML) → `oc apply` (create/update resources) — supports better resource/config tracking than `oc new-app`.
- **Unprivileged user template access** — users can read templates in the `openshift` namespace by default and copy them into their own project (where they have write permission) to process them there.
- **Template update limitation** — reprocessing + `oc apply` works for simple changes (e.g. a parameter update) but many workload updates aren't possible this way — more complex management should use other mechanisms like Helm charts.
- **oc diff for template changes** — piping a reprocessed template (with new parameters) to `oc diff -f -` previews the effect of the parameter change against live resources before applying.
- **Copying/customizing templates for production** — recommended practice: copy the standard template, give it a new specific name, adjust default parameter values, and remove the `namespace` field before uploading elsewhere.
- **Uploading a template (`oc create -f`)** — creates a **template resource** in the project (not the resources the template defines); makes the template available/discoverable to anyone with project access.

## Operators
- **Cluster Samples Operator** — populates default templates and image streams into the `openshift` namespace; installation-time opt-out/restriction supported.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc get templates -n openshift` | Lists templates in a namespace (name, description, parameters, objects count) | `-n` |
| `oc describe template template-name -n namespace` | Shows detailed template info (params, labels, generated objects) | `-n` |
| `oc process --parameters postgresql-ephemeral -n openshift` | Shows only the parameters a template uses | `--parameters`, `-n` |
| `oc process --parameters -f my-postgresql.yaml` | Shows parameters of a template defined in a local file | `--parameters`, `-f` |
| `oc get template postgresql-ephemeral -o yaml -n openshift` | Retrieves the full YAML manifest of a template | `-o yaml`, `-n` |
| `oc new-app --template=postgresql-ephemeral -p POSTGRESQL_USER=my-user` | Instantiates a template directly, creating live resources | `--template=`, `-p key=value` |
| `oc process my-postgresql -p POSTGRESQL_USER=user1 -o yaml > my-postgresql-manifest.yaml` | Renders a template into a manifest file with parameter overrides | `-p`, `-o yaml` |
| `oc process -f my-postgresql.yaml -p POSTGRESQL_USER=user1 -o yaml > file.yaml` | Renders a template defined in a local file | `-f`, `-p`, `-o yaml` |
| `oc process my-postgresql -o yaml --param-file=my-postgresql-params.env > file.yaml` | Renders a template using parameters from a file | `--param-file=` |
| `oc process my-postgresql --param-file=my-postgresql-params.env \| oc apply -f -` | Renders and directly applies a template's resources to the cluster | `--param-file=`, pipe to `oc apply -f -` |
| `oc process my-postgresql -o yaml --param-file=my-postgresql-params-2.env \| oc diff -f -` | Previews changes from a new parameter set against live resources | pipe to `oc diff -f -` |
| `oc get template postgresql-ephemeral -o yaml -n openshift > my-postgresql.yaml` | Copies a template to a local file for customization | `-o yaml`, `-n` |
| `oc create -f my-postgresql.yaml` | Uploads a (customized) template as a resource to the current project | `-f` |
| `oc create -f my-postgresql.yaml -n shared-templates` | Uploads a template to a specific project | `-f`, `-n` |
| `oc get templates -n shared-templates` | Lists templates available in a specific project | `-n` |

## Config / YAML Snippets
Template manifest structure (excerpt, postgresql-ephemeral):
```yaml
apiVersion: template.openshift.io/v1
kind: Template
labels:
  template: postgresql-ephemeral-template   # Applied to all objects the template creates
metadata:
objects:                                     # Resources the template generates
- apiVersion: v1
  kind: Secret
  metadata:
- apiVersion: v1
  kind: Service
  metadata:
- apiVersion: apps.openshift.io/v1
  kind: DeploymentConfig
  metadata:
parameters:                                   # Template parameters with defaults/descriptions
- description: Maximum amount of memory the container can use.
  displayName: Memory Limit
  name: MEMORY_LIMIT
  required: true
  value: 512Mi
- description: The name of the OpenShift Service exposed for the database.
  name: DATABASE_SERVICE_NAME
```

Parameters file (`.env`-style, for `--param-file`):
```
MEMORY_LIMIT=1024Mi
POSTGRESQL_USER='db-user'
POSTGRESQL_PASSWORD='my-secret-password'
```

## Exam Tips / Gotchas
- To run `oc process` against templates stored in a namespace (e.g. `openshift`), you need **write permission** on that namespace.
- Unprivileged users can **read** templates in the `openshift` namespace by default, but must **copy** the template into a project where they have write permission in order to process it there.
- `oc new-app --template` is convenient for dev/test but **not ideal for production** — prefer `oc process` + `oc apply` for better resource/config tracking.
- Reprocessing a template and reapplying supports simple updates (e.g. changing a parameter), but **many workload updates aren't achievable** this way — consider Helm charts for more complex application management.
- When customizing a template for production, **remove the `namespace` field** — processing a template in a different project without removing/matching this field produces an **error**.
- Uploading a template via `oc create -f` creates a **template resource**, not the resources the template defines — the template becomes available to anyone with access to that project.
- Template parameters marked `Generated: expression` with a `From` pattern auto-generate default values (e.g. a random password).

## Glossary
- **Template**: an OpenShift-provided Kubernetes custom resource describing a parameterized set of related resource configurations.
- **Cluster Samples Operator**: populates default templates and image streams in the `openshift` namespace.
- **Object Labels**: labels the template applies to every resource object it creates.
- **--param-file**: option to `oc process` supplying parameter values from a file instead of the command line.
