## Quick Summary
Covers Helm as a Kubernetes application lifecycle manager: chart structure, installing/inspecting/upgrading/rolling back releases via CLI (`helm`) and the OpenShift Developer Console, managing chart repositories, and how Helm compares to Operators for complex application management.

## Key Concepts
- **Helm** — open source tool managing the lifecycle of Kubernetes applications via "charts"; often the supported mechanism to deploy specific applications, but doesn't cover all application management needs — Operators offer a more complete lifecycle model for complex applications.
- **Chart** — a package describing a set of deployable Kubernetes resources; a collection of files with a defined structure: `Chart.yaml` (metadata), `templates/` (resource definition files), `values.yaml` (default values).
- **Chart hooks** — executed by Helm at specific points during install/upgrade; automate tasks, enabling charts to manage more complex applications than pure manifest-based processes.
- **Release** — the result of deploying a chart; a chart can be deployed multiple times to the same cluster, each deployment being a distinct release with a unique release name.
- **Chart versions** — a chart can have multiple versions as authors release updates (new app versions, features, fixes).
- **Chart reference** — can point to a local directory path, or a path/URL to a gzip-compressed tar archive.
- **Go template feature** — chart authors use Go templates in resource definitions so user-provided values (e.g. image repository) can be substituted at install time.
- **values.yaml override pattern** — create a custom YAML file containing only the values you want to override (partial override); omitted keys retain chart defaults.
- **Release naming** — many charts use the release name to construct created resource names (e.g. `<release>-sa` for a service account); release names must be unique per deployment.
- **Release storage** — Helm stores release information as a Secret of type `helm.sh/release.v1`; must not be manually manipulated (removing it breaks Helm's ability to operate on the release).
- **Namespaced vs non-namespaced chart resources** — charts can contain either; most application charts don't create a namespace themselves — you typically create the target namespace yourself before installing.
- **Helm repository** — a distribution mechanism for charts (in addition to files, archives, container images); managed locally via `helm repo` subcommands, stored in `~/.config/helm/repositories.yaml`.
- **HelmChartRepository / ProjectHelmChartRepository (custom resources)** — required for a chart repository to appear in the OpenShift web console's Developer Catalog; `helm repo add` alone only affects local CLI config, not the console.
- **Developer Catalog (web console)** — central location to find/install applications including Helm charts, via the Developer perspective.
- **Topology view** — shows a deployed Helm release visually, including all Kubernetes resources (deployments, services, routes) it created.
- **Release Details page (console)** — organizes management functions: Details, Resources, Release History, Upgrade, Rollback, Notes.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `helm show chart chart-reference` | Displays general chart info (maintainers, source URL, etc.) | — |
| `helm show values chart-reference` | Displays the chart's default values (from `values.yaml`) | — |
| `helm install release-name chart-reference --dry-run --values my-values.yaml` | Previews the manifests/resources a chart install would create | `--dry-run`, `--values` |
| `helm install release-name chart-reference --values my-values.yaml` | Installs a chart, creating a release | `--values`, `--version` (specific chart version) |
| `helm list` | Lists releases in the current namespace | `--all-namespaces`, `--namespace` |
| `helm upgrade release-name chart-reference` | Upgrades an existing release (values and/or chart version) | `--dry-run` (preview), `--values`, `--version` |
| `helm history release_name` | Shows the upgrade/rollback log for a release | — |
| `helm rollback release_name revision` | Rolls back a release to an earlier revision | — |
| `helm repo add openshift-helm-charts https://charts.openshift.io/` | Adds a Helm chart repository (local config only) | — |
| `helm repo list` | Lists configured repositories | — |
| `helm repo update` | Updates configured repositories | — |
| `helm repo remove REPO1 REPO2 ...` | Removes configured repositories | — |
| `helm search repo` | Lists charts available in configured repositories | `--versions` = list all versions (default shows only latest) |

## Config / YAML Snippets
Minimal Helm chart directory structure:
```
sample/
├── Chart.yaml         # Chart metadata: name, version
├── templates/          # Application resource definitions (e.g. deployments)
│   └── example.yaml
└── values.yaml           # Default values for the chart
```

Example `helm show values` output:
```yaml
image:
  repository: "sample"
  tag: "1.8.10"
  pullPolicy: IfNotPresent
```

Custom values override file (overrides only the tag, keeps default pullPolicy):
```yaml
image:
  tag: "1.8.10-patched"
```

## Comparisons
| Aspect | Helm | Operators |
|---|---|---|
| Lifecycle model | Package-and-deploy model (install/upgrade/rollback of resource sets) | More complete lifecycle model for complex applications |
| Best suited for | Standard application deployment via charts | Applications needing deeper, ongoing operational logic |

| Aspect | `helm install` | `helm upgrade` |
|---|---|---|
| Starting state | Creates resources from a blank state | Interacts with existing cluster resources |
| Risk profile | Lower — new release | Higher — can have complex effects (e.g. conflicting changes) |
| Preview option | `--dry-run` | `--dry-run` |

## Exam Tips / Gotchas
- `helm upgrade` **by default automatically updates the release to the latest chart version** — always review chart documentation and use `--dry-run` before upgrading.
- **Do not manually manipulate** the release secret (`helm.sh/release.v1` type) — removing it breaks Helm's ability to manage the release.
- Rolling back can have **greater implications than upgrading**, since upgrades might not be fully reversible — test rollbacks in a non-production environment matching production upgrades first.
- `helm repo add` and other repo subcommands only affect **local configuration** (`~/.config/helm/repositories.yaml`) — they do **not** affect cluster resources, and repos added this way are **not visible in the web console** unless a cluster admin creates a `HelmChartRepository` (cluster-wide) or `ProjectHelmChartRepository` (project-scoped) custom resource.
- `helm search repo` shows only the **latest version** of each chart by default — use `--versions` to see all.
- Editing default values in the web console's YAML view during install is **equivalent to** using a custom `values.yaml` file with `helm install`.
- Uninstalling a Helm release is **irreversible** — deletes all managed resources, potentially including persistent data (if the chart is configured to delete PVCs).
- In the console, rolling back a release via the UI is **equivalent to** running `helm rollback`.

## Glossary
- **Chart**: a packaged Helm application describing a set of deployable Kubernetes resources.
- **Release**: the result of a specific chart deployment; identified by a unique release name.
- **Chart.yaml**: file containing chart metadata (name, version, etc.).
- **values.yaml**: file containing a chart's default configurable values.
- **Hook**: chart-defined action Helm executes at specific install/upgrade lifecycle points.
- **HelmChartRepository**: cluster-scoped custom resource making a chart repository visible in the OpenShift web console.
- **ProjectHelmChartRepository**: project-scoped custom resource making a chart repository visible in the OpenShift web console for a specific project.
