## Quick Summary
Covers how applications get authorized Kubernetes API access via service accounts and RBAC: creating a service account, granting it roles/cluster roles, binding it to a pod, obtaining/mounting its token, and scoping access to the same namespace, a different namespace, or all namespaces.

## Key Concepts
- **RBAC preconfigured in OpenShift** — applications need **explicit** RBAC authorization to access restricted Kubernetes APIs.
- **Service account** — a Kubernetes object within a project representing the identity of an application running in a pod.
- **Default service account** — used automatically if a pod definition doesn't specify one; OpenShift grants it **no rights** by default — appropriate for regular business workloads.
- **Why not modify the default service account** — granting extra permissions to the default service account affects **all** pods in the project, which is usually unintended — create a dedicated service account instead.
- **3-step process to grant API access** — (1) create an application service account, (2) grant the service account access to the appropriate Kubernetes API (via role/cluster role binding), (3) assign the service account to the application pods.
- **Use case: Monitoring applications** — need read access to watch resources/verify cluster health (e.g. Red Hat Advanced Cluster Security scanning containers for vulnerabilities).
- **Use case: Controllers** — continuously watch and reconcile toward a resource's intended state (e.g. Argo CD/GitOps controllers reacting to repo changes).
- **Use case: Operators** — automate creation/config/management of Kubernetes-native app instances; need permissions for configuration/maintenance tasks (e.g. a database operator creating a Deployment from a CR).
- **Role vs Cluster Role (for apps)** — Role grants permissions to API resources within a **single namespace**; Cluster Role grants permissions within one/more namespaces or **cluster-wide**, depending on how it's bound.
- **Default cluster roles (broader permissions)** — e.g. the `edit` cluster role is less restrictive than a custom minimal role — grants read on secrets (among other things) and allows creating/updating most objects.
- **Role binding vs cluster role binding for scoping** — using a **cluster role in a (namespace-scoped) role binding** restricts its effect to that one namespace; using a **cluster role binding** grants the permissions cluster-wide.
- **spec.serviceAccountName** — pod definition field specifying which service account the pod uses.
- **TokenRequest API** — used to generate a service account token; required both for external processes needing a manual token and internally by the kubelet for pods.
- **Token mounting for in-pod use** — OpenShift/kubelet automatically requests a token via TokenRequest API and mounts it at `/var/run/secrets/kubernetes.io/serviceaccount/token` for the application to read and use for API authentication — this is automatic for pods; external/off-cluster processes must request manually.
- **Service account token duration** — tokens requested via `oc create token` are valid for **1 hour by default**; adjustable via `--duration`.
- **Cross-namespace service account reference syntax** — `system:serviceaccount:project:service-account`.
- **Scoping levels** — same namespace (Role/ClusterRole + RoleBinding, service account in that namespace), different namespace (RoleBinding created in the **target** namespace, referencing the service account from the **source** namespace via the syntax above), all namespaces (ClusterRoleBinding).

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc adm policy add-role-to-user cluster-role -z service-account` | Binds a (cluster) role to a service account within the current namespace | `-z` = avoids needing the full `system:serviceaccount:project:` prefix for a same-project service account |
| `oc adm policy add-cluster-role-to-user cluster-role service-account` | Binds a cluster role to a service account with cluster-wide scope | — |
| `oc create token pipeline` | Requests a short-lived token for a service account (e.g. `pipeline`) | `--duration` = custom token validity duration (default: 1 hour) |

## Config / YAML Snippets
Custom ClusterRole granting read access to secrets:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: secret-reader
rules:
- apiGroups: [""]              # Empty string = core API group
  resources: ["secrets"]         # Resource type this role applies to
  verbs: ["get", "watch", "list"]  # Allowed actions
```

## Comparisons
| Aspect | Role | Cluster Role |
|---|---|---|
| Scope | Single namespace | One/more namespaces, or cluster-wide (depending on binding type) |
| Binding to restrict to one namespace | Role binding (inherent) | Role binding using a cluster role (still restricted to that namespace) |
| Binding for cluster-wide scope | Not possible | Cluster role binding |

| Scenario | Mechanism |
|---|---|
| App needs access to resources in its own namespace | Role/ClusterRole + RoleBinding (same namespace as app's service account) |
| App needs access to resources in a different namespace | RoleBinding created in the **target** namespace, referencing the service account via `system:serviceaccount:project:service-account` |
| App needs access to resources in all namespaces | ClusterRoleBinding |

## Exam Tips / Gotchas
- The **default service account** has **no rights** by default — this is intentional; do **not** add permissions to it, since that affects **every pod** in the project.
- Applications need **explicit** RBAC authorization — nothing is granted implicitly.
- A **cluster role used in a namespace-scoped role binding** is still restricted to that namespace — only a **cluster role binding** gives cluster-wide access.
- `-z` flag on `oc adm policy add-role-to-user` saves you from writing the full `system:serviceaccount:project:service-account` string — but only works for service accounts in the **current** project.
- Cross-namespace access requires creating the **RoleBinding in the target namespace** (where the resource lives), referencing the service account from the app's own namespace.
- `oc create token` tokens are **short-lived** (1 hour by default) — meant for external/manual use (CI/CD, scripts), not for long-running in-pod authentication (which uses the auto-mounted, kubelet-managed token instead).
- In-pod tokens are automatically mounted at **`/var/run/secrets/kubernetes.io/serviceaccount/token`**.

## Glossary
- **Service account**: Kubernetes object representing an application's identity within a project.
- **TokenRequest API**: API used to generate service account tokens (used both manually and automatically by kubelet).
- **spec.serviceAccountName**: pod field specifying which service account the pod uses.
- **system:serviceaccount:project:service-account**: syntax for referencing a service account from another project/namespace.
- **RoleBinding**: binds a role/cluster role to a subject within a specific namespace.
- **ClusterRoleBinding**: binds a cluster role to a subject with cluster-wide scope.
