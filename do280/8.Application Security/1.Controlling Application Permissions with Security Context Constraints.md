# Controlling Application Permissions with Security Context Constraints

## Quick Summary
Covers Security Context Constraints (SCCs) — the OpenShift mechanism limiting what a pod can do on the host (privileged mode, extra capabilities, host volumes, SELinux context, user ID) — the default SCCs, why public images can fail under `restricted-v2`, and how to bind a less-restrictive SCC (e.g. `anyuid`) to a workload via a service account.

## Key Concepts
- **Security Context Constraint (SCC)** — OpenShift security mechanism limiting a running pod's access to the host environment; controls: running privileged containers, requesting extra capabilities, using host directories as volumes, changing a container's SELinux context, changing the user ID.
- **restricted-v2 SCC** — the SCC most OpenShift-created pods use by default; provides limited access to resources external to OpenShift.
- **anyuid SCC** — defines the "run as user" strategy as `RunAsAny`, meaning the pod can run as **any** available user ID in the container — needed for images that require a specific (often non-random) user ID.
- **Public image compatibility issues under restricted-v2** — a container requiring a specific user ID may fail (restricted-v2 assigns a **random** user ID); a container listening on a privileged port (<1024, e.g. 80/443) may also fail because the random UID can't bind to privileged ports.
- **scc-subject-review** — subcommand (via `oc adm policy scc-subject-review`) that lists SCCs capable of overcoming a specific workload's limitations.
- **Service account + SCC binding** — to run a pod under a different (less restrictive) SCC, you must create a service account and bind the SCC to it, then set the deployment to use that service account.
- **Cluster-admin-only SCC assignment** — only cluster administrators can assign an SCC to (or remove one from) a service account.
- **Privileged containers** — some containers (e.g. S2I builder class) need host-runtime-level access beyond normal container limits; pose security risks since they can access any resource on the node; enabled via SCCs applied to a dedicated service account with privileged access.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc get scc` | Lists all SCCs defined in the cluster | — |
| `oc describe scc anyuid` | Shows details of a specific SCC (priority, users, groups, settings) | — |
| `oc describe pod console-5df4fcbb47-67c52 -n openshift-console \| grep scc` | Shows which SCC a specific pod uses | `-n` |
| `oc get deployment deployment-name -o yaml \| oc adm policy scc-subject-review -f -` | Lists SCCs that could resolve a deployment's access limitations | `-f -` |
| `oc create serviceaccount service-account-name` | Creates a service account | `-n` = target namespace (if different from current) |
| `oc adm policy add-scc-to-user SCC -z service-account` | Binds an SCC to a service account (cluster-admin only) | `-z` = service account, `-n` = namespace (if different) |
| `oc set serviceaccount deployment/deployment-name service-account-name` | Changes a deployment to use a specific service account (triggers redeploy) | — |

## Comparisons
| Aspect | restricted-v2 (default) | anyuid |
|---|---|---|
| User ID | Random | Any available user ID (`RunAsAny`) |
| Typical use | Most OpenShift-created pods | Images requiring a specific/known user ID |
| Privileged port binding (<1024) | Not possible (random UID can't bind) | Possible, depending on the specific user configured |

## Exam Tips / Gotchas
- Most OpenShift-created pods use the **restricted-v2** SCC by default.
- Public registry images can **fail under restricted-v2** for two common reasons: requiring a **specific user ID** (restricted-v2 assigns a random one), or needing to **listen on a privileged port** (<1024) — the random UID cannot bind to such ports.
- `oc adm policy scc-subject-review` is the tool to identify which SCCs would resolve a specific workload's access limitations.
- Only **cluster administrators** can assign/remove an SCC on a service account.
- **Use caution** relaxing SCCs — allowing a pod to run under a less restrictive SCC can **decrease overall cluster security**.
- Changing a deployment's service account via `oc set serviceaccount` **triggers a redeploy** of its pods.
- Privileged containers (e.g. S2I builders) can access **any resource on the node** — a real security risk — and require an SCC-enabled service account with privileged access.

## Glossary
- **SCC (Security Context Constraint)**: OpenShift resource limiting pod access to host-level capabilities.
- **RunAsAny**: SCC "run as user" strategy allowing a pod to run as any available user ID.
- **scc-subject-review**: `oc adm policy` subcommand listing SCCs that could satisfy a workload's requirements.
- **S2I (Source-to-Image)**: builder class of containers requiring privileged, host-level access.
