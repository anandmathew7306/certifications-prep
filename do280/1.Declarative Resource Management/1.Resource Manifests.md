## Quick Summary
Covers imperative vs declarative resource management in OpenShift — why manifests (declarative) are preferred for reproducibility/version control/GitOps over imperative one-off commands — plus how to create, validate, diff, apply, and patch manifests, and how to force pod restarts when secret/configmap changes don't auto-trigger a rollout.

## Key Concepts
- **Imperative commands** — configure resources one at a time using action-reflecting command names and options; good for development/testing/experimentation, gives clearer per-component error messages; drawbacks: impaired reproducibility, lack of version control, lack of GitOps support.
- **Declarative commands** — use a resource manifest (YAML/JSON file) declaring the intended state; preferred for managing resources; enables version control, traceability, rollback, and single-command reproducible deployment of multiple resources; supports CI/CD/GitOps automation.
- **Resource manifest** — a YAML or JSON file encapsulating all attributes of an application's resource(s) in one file or a set of related files; YAML is generally preferred/more popular than JSON.
- **--dry-run=client** — generates/prints the object that would be sent to the server without creating it; does not confirm server-side policy compliance.
- **--save-config** — adds config attributes (stores resource config in the `kubectl.kubernetes.io/last-applied-configuration` annotation) needed for future `oc apply` operations.
- **Multipart YAML file** — multiple manifests in one file separated by `---` lines; single-file approach keeps related manifests together (easier to reflect changes across resources); multi-file approach is more convenient for sharing individual resource definitions.
- **`kubectl.kubernetes.io/last-applied-configuration` annotation** — stores the last-applied manifest content; used by `oc apply` to detect and clear fields removed from the manifest.
- **--dry-run=server** — submits a server-side request without persisting the resource; confirms the manifest conforms to current server policies (unlike `--dry-run=client`).
- **--validate=true** — validates input against a schema; fails the request if invalid.
- **oc diff** — compares live objects against manifests, emphasizing significant/meaningful changes (unlike generic text-diff tools, which report noisy irrelevant differences like auto-added annotations); GitOps tools rely on this to detect out-of-band changes.
- **Update considerations for secrets/configmaps** — since pods read secrets/configmaps only at startup, applying an updated manifest that changes only secret/configmap values does NOT generate new pods automatically — pods remain stale until manually restarted.
- **oc apply mechanics** — compares three sources: the manifest file, the live resource configuration, and the `last-applied-configuration` annotation; creates the resource if missing; removes fields present in the annotation but absent from the manifest; updates the annotation after applying.
- **oc create vs oc apply for existing resources** — `oc create -f` is imperative and errors if the resource already exists; `oc apply -f` is declarative and reconciles current vs. intended state.
- **oc patch** — modifies/updates fields in an existing object using a JSON/YAML snippet or file; repeatable way to fix/update objects (e.g. distributing a patch for a quick fix before a full update).

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc create deployment db-pod --port 3306 --image registry.ocp4.example.com:8443/rhel9/mysql-80:1-237` | Imperatively creates a deployment | `--port`, `--image` |
| `oc set env deployment/db-pod MYSQL_USER='user1' MYSQL_PASSWORD='mypa55w0rd' MYSQL_DATABASE='items'` | Imperatively sets environment variables on a deployment | — |
| `oc explain deployment.spec.template.spec` | Shows field descriptions for a manifest path | — |
| `oc create deployment hello-openshift -o yaml --image ... --save-config --dry-run=client > file.yaml` | Generates a starter manifest file without creating the resource | `-o yaml`, `--save-config`, `--dry-run=client` |
| `oc create -R -f ~/my-app` | Creates resources from manifests in a directory (recursively) | `-f`, `-R`/`--recursive=true` |
| `oc create -f https://example.com/example-apps/deployment.yaml` | Creates resources from a manifest at a URL | `-f` |
| `oc apply -f ~/my-app/example-deployment.yaml --dry-run=server --validate=true` | Validates a manifest server-side without applying changes | `--dry-run=server`, `--validate=true` |
| `oc diff -f example-deployment.yaml` | Shows meaningful differences between a manifest and the live resource | `-f` |
| `oc rollout restart deployment deployment-name` | Forces a pod restart to pick up updated secret/configmap values | — |
| `oc patch deployment hello -p '{"spec":{"template":{"spec":{"containers":[{"name":"hello-rhel7","resources": {"requests": {"cpu": "100m"}}}]}}}}'` | Patches a deployment from an inline JSON snippet | `-p` |
| `oc patch deployment hello --patch-file ~/volume-mount.yaml` | Patches a deployment from a patch file | `--patch-file` |

## Config / YAML Snippets
Minimal (non-production-ready) deployment manifest generated via dry-run:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  annotations:
  creationTimestamp: null
  labels:
    app: hello-openshift
  name: hello-openshift
spec:
  replicas: 1
  selector:
    matchLabels:
      app: hello-openshift
  strategy: {}
  template:
    metadata:
      creationTimestamp: null
      labels:
        app: hello-openshift
    spec:
      containers:
      - image: quay.io/redhattraining/hello-world-nginx:v1.0
        name: hello-world-nginx
        resources: {}
status: {}
```

Cleaned-up/customized manifest:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  namespace: resource-manifests    # Prevents deployment to the wrong project
  labels:
    app: hello-openshift
  name: hello-openshift
spec:
  replicas: 2                       # Requires two replicas instead of one
  selector:
    matchLabels:
      app: hello-openshift
  template:
    metadata:
      labels:
        app: hello-openshift
    spec:
      containers:
      - image: quay.io/redhattraining/hello-world-nginx:v1.0
        name: hello-world-nginx
        ports:
        - containerPort: 8080        # Container port for the service to use
          protocol: TCP
```

Multipart manifest file (separated by `---`):
```yaml
---
apiVersion: apps/v1
kind: Deployment
metadata:
  namespace: resource-manifests
  annotations:
---
apiVersion: v1
kind: Service
metadata:
  namespace: resource-manifests
  labels:
    app: hello-openshift
  name: hello-openshift
spec:
```

Patch file content (mounting a PVC as a volume):
```yaml
spec:
  template:
    spec:
      containers:
        - name: hello
          volumeMounts:
            - name: www
              mountPath: /usr/share/nginx/html/
      volumes:
        - name: www
          persistentVolumeClaim:
            claimName: nginx-www
```

## Comparisons
| Aspect | Imperative Commands | Declarative Commands (Manifests) |
|---|---|---|
| Reproducibility | Impaired — sequence of commands must be tracked/maintained | Strong — single file/command reproduces the intended state |
| Version control | Not supported | Supported (manifests can be version-controlled) |
| GitOps support | Not supported | Supported |
| Error clarity | Clearer, per-component error messages | Can be harder to debug (like debugging a completed running app) |
| Best suited for | Development, testing, experimentation | Production deployments, reproducible/repeatable processes |

| Aspect | oc create -f | oc apply -f |
|---|---|---|
| Nature | Imperative | Declarative |
| Behavior on existing resource | Errors out | Reconciles current state vs. manifest, updates as needed |
| Sources considered | Manifest file only | Manifest file + live config + last-applied-configuration annotation |

| Aspect | --dry-run=client | --dry-run=server |
|---|---|---|
| What it does | Prints the object that would be sent to the server | Sends the request to the server to confirm compliance, without persisting |
| Catches server-side policy issues | No | Yes |

## Exam Tips / Gotchas
- `oc create -f` against a manifest for an **already-live** resource results in an **error** (imperative, doesn't account for current state) — use `oc apply -f` instead for updates.
- `--dry-run=client` only prints the object locally; cluster resource controllers can still refuse a manifest even if syntax is valid YAML — use `--dry-run=server` to confirm actual server policy compliance.
- Applying a manifest that changes **only** secret/configmap values does **NOT** automatically restart pods — pods read these only at startup, so they remain stale until you run `oc rollout restart deployment` (or delete the pod, for single-replica deployments).
- For multi-replica deployments, `oc rollout restart` is **preferred** over deleting pods manually, since it minimizes downtime.
- `oc diff` filters out noisy, meaningless differences (e.g. auto-added annotations/attributes from resource controllers) that plain text-diff tools would report — GitOps tools rely on `oc diff` to detect out-of-band changes.
- `--save-config` on `oc create` produces the annotations required for future `oc apply` commands to work correctly.
- The `oc patch` command modifies only the specified fields — if a field/volume already exists, the patch **replaces** the existing data with the new data.
- Use `-R`/`--recursive=true` with `oc create -f` to process manifests in subdirectories.

## Glossary
- **Resource manifest**: a YAML/JSON file declaring the intended state of one or more Kubernetes/OpenShift resources.
- **last-applied-configuration annotation**: stores the previously applied manifest content, used by `oc apply` to detect/remove fields no longer present.
- **GitOps**: practice of managing infrastructure/config via version-controlled manifests, applied and reconciled against the live cluster state.
