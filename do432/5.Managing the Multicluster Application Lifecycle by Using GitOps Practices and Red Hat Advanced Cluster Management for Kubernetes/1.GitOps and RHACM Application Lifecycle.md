# 5.1 GitOps + RHACM Application Lifecycle

- **GitOps**: DevOps practices applied to delivery/infra — Git repo = single source of truth, entire intended state declared and stored there. Uses **OpenShift GitOps** (Argo CD) integrated with RHACM.
- **Benefits**: declarative deployments, full audit trail/version control (easy rollback), consistency across dev/stage/prod (less drift), scalability (Pull model uses hub-spoke), better security (no need to centralize all cluster credentials), resilience (Pull model = no single point of failure), flexibility (clusters pull on their own schedule — good for intermittent connectivity).
- **Current application model** (replaces the deprecated Channel/Subscription/PlacementRule "Application Subscription Model"): built around **`ApplicationSet`**, working with:
  - **Placement** — picks target clusters from a `ClusterSet`.
  - **ClusterSet** — groups clusters for RBAC.
  - **GitOpsCluster** — represents an Argo CD server + its placement, tying Argo CD into RHACM's cluster management.
  - **Application** — the actual per-cluster deployment, generated *from* the ApplicationSet.
- **Push model**: hub-cluster Argo CD directly deploys manifests to managed clusters (needs hub to hold managed-cluster credentials). **Default** unless the Pull model is explicitly annotated.
  - Best when: hub has reliable outbound connectivity to all clusters; managed clusters can't reach Git directly (hub proxies); watch for hub CPU/memory limits at scale.
- **Pull model**: hub propagates resources via a **`ManifestWork`** object; each managed cluster runs its *own* Argo CD instance and pulls from Git itself.
  - Best when: firewalls allow outbound-only from managed clusters (hub can't initiate inbound); need to offload reconciliation work from the hub; want decentralized credentials (each cluster only needs its own Git access) and reduced blast radius if the hub has issues. Note: the **local cluster is excluded** as a Pull-model target.
