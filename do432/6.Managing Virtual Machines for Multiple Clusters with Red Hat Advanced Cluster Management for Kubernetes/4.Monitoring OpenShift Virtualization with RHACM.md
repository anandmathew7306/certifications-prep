# 6.7 Monitoring OpenShift Virtualization with RHACM

- RHACM extends the observability service with dedicated **Grafana dashboards** for virtualization (accessible via Infrastructure → Virtual machines → "Observability dashboards," or Grafana → Home → Dashboards → *ACM / OpenShift Virtualization*):
  - **Clusters Overview** — fleet-wide rollup: cluster/VM counts and health, VM counts by status, resource-utilization history per cluster (CPU/memory/network/storage IOPS). Filterable by cluster/operator health.
  - **Single Cluster View** — drills into one cluster: operator/version info, VM counts by status/OS, per-node/per-VM resource graphs, and an Alerts section (by severity, operator health impact, CSV issues). Cross-links from Clusters Overview.
  - **Single Virtual Machine View** — one VM's config, resource-usage history, and alerts.
  - **Virtual Machines Inventory** — searchable/filterable table of every VM (cluster, namespace, status, node, OS, instance type, etc.) — a jumping-off point for ops actions (power off, delete, clone, migrate).
  - **Virtual Machines by Time in Status** — tracks how long VMs have sat in a given state (stopped/starting/migrating/error) — useful for SLA/cleanup triage.
- **Right-sizing for OpenShift Virtualization** (Tech Preview): Prometheus-recording-rule-powered recommendations, enabled via RHACM governance (ships preconfigured policies/dashboards). Two dashboard families:
  - **Cluster/namespace-level**: *ACM Right-Sizing Namespace* — shows CPU/memory over/under-provisioning per namespace with a recommended adjustment.
  - **VM-level**: *VM Dashboard Overestimation* / *VM Dashboard Underestimation* (and a summary *Right Sizing OpenShift Virtualization Dashboard* showing total over/underestimation counts per cluster) — click through from the summary to a specific VM's detail dashboard. (A negative "underestimation" value simply means there is none.)
- **Troubleshooting workflow example**: start broad (Clusters Overview → spot the affected cluster) → narrow (Single Cluster View → spot the affected VM via resource graphs) → drill in (Single Virtual Machine View → confirm near-100% CPU/memory usage, pointing to an in-guest process issue rather than a platform problem).
