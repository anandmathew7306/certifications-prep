# 4.3 Networking with Multus CNI

- Kubernetes network model: every pod has its own IP; pods and nodes talk to each other without NAT.
- Limits: IPs are ephemeral and workloads only see the pod and service networks.
- **Multus** is a meta CNI plug-in that chains other CNI plug-ins so a pod or VM can have extra interfaces (multihoming).
  - Managed by the Cluster Network Addons Operator (CNAO), which the HyperConverged Operator deploys.
- Uses: static or DHCP IPs, external networks, traffic isolation.
- The pod network interface is always kept (`eth0` in pods, often `enp1s0` in Linux VMs). Extra ones: `netN` in pods, `enpNsM` in VMs.
- Extra networks are defined with a **NetworkAttachmentDefinition** (NAD), a namespaced CR. It must be in the same namespace as the VM.
- CNI plug-ins Multus can chain:
  - `bridge`: Linux bridge on the node; needed to put VMs on extra networks, shares the host's L2 domain.
  - `host-device`: exclusive use of a physical NIC; high throughput, low latency.
  - `ipvlan`: unique IPs, same MAC as the host NIC.
  - `macvlan`: unique MAC per pod/VM; good for DHCP or MAC-based licensing.
  - `SR-IOV`: virtual function on SR-IOV hardware.
- Admin must first prepare the nodes (e.g. the Linux bridge).
- Bridge NAD key fields: `type: cnv-bridge`, `bridge` (node bridge name), optional `vlan` and `macspoofchk`; the `resourceName` annotation limits scheduling to nodes with the bridge.
- Create in console: Networking -> Network Attachment Definitions. Check with `oc get net-attach-def -n <ns>`.
