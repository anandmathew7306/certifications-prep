# 4.5 Creating Virtual Machines on User-defined Networks

- A **user-defined network** (UDN) replaces the shared pod network as a namespace's primary network, isolated from other networks.
- Benefits:
  - Tenant isolation per namespace; a cluster UDN (admin only) can span several namespaces.
  - The same subnet can be reused in many namespaces (for example dev, test, prod).
  - IPs persist across restarts and live migration with the Layer2 topology, so migration needs no NAT.
  - Isolation without writing network policies.
- Limits: no `virtctl ssh`, no `oc port-forward`, no headless services, no readiness or liveness probes, no VM DNS record, cannot also join the pod network, no secondary UDNs. Internal services like the image registry are not reachable.
- The namespace must be created by an admin with the label `k8s.ovn.org/primary-user-defined-network`. The label cannot be added later.
- Until the UDN exists, no pods or VMs can start in that namespace.
- Create in console: Networking -> UserDefinedNetworks -> Create (one per namespace).
- CLI: a `UserDefinedNetwork` CR (`k8s.ovn.org/v1`) with:
  - `topology: Layer2` and `role: Primary` (the only values OpenShift Virtualization supports).
  - `subnets`: one IPv4 CIDR, optional IPv6.
  - `ipam.lifecycle: Persistent` (required for live migration).
- Check: `oc get userdefinednetwork <name> -o yaml` and look at the status conditions.
- VMs from the catalog get the right settings automatically; do not change the default network config.
- In YAML, set the interface binding to `l2bridge`. The guest must use DHCP to get its IP.
