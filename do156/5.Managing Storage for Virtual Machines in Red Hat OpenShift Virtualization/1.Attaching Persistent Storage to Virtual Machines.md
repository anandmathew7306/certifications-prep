# 5.1 Attaching Persistent Storage to Virtual Machines

- Container storage is ephemeral; persistent storage survives pod restarts.
- Building blocks:
  - CSI plug-ins connect the cluster to the storage back end.
  - StorageClass (cluster-wide): storage type, provisioner, reclaim policy, expansion.
  - PV (cluster-wide) is the actual volume; PVC (namespaced) is the request for one.
- Provisioning: static (admin creates PVs by hand) or dynamic (provisioner creates the PV when a PVC asks for a class).
- Volume modes: `Filesystem` (default) or `Block`. Block is recommended for VM disks (faster).
- Access modes: RWO, RWOP, ROX, RWX. Live migration needs RWX.
- Default class annotations:
  - `storageclass.kubernetes.io/is-default-class=true` = cluster default.
  - `storageclass.kubevirt.io/is-default-virt-class=true` = VM default, wins over the cluster default.
  - Boot sources use the default class and move if it changes.
- StorageProfile (cluster-wide, same name as its class) holds the best PVC defaults for VM disks. Order of entries sets the default. With a profile you only give the size.
- DataVolume (namespaced, `cdi.kubevirt.io`) = PVC settings plus a source (`http`, `pvc`, `blank: {}`, ...). Filesystem PVCs get about 5.5% extra space. Deleting the DV deletes its PVC and PV.
- Add a disk: VM -> Configuration -> Storage -> Add disk. Hot plug uses the SCSI bus (virtio-scsi), not virtio.
- Local node disks (hostPath, Local Storage, LVM Storage operators) work but no live migration.
- Storage class migration (Tech Preview in 4.18): Actions -> Migration -> Storage on a running VM.
