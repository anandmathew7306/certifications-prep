# 3.1 Virtual Machine Resources

- VMs keep state and data, so they behave most like StatefulSet pods.
- `VirtualMachine` (VM) is the template; the running copy is a `VirtualMachineInstance` (VMI). Like Deployment vs ReplicaSet: delete the VMI and the VM recreates it.
- Startup chain: `virt-controller` watches for VMIs -> `virt-handler` (DaemonSet on each node) -> creates the `virt-launcher` pod, which runs the VM through a local `libvirtd`.
- Consoles: VNC (default in web console, text or graphical), serial (text), RDP (Windows, needs QEMU guest agent).
- Networking options:
  - Default pod network with `masquerade` binding (NAT, cluster-internal only).
  - Primary user-defined network (UDN): per-project subnet replacing the pod network.
  - Multus + `NetworkAttachmentDefinition` for extra/external networks; SR-IOV for high performance.
- Storage: PVCs attach PVs to the VM.
- Boot sources: RAW/QCOW2 cloud image, ISO, container disk, or PVC. Registry imports create a `DataImportCron`. Managed under Virtualization -> Bootable Volumes.
- Golden images: Red Hat images imported by CDI into `openshift-virtualization-os-images`, auto-updated; controlled by `enableCommonBootImageImport` in the HCO.
- ConfigMaps/secrets are added to a VM as disks; create them first, then mount manually inside the guest.
- `virsh` (inside `virt-launcher`) is only for low-level troubleshooting; prefer the console, `oc`, or `virtctl` (e.g. `virtctl stop vm1`).
- `oc get vmis -A` lists all VMIs, including stand-alone ones.
- Ways to create VMs: templates (overridable), instance types (CPU/memory fixed, change the type to resize), YAML manifests (`virtctl create vm` generates a base).
