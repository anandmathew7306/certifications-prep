# 2.3 Deploying the OpenShift Virtualization Operator

- Install from OperatorHub (search "OpenShift Virtualization"); it goes into the `openshift-cnv` namespace.
- OLM first starts the operator pods (`virt-operator`, `cdi-operator`, `cluster-network-addons-operator`, `ssp-operator`, `hyperconverged-cluster-operator`, `hostpath-provisioner-operator`). They idle until their CRs exist.
- Next step: create a **HyperConverged** instance. HCO then creates the KubeVirt, CDI, SSP, and `NetworkAddonsConfig` CRs.
  - Ready when conditions show ReconcileComplete, Available, Upgradeable. Check with `oc get hco -n openshift-cnv`.
  - Useful fields: `nodePlacement` (infra/workloads), cluster-wide eviction strategy (VM-level setting wins), `liveMigrationConfig`, feature gates (e.g. `enableCommonBootImageImport`), `uninstallStrategy` (default blocks removal while VMs exist).
- Components deployed by virt-operator:
  - `virt-api`: REST entry point, validates VM/VMI objects.
  - `virt-controller`: cluster-wide; creates the pods for VMIs.
  - `virt-handler`: DaemonSet on every node; drives VMs to the wanted state.
  - `virt-launcher`: one pod per running VMI, uses its own `libvirtd` to run the VM.
- HPP is optional: create a `HostPathProvisioner` CR. Never put its storage pool on the OS partition.
- Requirements and gotchas:
  - Bare metal (on-prem, AWS, IBM Cloud) or IBM Z; CPUs need Intel VT / AMD-V and NX enabled.
  - Live migration needs shared RWX storage.
  - A default storage class is required (`storageclass.kubevirt.io/is-default-virt-class=true` or the normal default annotation).
  - Single-node OpenShift: no HA, live migration, or eviction strategies.
- VM objects: `VirtualMachine` (definition) creates a `VirtualMachineInstance` when started. Use `oc explain VirtualMachine`.
- `virtctl` starts, stops, and opens VM consoles; download it from Help -> Command Line Tools.
- Cluster settings: Virtualization -> Overview -> Settings.
