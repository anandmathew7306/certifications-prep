## Quick Summary

## Key Concepts
- **Ephemeral storage** — default container storage; lifetime tied to the pod, not shareable across pods, deleted with the container.
- **Persistent Volume (PV)** — cluster storage resource; provisioned statically (admin creates manually) or dynamically (storage class creates on demand); accessible across the entire cluster, not exclusive to a project.
- **Persistent Volume Claim (PVC)** — a request from an application for storage (capacity, access mode); does not specify storage technology; belongs to a specific project/namespace and cannot be shared between projects; lifecycle tied to namespace, not to a pod.
- **Storage class** — describes a type/tier of storage; PVCs refer to a storage class rather than specifying provisioned storage directly; enables dynamic provisioning.
- **Static provisioning** — cluster administrator manually creates persistent volumes.
- **Dynamic provisioning** — storage classes create persistent volumes on demand based on PVC requests.
- **configMap volume** — externalizes app configuration data; portable/version-controllable.
- **emptyDir volume** — per-pod scratch directory, usually empty after provisioning; ephemeral storage.
- **hostPath volume** — mounts a file/directory from the host node into a pod; requires privileged pod config; not recommended for production (Red Hat supports it only for dev/testing on single-node clusters).
- **iSCSI** — IP-based standard providing block-level access to storage devices.
- **local volume** — accesses local storage devices (disk/partition) via standard PVC interface; tied to node availability, not suitable for all applications.
- **NFS volume** — shared access by multiple pods simultaneously; commonly used; Red Hat recommends only for nonproduction systems.
- **Volume access modes** — ReadWriteOnce (RWO), ReadWriteOncePod (RWOP), ReadOnlyMany (ROX), ReadWriteMany (RWX); a volume's provider determines supported modes.
- **Volume modes** — Filesystem (default if undefined) or Block; raw block volumes have no filesystem, set via `volumeMode: Block`.
- **persistentVolumeReclaimPolicy** — determines what happens to a PV after its PVC is deleted; values: Retain or Delete.
- **allowVolumeExpansion** — storage class field that must be `true` to permit PVC expansion.
- **Storage Object in Use Protection** — enabled by default; prevents removal of bound PVs/PVCs actively used by pods (postpones deletion until no longer in use), avoiding data loss.
- **PV lifecycle phases** — Available (unbound, usable by any PVC in any namespace) → Bound (bound to one PVC/namespace, exclusive) → In use (pod actively uses it; deletion postponed via Storage Object in Use Protection) → Released (PVC deleted, storage reclaimable) → Reclaimed (per reclaim policy: Retain or Delete).
- **Best-effort PVC-to-PV matching** — not an exact match; a PVC might bind to a PV with more capacity or broader access mode than requested.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc create -f my-fc-volume.yaml` | Creates a PV resource from a manifest (admin only) | `-f` = file |
| `oc set volumes deployment/example-application --add --name example-pv-storage --type persistentVolumeClaim --claim-mode rwo --claim-size 15Gi --mount-path /var/lib/example-app --claim-name mypvc` | Adds a PVC as a volume to a deployment | `--add`, `--name`, `--type` (emptyDir/hostPath/secret/configMap/persistentVolumeClaim), `--claim-mode` (default RWO; RWO/RWOP/RWX/ROX), `--claim-size` (SI notation), `--mount-path`, `--claim-name` (required for persistentVolumeClaim type) |
| `oc create -f pvc_file_name.yaml` | Creates a PVC from a manifest file | `-f` |
| `oc get pvc` | Lists available PVCs in the current namespace | — |
| `oc get storageclass` | Lists storage classes the cluster provides | — |
| `oc set volumes deployment/example-application --add --name example-pv-storage --type pvc --claim-class nfs-storage --claim-mode rwo --claim-size 15Gi --mount-path /var/lib/example-app --claim-name mypvc` | Adds a dynamically provisioned PVC volume, specifying a storage class | `--claim-class` = storage class name |
| `oc patch pvc/mypvc --type merge -p '{"spec": {"resources": {"requests": {"storage": "30Gi"}}}}'` | Expands a PVC's storage capacity | `--type merge`, `-p` = patch payload |
| `oc delete pvc/mypvc` | Deletes a PVC | — |

## Config / YAML Snippets
Manually created PV (Fibre Channel, block mode):
```yaml
apiVersion: v1
kind: PersistentVolume            # Resource type for PVs
metadata:
  name: block-pv                    # Name subsequent claims use to access the PV
spec:
  capacity:
    storage: 10Gi                     # Amount of storage allocated to this volume
  accessModes:
    - ReadWriteOnce                    # Access mode the storage device must support
  volumeMode: Block                   # Required for Block volumes (optional for Filesystem)
  persistentVolumeReclaimPolicy: Retain   # How the cluster handles the PV after PVC deletion: Retain or Delete
  fc:                                  # Attributes specific to Fibre Channel storage type
    targetWWNs: ["50060e801049cfd1"]
    lun: 0
    readOnly: false
```

Deployment updated with volumeMounts/volumes (from `oc set volumes`):
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  namespace: storage-volumes         # Must be same namespace as the PVC
spec:
  template:
    spec:
        volumeMounts:
        - mountPath: /var/lib/example-app    # Mount path in the container
          name: example-pv-storage             # Volume name associated with the mount
      volumes:
      - name: example-pv-storage              # Volume name
        persistentVolumeClaim:
          claimName: mypvc                       # Claim name bound to the volume
```

PersistentVolumeClaim manifest:
```yaml
apiVersion: v1
kind: PersistentVolumeClaim         # Resource type for a PVC
metadata:
  name: mypvc                          # Used in claimName field of a deployment's volumes section
  labels:
    app: example-application
spec:
  accessModes:
    - ReadWriteOnce                      # Requested access mode; storage class provisioner or eligible static PV must support it
  resources:
    requests:
      storage: 15Gi                       # Requested size; storage class matches or an eligible static PV must be ≥ this size
```

## Comparisons
| Access mode | Abbreviation | Description |
|---|---|---|
| ReadWriteOnce | RWO | Single node mounts read/write; multiple pods on that node can access simultaneously |
| ReadWriteOncePod | RWOP | Single pod in the cluster mounts read/write |
| ReadOnlyMany | ROX | Many nodes mount read-only |
| ReadWriteMany | RWX | Many nodes mount read/write |

| Volume type | RWO | RWOP | ROX | RWX |
|---|---|---|---|---|
| configMap | Yes | Yes | No | No |
| emptyDir | Yes | Yes | No | No |
| hostPath | Yes | Yes | No | No |
| iSCSI | Yes | Yes | Yes | No |
| local | Yes | Yes | No | No |
| NFS | Yes | Yes | Yes | Yes |

| Volume plug-in | Manually provisioned | Dynamically provisioned |
|---|---|---|
| AWS EBS | Yes | Yes |
| Azure disk | Yes | Yes |
| Cinder | Yes | Yes |
| Fibre channel | Yes | No |
| GCP | Yes | Yes |
| iSCSI | Yes | No |
| local | Yes | No |
| Red Hat OpenShift Data Foundation | Yes | Yes |
| VMware vSphere | Yes | Yes |

| Policy | Description |
|---|---|
| Retain | Enables manual reclamation of the resource for supporting volume plug-ins |
| Delete | Deletes both the PersistentVolume object and the associated external storage asset |

| Aspect | Static Provisioning | Dynamic Provisioning |
|---|---|---|
| PV creation | Cluster administrator creates manually | Storage class provisioner creates on demand |
| Developer knowledge needed | May need to request PV creation from admin | Declares storage requirements only |

## Exam Tips / Gotchas
- If `volumeMode` is not defined, Kubernetes defaults to **Filesystem**.
- `volumeMode: Block` is **required** for Block volumes but optional for Filesystem volumes.
- Red Hat does **not recommend hostPath in production** — supported only for dev/testing on single-node clusters.
- Red Hat recommends **NFS only for nonproduction systems**.
- PVC-to-PV binding is **not an exact match** — Kubernetes binds on a best-effort basis (e.g. a PVC may bind to a larger or more permissive PV).
- Once a PV is bound to a PVC, it **cannot** be bound to another PVC.
- Claims remain **unbound indefinitely** if no matching volume exists or can be created.
- When a default storage class is configured, a PVC must explicitly name a different storage class, or set `storageClassName: ""` to bind without one.
- Because admins can change the default storage class, **Red Hat recommends always specifying the storage class** explicitly when creating a PVC.
- **Storage Object in Use Protection is enabled by default** — deleting a PVC/PV in active use is postponed, not immediate, to prevent data loss.
- PVC storage can be **increased but not reduced** via expansion.
- `allowVolumeExpansion` must be `true` on the storage class to permit PVC expansion.
- If an expansion fails, the expansion controller **continuously retries**; recovery is possible by requesting a smaller (but still larger-than-current) size.
- Starting from **RHOCP 4.19**, developers can recover from a failed PVC expansion without administrator intervention (previously required manual admin steps: change reclaim policy, delete, re-create with smaller size).
- After deleting a PVC, the storage class reclaims the volume per the reclaim policy.

## Glossary
- **PV**: Persistent Volume — cluster-provisioned storage resource.
- **PVC**: Persistent Volume Claim — namespaced request for a PV.
- **StorageClass**: object describing/classifying a type of storage, enabling dynamic provisioning.
- **RWO / RWOP / ROX / RWX**: volume access mode abbreviations (see Comparisons table).
- **Reclaim policy**: PV setting (Retain/Delete) controlling behavior after the PV is released.
- **Storage Object in Use Protection**: default-enabled feature preventing deletion of actively used bound PVs/PVCs.
- **Raw block volume**: a volume without a filesystem, set via `volumeMode: Block`.
