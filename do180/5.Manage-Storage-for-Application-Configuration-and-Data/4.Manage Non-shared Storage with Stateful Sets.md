## Quick Summary
Covers clustering applications' storage needs (file vs block storage), why StatefulSets provide non-shared, per-pod persistent storage with stable identities (unlike Deployments), how headless services provide stable DNS for StatefulSet pods, and how to create/scale/delete StatefulSets and their PVCs via manifests.

## Key Concepts
- **Shared storage** — allocates resources from a single device to multiple services; solves multi-disk provisioning limitations.
- **File storage** — familiar directory structure; good for typical organized data volumes, backup, archiving, file sharing, collaboration; OS/file system handles locking/caching; poor for large/unstructured data sets.
- **NAS (Network-Attached Storage)** — file-based storage architecture giving networked devices a single access point with built-in security, management, fault tolerance; supports IP and TCP transfer protocols.
- **NFS (Network File System)** — protocol enabling remote hosts to mount and interact with file systems over a network as if local.
- **SMB (Server Message Block)** — application-layer protocol for accessing server resources like file shares and shared printers.
- **Block storage** — provides access to raw block devices (e.g. SAN, iSCSI); requires formatting/mounting; ideal for computationally heavy workloads needing raw-device-level speed; used for SQL databases (single-node), VMs (multinode), high-performance access, server-side processing, multi-block RAID configs.
- **Stateful application** — behaves according to past states/transactions affecting current/future state; simplifies failure recovery by resuming from a known point.
- **StatefulSet** — represents a set of pods with consistent identities: stable network identity (DNS, hostname) and storage (from volume claim templates); guarantees a network identity always maps to the same storage identity.
- **StatefulSet vs Deployment storage** — Deployment pods (used for stateless apps by default, can attach a PV for stateful use) all share the same PVC; StatefulSet pods do NOT share a PV — each has its own unique PV; pods created without a replica set, each replica records its own transactions with a maintained identifier across rescheduling.
- **Headless service** — a service with `clusterIP: None`; has no single stable ClusterIP; DNS lookup returns IPs of all individual selected pods, enabling clients to connect directly to a specific pod instead of through a load balancer.
- **StatefulSet pod DNS format** — `<pod-name>.<service-name>.<namespace>.svc.cluster.local` (e.g. `dbserver-0.mysql-headless`); enables peer discovery/direct communication, critical for distributed databases needing to address specific pods (e.g. for writes/replication).
- **StatefulSet pod naming** — `<statefulset-name>-<ordinal-index>` (e.g. `dbserver-0`); pods start one at a time by ordinal index, each waiting for readiness before the next starts.
- **StatefulSet PVC naming** — `data-<statefulset-name>-<ordinal-index>` (e.g. `data-dbserver-0`); one PVC per replica pod.
- **volumeClaimTemplates** — defines the persistent volume configuration applied identically to each StatefulSet replica.
- **Application-level replication** — StatefulSet does not replicate data between pods itself; data replication (e.g. primary/replica database roles) must be configured at the application level.

|---|---|---|
| `oc create -f headless-service.yaml` | Creates a headless service | `-f` |
| `oc get svc` | Verifies service creation (shows CLUSTER-IP as None for headless) | — |

| `oc delete statefulset dbserver` | Deletes a StatefulSet (does NOT delete its PVCs) | — |

## Config / YAML Snippets
StatefulSet definition:
```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: dbserver                    # Name of the stateful set
spec:
  selector:
    matchLabels:
      app: database                   # Application labels
  replicas: 3                          # Number of replicas
  serviceName: mysql                   # Governing service name; must exist before the stateful set
  template:
    metadata:
      labels:
        app: database                   # Application labels
    spec:
      containers:
      - env:                              # Environment variables (explicit or via secret)
        - name: MYSQL_USER
          valueFrom:
            secretKeyRef:
              key: user
              name: sakila-cred
        image: registry.lab.example.com:8443/redhattraining/mysql-app:v1   # Image source
        name: database                     # Container name
        ports:                              # Container ports
        - containerPort: 3306
          name: database
        volumeMounts:                       # Mount path for persistent volume (same config per replica)
        - mountPath: /var/lib/mysql
          name: data
      terminationGracePeriodSeconds: 10
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ "ReadWriteOncePod" ]    # Valid: ReadWriteOncePod, ReadWriteOnce, ReadWriteMany, ReadOnlyMany; RWOP recommended for production
      storageClassName: "lvms-vg1"            # Storage class for the persistent volume
      resources:
        requests:
          storage: 1Gi                          # Size of the persistent volume
```

Headless service definition:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: mysql                        # Name of the headless service
  labels:
    app: database
spec:
  ports:
  - port: 3306
    name: mysql
  clusterIP: None                     # Set to None to make the service headless
  selector:
    app: database                     # Must match labels of pods the stateful set created
```

## Comparisons
| Aspect | File Storage | Block Storage |
|---|---|---|
| Structure | Familiar directory structure | Raw block devices, no inherent file structure |
| Best for | Organized data, backup, archiving, file sharing, collaboration | Computationally heavy workloads needing raw-device-level speed |
| Example use cases | Web server content, file-sharing, FTP storage, backup archives | SQL databases (single-node), VMs (multinode), high-performance access, RAID configs |
| Locking/caching | Handled by OS and file system | — |
| Weakness | Poor handling of large/unstructured data sets | Typically requires formatting and mounting |
| Example protocols | NFS, SMB | SAN, iSCSI |

| Aspect | Deployment | StatefulSet |
|---|---|---|
| Default use | Stateless applications | Stateful applications (e.g. databases) |
| Storage sharing | All pods use the same PVC (if a PV is attached) | Each pod has its own unique PV — no sharing |
| Pod creation mechanism | Managed via replica set | Created without a replica set; each replica has its own identifier maintained across rescheduling |
| Imperative creation | Supported (`oc create deployment`) | **Not supported** — must use manifest files only |
| Pod naming | Random suffix (via replica set) | Stable `<statefulset-name>-<ordinal-index>` format |

| Aspect | Typical Service | Headless Service |
|---|---|---|
| ClusterIP | Assigned single stable IP | `None` — no ClusterIP |
| DNS lookup result | Single service IP (load-balanced) | IPs of all individual selected pods |
| Client connection | Via load balancer | Directly to a specific pod |

## Exam Tips / Gotchas
- **StatefulSets can only be created using manifest files** — `oc`/`kubectl` CLIs have no imperative command to create them.
- A StatefulSet's governing service (headless service) **must exist before** the StatefulSet is created.
- `ReadWriteOncePod` (RWOP) is the **recommended access mode for production** StatefulSet volumes.
- StatefulSet pods start **one at a time, sorted by ordinal index**, each waiting for readiness before the next starts.
- Deleting a StatefulSet with `oc delete statefulset` does **NOT** delete its associated PVCs — they remain (`Bound`) after deletion.
- StatefulSets do **not** replicate data between pods automatically — application-level configuration is required for replication (e.g. primary/replica roles); this configuration is out of scope for the course.
- Each StatefulSet pod's PVC follows the naming pattern `data-<statefulset-name>-<ordinal-index>`.
- OpenShift managed storage class availability varies by cloud: ROSA can use Amazon EFS-backed storage classes; Azure Red Hat OpenShift can use Azure Files; Red Hat OpenShift Dedicated can use Google Cloud Filestore.

## Glossary
- **NAS**: Network-Attached Storage — file-based storage architecture accessible to networked devices.
- **SAN**: Storage Area Network — block-based storage technology.
- **NFS**: Network File System — protocol for remote file system mounting.
- **SMB**: Server Message Block — application-layer protocol for accessing server file/printer resources.
- **StatefulSet**: workload resource managing pods with stable, unique identities and non-shared persistent storage.
- **Headless service**: a service with `clusterIP: None`, providing per-pod DNS resolution instead of load-balanced access.
- **volumeClaimTemplates**: StatefulSet field defining the PVC template applied to each replica.
- **Ordinal index**: the numeric suffix (0, 1, 2...) identifying each StatefulSet pod's stable position/identity.
