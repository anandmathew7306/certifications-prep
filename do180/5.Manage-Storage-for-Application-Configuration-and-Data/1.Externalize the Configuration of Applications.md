# Externalize the Configuration of Applications

## Quick Summary
Covers externalizing application configuration in Kubernetes using ConfigMaps (non-sensitive data) and Secrets (sensitive data, Base64-encoded not encrypted), how to create/update/delete them via CLI and web console, and how to consume them as environment variables or mounted volumes in pods.

## Key Concepts
- **Configuration externalization** — using env variables, external files, or CLI args to configure an app, making the container image portable across environments.
- **ConfigMap** — namespaced object injecting configuration data into containers; can store fine-grained (individual properties) or coarse-grained (whole config files/JSON blobs) data; data does not require protection.
- **Secret** — namespaced object storing sensitive data (passwords, sensitive config files, credentials like SSH keys/OAuth tokens); data is Base64-encoded, not encrypted; access restricted to fewer authorized users than ConfigMaps.
- **binaryData (ConfigMap field)** — points to a Base64-encoded file containing non-UTF-8 data (e.g. a binary Java keystore file).
- **Opaque secret type** — stores arbitrary key-value pairs, not validated against any convention.
- **Etcd encryption** — by default, ConfigMaps and Secrets are not encrypted at rest; encrypting the Etcd database encrypts secrets, configuration maps, routes, OAuth access tokens, and OAuth authorization tokens (out of scope for this course).
- **ConfigMap namespace scoping** — ConfigMap objects can be referenced only by pods in the same project/namespace.
- **secretKeyRef / configMapKeyRef** — used in a pod's `env` section to populate a single environment variable from a secret/configmap key.
- **envFrom / configMapRef / secretRef** — used to inject *all* key-value pairs from a ConfigMap/Secret as environment variables.
- **optional: true** (env var source field) — allows the pod to start even if the referenced ConfigMap/Secret or key does not exist.
- **Volume mount for secrets/configmaps** — Kubernetes creates one file per key at the mount path; file content is the decoded value.
- **--prefix option (`oc set env`)** — maps secret/configmap key names to environment variable names; lowercase keys are converted to uppercase to match the prefix pattern.
- **oc extract** — retrieves the latest secret/configmap data to local files (one file per key).
- **oc set data** — updates a secret or configmap from local file content.
- **kubelet eventually-consistent volume updates** — kubelet watches for changes to keys/values used in pod volumes and propagates changes to pods without requiring a restart; however, a restart is still needed if the application only reads config at startup.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc create secret generic secret_name --from-literal key1=secret1 --from-literal key2=secret2` | Creates a generic secret from literal key-value pairs | `--from-literal` (repeatable) |
| `kubectl create secret generic ssh-keys --from-file id_rsa=/path --from-file id_rsa.pub=/path` | Creates a generic secret from file contents | `--from-file key=path` |
| `oc create secret tls secret-tls --cert /path-to-certificate --key /path-to-key` | Creates a TLS secret | `--cert`, `--key` |
| `kubectl create configmap my-config --from-literal key1=config1 --from-literal key2=config2` | Creates a configuration map from literal values | `--from-literal` |
| `oc create cm my-config --from-literal key1=config1 --from-literal key2=config2` | Same as above, using the `cm` shortname | — |
| `oc create secret generic demo-secret --from-literal user=demo-user --from-literal root_password=zT1KTgk` | Creates a secret with literal key-value pairs | `--from-literal` |
| `oc create secret generic demo-secret --from-file user=/tmp/demo/user --from-file root_password=/tmp/demo/root_password` | Creates a secret from file contents | `--from-file key=path` |
| `oc set volume deployment/demo --add --type secret --secret-name demo-secret --mount-path /app-secrets` | Mounts a secret as a volume in a deployment | `--type secret`, `--secret-name`, `--mount-path` |
| `oc create configmap demo-map --from-file=config-files/httpd.conf` | Creates a configmap from an external file | `--from-file=` |
| `oc set volume deployment/demo --add --type configmap --configmap-name demo-map --mount-path /app-config` | Mounts a configmap as a volume in a deployment | `--type configmap`, `--configmap-name`, `--mount-path` |
| `oc set volume deployment/demo` | Confirms volumes attached to a deployment | — |
| `oc set env deployment/demo --from secret/demo-secret --prefix MYSQL_` | Sets env variables on a deployment from a secret | `--from`, `--prefix` |
| `oc extract secret/demo-secret -n demo --to /tmp/demo --confirm` | Extracts secret/configmap data to local files | `-n` = namespace, `--to` = target dir, `--confirm` = overwrite/create dir |
| `oc set data secret/demo-secret -n demo --from-file /tmp/demo/root_password` | Updates a secret/configmap from local file content | `-n`, `--from-file` |
| `kubectl delete secret/demo-secret -n demo` | Deletes a secret | `-n` = namespace |
| `oc delete configmap/demo-map -n demo` | Deletes a configmap | `-n` = namespace |
| `echo bXl1c2VyCg== \| base64 --decode` | Decodes a Base64-encoded secret value | `--decode` |

## Config / YAML Snippets
Deployment with env variable from a secret:
```yaml
apiVersion: apps/v1        # API version of the resource
kind: Deployment            # Deployment resource type
metadata:
  name: hello-deployment
spec:                        # General config: replicas, selector, template
  replicas: 1
  selector:
    matchLabels:
      app: hello-deployment
  template:
    metadata:
      labels:
        app: hello-deployment
    spec:                     # App-level config: image, container name, ports, env vars
      containers:
      - env:                    # Environment variables for the container
        - name: ENV_VARIABLE_1
          valueFrom:
            secretKeyRef:
              key: hello
              name: world
        image: quay.io/hello-image:latest
```

ConfigMap example:
```yaml
apiVersion: v1
kind: ConfigMap              # ConfigMap resource type
metadata:
  name: example-configmap
  namespace: my-app
data:                          # Configuration data (plain text)
  example.property.1: hello
  example.property.2: world
  example.property.file: |-
    property.1=value-1
    property.2=value-2
    property.3=value-3
binaryData:                    # Base64-encoded non-UTF-8 data (e.g. binary keystore)
  bar: R0lGODlhAgACAIABAO4AAP///yH5BAEHAAEALAAAAAACAAIAAAIDRAIFADs=
```

Secret example:
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: example-secret
  namespace: my-app
type: Opaque                   # Type of secret
data:                            # Base64-encoded string/data
  username: bXl1c2VyCg==
  password: bXlQQDU1Cg==
stringData:                      # Decoded (plaintext) string/data
  hostname: myapp.mydomain.com
  secret.properties: |
    property1=valueA
    property2=valueB
```

ConfigMap for env var initialization:
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: config-map-example
  namespace: example-app      # Project where the configmap resides; referenceable only by pods in same project
data:
  database.name: sakila         # Initializes database.name variable
  database.user: redhat         # Initializes database.user variable
```

Pod populating specific env vars from a ConfigMap:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-map-example-pod
  namespace: example-app
spec:
  containers:
    - name: example-container
      image: registry.example.com/mysql-80:1-237
      command: [ "/bin/sh", "-c", "env" ]
      env:                              # Environment variables for the pod
        - name: MYSQL_DATABASE            # Pod env var name
          valueFrom:
            configMapKeyRef:
              name: config-map-example      # ConfigMap to pull from
              key: database.name             # Key to pull
        - name: MYSQL_USER
          valueFrom:
            configMapKeyRef:
              name: config-map-example
              key: database.user
              optional: true                  # Pod starts even if configmap/key doesn't exist
```

Pod injecting all env vars from a ConfigMap:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-map-example-pod2
  namespace: example-app
spec:
  containers:
    - name: example-container
      image: registry.example.com/mysql-80:1-237
      command: [ "/bin/sh", "-c", "env" ]
      envFrom:                          # Pulls ALL env vars from a ConfigMap
        - configMapRef:
            name: config-map-example      # ConfigMap to pull from
  restartPolicy: Never
```

Pod populating env var from a Secret:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secret-example-pod
spec:
  containers:
    - name: secret-test-container
      image: busybox
      command: [ "/bin/sh", "-c", "export" ]
      env:                                # Environment variables for the pod
        - name: TEST_SECRET_USERNAME_ENV_VAR
          valueFrom:                        # Source of the environment variable
            secretKeyRef:                     # secretKeyRef source object
              name: test-secret                 # Name of the secret (must exist)
              key: username                       # Key extracted from the secret
```

## Comparisons
| Aspect | ConfigMap | Secret |
|---|---|---|
| Data sensitivity | Does not require protection | Holds sensitive info (passwords, credentials, keys) |
| Encoding | Plain text (data) or Base64 (binaryData) | Always Base64-encoded (not encrypted) |
| Access restriction | Standard | Restricted to fewer authorized users |
| Assignable as volume via web console | Not supported via web console | Supported via web console |

## Exam Tips / Gotchas
- Secret data is **Base64-encoded, not encrypted** — decodable via `base64 --decode`.
- By default, ConfigMaps and Secrets are **not encrypted at rest**; encrypting Etcd is required for that (out of scope of this course), and covers secrets, configmaps, routes, OAuth access/authorization tokens.
- ConfigMap objects can be referenced **only by pods in the same project/namespace**.
- `optional: true` on a configMapKeyRef/secretKeyRef lets the pod start even if the referenced object/key is missing.
- Running `oc extract` more than once requires `--confirm` to overwrite existing files (also used to create the target directory).
- Pods using **environment variables** from a secret/configmap must be **restarted** to pick up updates.
- Pods using a **volume mount** for secrets/configmaps get updates automatically (eventually consistent, via kubelet watching for changes) — **but** a restart is still required if the app only reads config at startup.
- You **cannot** assign configuration maps as volumes to workloads via the web console (secrets can be assigned as volumes via web console, configmaps cannot).
- `--prefix` option on `oc set env`: lowercase secret/configmap key names are converted to uppercase to match the prefix pattern.
- Kubernetes validates that data conforms to the declared secret type when using a specific secret resource type.

## Glossary
- **ConfigMap**: namespaced object for injecting non-sensitive configuration data into containers.
- **Secret**: namespaced object for storing sensitive data, Base64-encoded (not encrypted).
- **Opaque secret**: default secret type for arbitrary key-value data, no format validation.
- **binaryData**: ConfigMap field for storing Base64-encoded non-UTF-8 file content.
- **secretKeyRef**: reference to a specific key within a Secret, used to populate an env variable.
- **configMapKeyRef**: reference to a specific key within a ConfigMap, used to populate an env variable.
- **envFrom**: pod spec attribute that pulls all key-value pairs from a ConfigMap or Secret as env variables.
