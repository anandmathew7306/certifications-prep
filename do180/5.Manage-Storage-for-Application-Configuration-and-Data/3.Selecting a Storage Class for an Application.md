## Quick Summary
Covers how storage classes define types of dynamically provisioned storage, the impact of reclaim policy (Retain vs Delete) on data after PVC deletion, application responsibility for storage safety, factors admins use to design storage classes, how to create/inspect a StorageClass object, and how to bind a PVC to a specific storage class.

## Key Concepts
- **Storage class** — describes a type of storage for the cluster; also called a "profile" in other storage systems; admin-defined, used for dynamic provisioning.
- **Default storage class** — admin-selected class that Kubernetes uses to auto-provision a PVC that doesn't specify a storage class; can change, so developers should explicitly set the storage class.
- **Reclaim policy** — determines what happens to PVC data after the PVC is deleted; Kubernetes releases the volume but it isn't immediately available for another claim.
- **Retain reclaim policy** — deleting the PVC removes only the PVC object; the PV, physical storage device, and data remain; requires manual admin steps to reclaim.
- **Delete reclaim policy** — automatically deletes the PV, its data, and physical storage when the PVC is deleted; default for storage provisioners adhering to the Kubernetes Container Storage Interface (CSI) standard, and default if a storage class doesn't specify a reclaim policy.
- **Application responsibility for storage** — Kubernetes does not enforce data integrity/consistency between applications sharing a volume; improperly configured sharing (e.g. RWO PVC mounted by two pods on the same host) can cause unexpected behavior.
- **RWO vs RWX safety** — neither access mode guarantees files can be shared safely/reliably; RWO = only one cluster node can read/write; RWX = any pod can access for read/write.
- **StorageClass object** — defines a storage class; contains info about the storage provider and medium capabilities; globally scoped (not namespaced), available to all projects.
- **Parameters (StorageClass field)** — provisioner-specific config (file types, storage types, encryption, replication); omitted parameters use provisioner defaults.
- **Provisioner** — identifies the storage medium plug-in source; names starting with `kubernetes.io` are available by default in a cluster.
- **VolumeBindingMode** — `Immediate` (default): PV created immediately at PVC creation, without knowledge of pod scheduling needs, can cause unschedulable pods or issues with topology-constrained backends; `WaitForFirstConsumer`: PV created only once the consuming pod exists, respecting pod scheduling constraints.
- **AllowVolumeExpansion** — when `true`, allows growing (not shrinking) the underlying volume by editing the PVC.
- **storageClassName (PVC attribute)** — specifies which storage class a PVC requests; only PVs of that class can bind to the PVC.
- **PVC pending state** — occurs when no PV matches all PVC criteria; PVC waits until an appropriate PV becomes available.

## Config / YAML Snippets
StorageClass definition (AWS EBS example):
```yaml
apiVersion: storage.k8s.io/v1        # Required: current API version
kind: StorageClass                    # Required: API object type
metadata:
  name: io1-gold-storage                # Required: name of the storage class
  annotations:                           # Optional: annotations
    storageclass.kubernetes.io/is-default-class: 'false'
    kubernetes.io/description: Provides RWO and RWOP volumes
parameters:                             # Optional: provisioner-specific parameters
  type: io1
  iopsPerGB: "10"
provisioner: ebs.csi.aws.com            # Required: provisioner type for this class
reclaimPolicy: Delete                    # Optional: selected reclaim policy
volumeBindingMode: WaitForFirstConsumer   # Optional: selected volume binding mode
allowVolumeExpansion: true                # Optional: volume expansion setting
```

PVC requesting a specific storage class (block mode):
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-block-pvc
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Block
  storageClassName: storage-class-name    # Requests this specific storage class
  resources:
    requests:
      storage: 10Gi
```

## Comparisons
| Aspect | Retain Reclaim Policy | Delete Reclaim Policy |
|---|---|---|
| Effect on PVC deletion | Only the PVC object is deleted; PV, storage device, and data remain | PV, data, and physical storage are all automatically deleted |
| Manual steps needed | Yes — admin must manually reclaim (backup PV, delete PV, then reuse/remove storage asset) | No |
| Cost impact | Can result in higher storage costs if space isn't manually reclaimed | Can reduce storage costs |
| Default for | — | All CSI-compliant provisioners, and any storage class that doesn't specify a reclaim policy |

| Aspect | Immediate (VolumeBindingMode) | WaitForFirstConsumer (VolumeBindingMode) |
|---|---|---|
| When PV created | At PVC creation time | After the consuming pod is scheduled |
| Awareness of pod scheduling | No — can cause unschedulable pods or topology issues | Yes — PV created to match pod's scheduling constraints |
| Default | Yes | No |

## Exam Tips / Gotchas
- Because the default storage class can change, **developers should explicitly set the storage class** for their application rather than relying on the default.
- **Delete** is the default reclaim policy for CSI-compliant provisioners, and is used when a storage class doesn't specify a reclaim policy.
- To **keep data** after PVC deletion, choose a storage class with the **Retain** reclaim policy.
- Manual PV reclamation steps (Retain policy): back up PV YAML → delete the PV → the external storage asset (e.g. AWS EBS, GCE Persistent Disk, Azure Disk, Cinder) still exists after PV deletion → admin can create a new PV using the same storage/data, or remove the data and delete the storage asset.
- Kubernetes does **not** prevent inadvisable storage sharing between applications (e.g. two databases needing exclusive access sharing a volume) — this is the application's responsibility.
- Neither RWO nor RWX guarantee safe/reliable file sharing — it depends on the applications involved.
- `AllowVolumeExpansion: true` only allows **growing**, not shrinking, a volume.
- `WaitForFirstConsumer` avoids issues with topology-constrained or non-globally-accessible storage backends that `Immediate` binding mode can cause.
- OpenShift on managed infrastructure (e.g. ROSA, Azure Red Hat OpenShift) is often preconfigured with platform-specific storage classes (e.g. ROSA's default `gp3-csi` for AWS EBS volumes).
- A PVC that can't find a matching PV enters a **pending state** and waits.
- Declaring a PVC independently via YAML manifest (rather than only via `oc set volume`) is the **preferred method** for repeatability, configuration management, and version control.
- StorageClass objects are **globally scoped** (not namespaced) — available to all projects in the cluster.

## Glossary
- **CSI**: Container Storage Interface — Kubernetes standard for storage provisioners; Delete is the default reclaim policy for CSI-compliant provisioners.
- **StorageClass**: cluster-scoped object defining a storage type/provisioner/parameters for dynamic provisioning.
- **VolumeBindingMode**: StorageClass attribute controlling when a PV is bound/created relative to PVC and pod scheduling (Immediate or WaitForFirstConsumer).
- **AllowVolumeExpansion**: StorageClass attribute permitting PVC volume growth.
- **Provisioner**: the storage medium plug-in source associated with a storage class.
