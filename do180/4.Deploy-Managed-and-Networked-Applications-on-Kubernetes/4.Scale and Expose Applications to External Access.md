## Quick Summary
Covers how RHOCP exposes applications externally: service types (ClusterIP, LoadBalancer, ExternalIP, NodePort, ExternalName) for internal/external pod access, Route resources (RHOCP's preferred external exposure method), the newer Gateway API (GatewayClass/Gateway/HTTPRoute), Kubernetes Ingress objects, sticky sessions for session persistence, and scaling deployments/load balancing pods.

## Key Concepts
- **Service IP allocation** — RHOCP assigns each service a unique IP from an internal OVN-Kubernetes service network (separate from the pod network, accessible only within the cluster); default load balancing is round-robin.
- **Route** — RHOCP resource assigning a publicly accessible hostname to an application; handled by the HAProxy-based OpenShift ingress controller; supports advanced features beyond standard Ingress (TLS re-encryption, passthrough, split traffic for blue-green deployments).
- **Wildcard domain DNS** — resolves all names to configured IPs; doesn't recognize specific route hostnames — the ingress controller treats route hostnames as HTTP virtual hosts; invalid/non-existent route hostnames trigger an HTTP 503 error.
- **Route auto-generated hostname format** — `<route-name>-<project-name>.<default-domain>` when `--hostname` is omitted.
- **Ingress ↔ Route relationship** — creating an Ingress object auto-generates a managed Route object, which is deleted when the Ingress is removed.
- **RHOCP Gateway API** — alternative ingress traffic management framework managed by the Cluster Ingress Operator, using Red Hat OpenShift Service Mesh components for routing; separates concerns into GatewayClass (cluster-scoped controller config), Gateway (namespace-scoped entry point/listener/TLS config), and HTTPRoute (HTTP/terminated-HTTPS routing rules to services); does not support user-defined networks (UDNs).
- **Kubernetes Ingress** — provides functions similar to Route; supports HTTP, HTTPS, SNI, TLS with SNI; processed by the OpenShift ingress controller (TLS termination, path redirection, sticky sessions); Route is preferred for advanced features/native integration.
- **Sticky sessions** — ensure stateful traffic reaches the same pod for a user session, via cookies managed by the OpenShift ingress controller; cannot be set on passthrough routes (traffic is encrypted, router doesn't terminate TLS or read request contents).
- **Scaling** — adjusting deployment replica count updates the replica set, which creates/deletes pods to match; avoid modifying a replica set directly since the deployment controller manages it.
- **Service as internal load balancer** — distributes connections across replicated pods via the service name; when both an ingress controller and a service provide load balancing, RHOCP relies on the controller to direct traffic to pods.

## Operators
- **Cluster Ingress Operator** — manages the RHOCP Gateway API framework.
- **OpenShift ingress controller** — HAProxy-based; default controller processing Route and Ingress objects; supports third-party ingress controllers deployed in parallel.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc expose service api-frontend --hostname api.apps.acme.com` | Creates a route exposing a service | `--hostname`, `--target-port` (copied from deployment if omitted) |
| `oc delete route a-simple-route` | Deletes a route | — |
| `oc create ingress ingr-sakila --rule="ingr-sakila.apps.lab.example.com/*=sakila-service:8080"` | Creates an Ingress object | `--rule=` |
| `oc delete ingress frontend` | Deletes an Ingress object | — |
| `oc annotate ingress ingr-example ingress.kubernetes.io/affinity=cookie` | Configures cookie-based session persistence for an Ingress | — |
| `oc annotate route route-example router.openshift.io/cookie_name=myapp` | Configures a custom cookie name for Route session persistence | — |
| `ROUTE_NAME=$(oc get route route-example -o jsonpath='{.spec.host}')` | Captures a route's hostname into a variable | `-o jsonpath` |
| `curl $ROUTE_NAME -k -c /tmp/cookie_jar` | Accesses a route and saves the session cookie | `-k` = insecure, `-c` = save cookie jar |
| `curl $ROUTE_NAME -k -b /tmp/cookie_jar` | Reuses a saved cookie on subsequent requests | `-b` = load cookie jar |
| `oc scale --replicas=5 deployment/scale` | Scales a deployment's replica count | `--replicas=` |

## Config / YAML Snippets
Minimal Route definition:
```yaml
kind: Route
apiVersion: route.openshift.io/v1
metadata:
  name: a-simple-route      # Unique route name
  labels:                    # Selectors for the route
    app: API
    name: api-frontend
spec:
  host: api.apps.acme.com    # Hostname, a subdomain of the cluster wildcard domain
  to:
    kind: Service
    name: api-frontend         # Service to redirect traffic to (determines target pods)
  port:
    targetPort: 8443            # Maps router port to the service's endpoint port
```

GatewayClass definition:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: openshift-default
spec:
  controllerName: openshift.io/gateway-controller/v1   # Default RHOCP cluster ingress routing controller
```

Gateway definition:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: dev-gateway
  namespace: openshift-ingress
spec:
  gatewayClassName: openshift-ingress
  listeners:
  - name: http
    protocol: HTTP
    port: 80                    # Listening port
    hostname: "example.com"     # Domain served by this listener
```

HTTPRoute definition:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: dev-db
  namespace: openshift-ingress
spec:
  parentRefs:
  - name: dev-gateway           # Must match the associated Gateway object's name
  hostnames:
  - sales-db.example.com
  rules:
    - backendRefs:
        - name: sales-db          # Target Kubernetes service
          port: 8080
```

Minimal Ingress definition:
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend                # Unique name for the Ingress object
spec:
  rules:
  - host: www.example.com         # Hostname for inbound traffic
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend           # Service to redirect traffic to
            port:
              number: 80               # Service backend port
  tls:
  - hosts:
    - www.example.com
    secretName: example-com-tls-certificate   # TLS cert secret; requires matching host
```

## Comparisons
| Aspect | ClusterIP | LoadBalancer | ExternalIP | NodePort | ExternalName |
|---|---|---|---|---|---|
| Default | Yes (unless otherwise specified) | No | No | No | No |
| Accessibility | Internal to cluster only | Externally accessible via cloud provider load balancer | Virtual IP on a cluster node, routed to a pod via NAT | Specific port (default range 30000–32767) on every node's IP | Maps service to external DNS name via CNAME |
| Cost/Security note | Low overhead, automated | Can be costly if assigned per application; needs extra security config | Legacy feature, security concerns — direct node network connections conflict with most security policies | Requires direct node network connections — security risk; needs strict firewall/access controls | — |
| Recommended use | Most internal application communication | External exposure needing cloud LB | Only when specific requirements aren't met by LoadBalancer/NodePort | Use with caution and mitigations | External DNS mapping use cases |

| Aspect | Route | Ingress |
|---|---|---|
| Origin | RHOCP-specific | Standard Kubernetes |
| Advanced features | TLS re-encryption, passthrough, split traffic (blue-green) | TLS termination, path redirection, sticky sessions (via ingress controller) |
| Preferred for | Advanced features, native OpenShift ingress controller integration | Cases needing standard Kubernetes ecosystem compatibility |
| Relationship | — | Creating an Ingress auto-generates a managed Route, deleted when Ingress is removed |

## Exam Tips / Gotchas
- ClusterIP is the **default** service type unless otherwise specified.
- ExternalIP is called out as a **legacy feature due to security concerns** — use LoadBalancer or NodePort unless ExternalIP specifically meets requirements.
- NodePort's default port range is **30000–32767**.
- Omitting `--hostname` on `oc expose service` generates a hostname as `<route-name>-<project-name>.<default-domain>`.
- Invalid/non-existent route hostnames trigger an **HTTP 503** error (wildcard DNS resolves the name, but the ingress controller doesn't recognize it as a virtual host).
- Deleting an Ingress object also deletes its auto-generated managed Route object.
- Gateway API does **not** support user-defined networks (UDNs).
- Sticky-session cookies **cannot** be set on passthrough routes, since traffic is encrypted and the router doesn't terminate TLS or read request contents.
- Avoid modifying a replica set directly — always scale via the deployment, since the deployment controller manages replica set changes.
- Cloud-deployed clusters more commonly add a public ingress controller backed by a cloud load balancer rather than relying on the default router.

## Glossary
- **ClusterIP**: default service type providing an internal-only cluster IP.
- **LoadBalancer**: service type provisioning a cloud provider load balancer for external access.
- **ExternalIP**: legacy service type routing a node-assigned virtual IP to a pod via NAT.
- **NodePort**: service type exposing a service on a specific port across all node IPs.
- **ExternalName**: service type mapping to an external DNS name via CNAME.
- **Route**: RHOCP resource for exposing applications externally via HAProxy-based ingress controller.
- **Ingress**: standard Kubernetes resource for external HTTP/HTTPS/TLS/SNI exposure.
- **GatewayClass**: cluster-scoped Gateway API resource defining routing controller configuration.
- **Gateway**: namespace-scoped Gateway API resource defining network entry points/listeners/TLS.
- **HTTPRoute**: namespace-scoped Gateway API resource defining HTTP routing rules to backend services.
- **Sticky sessions**: cookie-based mechanism ensuring a user's requests reach the same pod.
- **Passthrough route**: a route type where TLS is not terminated by the router (traffic stays encrypted end-to-end).
