## Quick Summary
Covers how to monitor an OpenShift cluster via the web console — nodes/machines/machine configs, viewing node and pod logs, terminal access, metrics/alerting via Prometheus-based monitors, high-level Events, and the API Explorer for browsing resource types.

## Key Concepts
- **Node** — any single system (bare metal, virtual, or cloud) in the cluster where pods can run; runs services to communicate within the cluster and receives control plane operational requests.
- **Machine** (OpenShift-specific term) — the resource that describes a cluster node; especially valuable when provisioning infrastructure on public cloud providers.
- **MachineConfig resource** — defines the initial state and changes to files, services, OS updates, and critical OpenShift service versions for kubelet and cri-o services.
- **Debug pod** — an OpenShift node interface to a container running on the node; accessed from the node terminal to use host binaries.
- **ServiceMonitor resource** — defines how a specific service uses metrics to define a monitor and alerting values.
- **PodMonitor resource** — same monitoring approach as ServiceMonitor, but for pods.
- **Metrics /metrics endpoint** — HTTP service endpoint providing data metrics for monitoring cluster/application performance, authored via Prometheus client libraries.
- **Monitors** — processes that continuously assess a metric's value and alert based on a predefined condition.
- **Events** — high-level abstraction of log files, showing significant changes; useful for at-a-glance understanding of cluster/node/project/pod behavior (contrasted with deeper-detail logs).
- **API Explorer** — lets users view the catalog of Kubernetes resource types available in the cluster, including description, schema, and metadata.

## Operators
- **Machine Config Operator (MCO)** — cluster-level operator that maintains OS and configuration of cluster machines; uses MachineConfig resource definitions to continually validate and remediate machine state; orchestrates changes across affected nodes after a MachineConfig change.
- **OpenShift Cluster Observability Operator (COO)** — optional component enabling additional features like observability signal correlation and incident detection groups, for highly customizable monitoring stacks; offers a more tailored/detailed per-namespace view than the default monitoring system.

## Exam Tips / Gotchas
- MachineConfig change orchestration by the MCO is prioritized alphabetically by zone, using the `topology.kubernetes.io/zone` node label.
- In hosted control plane clusters, control plane nodes are NOT visible to cluster administrators — Compute → Nodes shows only compute nodes (control plane runs in a separate hosting cluster).
- Making changes directly on a cluster node from the terminal is not recommended, though common practice for diagnostics/remediation.
- To fix a pod: update the pod configuration and redeploy — not recommended to alter a running pod directly via terminal.
- Logs = deep/granular detail; Events = high-level abstraction for significant changes — know the distinction.
- API Explorer available starting from RHOCP version 4.

## Glossary
- **Node**: any system in the cluster where pods can run.
- **Machine**: OpenShift's resource describing a cluster node.
- **MachineConfig**: resource defining machine state/config (files, services, OS updates, kubelet/cri-o versions).
- **MCO**: Machine Config Operator.
- **COO**: Cluster Observability Operator.
- **ServiceMonitor / PodMonitor**: resources defining metrics-based monitors for services/pods respectively.
- **Prometheus**: open source monitoring and alerting toolkit used for metrics collection.
- **Debug pod**: container interface on a node accessed via terminal for diagnostics.
