## Quick Summary
Covers the Horizontal Pod Autoscaler (HPA), which automatically scales pod replicas based on observed metrics (CPU/memory) to handle load fluctuations; explains its control-loop mechanics, resource-request prerequisites, creation via CLI/YAML/web console, and monitoring via `oc get hpa`/`oc describe hpa`; also introduces the Vertical Pod Autoscaler (VPA).

## Key Concepts
- **HorizontalPodAutoscaler (HPA)** — resource type that automatically scales the number of pods in a replication controller, deployment, replica set, or stateful set based on observed metrics (e.g. CPU utilization).
- **Benefits of autoscaling** — high availability/performance (adds pods during traffic spikes), cost optimization (removes pods during low traffic, freeing resources for other workloads), operational efficiency (removes need for manual scaling intervention).
- **HPA control loop** — runs inside the Kubernetes controller manager; checks HPA resources every 15 seconds by default; uses metrics from the RHOCP monitoring stack (preinstalled).
- **Autoscaling steps per check cycle** — (1) retrieve target metric from HPA definition; (2) collect current metric value per targeted pod from the metrics server; (3) compute usage percentage per pod based on metric vs. resource requests; (4) compute average usage across targeted pods; (5) establish ratio between target and current average metric value; (6) use ratio to decide scaling direction.
- **Resource requests prerequisite** — HPA requires resource requests defined on pod containers to calculate utilization percentage; without them, scaling cannot be performed.
- **LimitRange resource** — can be added to a project to define default resource requests for pods (relevant when deployments lack explicit requests).
- **scaleTargetRef** — HPA YAML field pointing to the resource the HPA manages.
- **minReplicas / maxReplicas** — HPA fields specifying the minimum/maximum pod count; balances handling load bursts vs. avoiding cluster resource overload.
- **averageUtilization** — target average CPU (or memory) utilization percentage per pod; above target triggers scale-up, below triggers scale-down.
- **Memory-based autoscaling caveat** — not suitable for all applications, e.g. JVM-based apps that claim large memory at startup and don't release it; ineffective if memory usage doesn't correlate with load.
- **`<unknown>` TARGETS value** — HPA's initial state in `oc get hpa` output; may take up to 5 minutes to resolve; persistent `<unknown>` may indicate the target deployment lacks resource requests for the specified metric (HPA only scales pods with resource requests).
- **Vertical Pod Autoscaler (VPA)** — complements HPA; scales vertically by adjusting CPU/memory requests and limits for individual pods rather than adding/removing replicas.
- **VPA InPlaceOrRecreate update mode** — starting RHOCP 4.21; uses in-place pod resize when the node has sufficient capacity (no restart); otherwise re-creates the pod on a node with sufficient resources.

|---|---|---|

| `oc describe hpa hello` | Shows detailed HPA config, current metrics, and scaling event history | — |

## Config / YAML Snippets
HPA scaling on CPU utilization:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello
  namespace: test1
spec:
  scaleTargetRef:              # Points to the resource the HPA manages
    apiVersion: apps/v1
    kind: Deployment
    name: hello
  minReplicas: 1                # Minimum number of pods
  maxReplicas: 10                # Maximum number of pods
  metrics:                        # Metrics used for scaling decisions
    - type: Resource
      resource:
        name: cpu
        target:
          averageUtilization: 80    # Target avg CPU utilization %; above = scale up, below = scale down
          type: Utilization
```

HPA scaling on memory utilization:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello
spec:
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - resource:
      name: memory              # Set to memory to trigger scaling based on memory utilization
      target:
        averageUtilization: 80
```

## Exam Tips / Gotchas
- Pods created via `oc create deployment` do **not** define resource requests by default — HPA usage may require manually adding requests, using custom YAML, or a `LimitRange` resource with defaults.
- HPA **only scales pods with resource requests** — a persistent `<unknown>` value in `oc get hpa` TARGETS column often signals missing resource requests on the target deployment.
- HPA's `<unknown>` value can take up to **5 minutes** to resolve into an actual percentage after HPA creation.
- Default HPA check interval: **every 15 seconds** (controller manager).
- Memory-based autoscaling is not suitable for all apps — e.g. JVM apps that claim large memory upfront and never release it, breaking the load-to-memory correlation.
- min/max replica bounds balance handling sudden load bursts against overloading cluster capacity for other workloads.
- Starting **RHOCP 4.21**, VPA supports `InPlaceOrRecreate` mode — resizes in place when possible, re-creates the pod only if the node lacks sufficient capacity.

## Glossary
- **HPA**: Horizontal Pod Autoscaler — scales pod replica count based on observed metrics.
- **VPA**: Vertical Pod Autoscaler — adjusts CPU/memory requests/limits on individual pods rather than replica count.
- **scaleTargetRef**: HPA field referencing the resource being autoscaled.
- **averageUtilization**: HPA target metric field representing desired average resource utilization percentage.
- **LimitRange**: resource defining default resource requests/limits for pods in a project.
- **InPlaceOrRecreate**: VPA update mode (RHOCP 4.21+) that resizes pods in place when possible, or recreates them if needed.
