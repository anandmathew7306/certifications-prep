## Quick Summary
Covers how Kubernetes/OpenShift keep applications running after failures, what behaviors applications should exhibit to work well with cluster HA tooling, and the three core HA techniques (restarting pods, probing, horizontal scaling) — with restart policy explained in detail.

## Key Concepts
- **High availability (HA)** — makes applications more robust/resistant to runtime failures, decreasing the likelihood of complete unavailability; protects apps from themselves (bugs), their environment (networking issues), and other applications (resource exhaustion); also protects the cluster from misbehaving applications (e.g. memory leaks).
- **HA as augmentation, not substitute** — cluster-level HA tooling mitigates worst-case scenarios but does not replace fixing application-level issues.
- **Expected application behaviors for RHOCP** — tolerates restarts; responds to health probes (startup, readiness, liveness); supports multiple simultaneous instances; has well-defined/well-behaved resource usage; operates with restricted privileges.
- **Health check endpoint** — most HTTP-based apps provide an endpoint to verify health; the application itself is responsible for providing it and deciding how it determines its own state (e.g. only healthy if a dependent database is reachable) — this decision is at developer discretion.
- **Crashed vs. unhealthy-but-running pod** — a crashed pod can't respond to requests and may be auto-restarted depending on config; a pod that fails without crashing keeps running but the cluster won't route requests to it — detecting this requires appropriate health probes.
- **restartPolicy (pod spec field)** — controls whether kubelet restarts terminated containers in a pod; values: Always (default), OnFailure, Never.
- **Higher-level controllers (Deployment/StatefulSet)** — typically used to manage pods for application workloads; ensure a specified number of replicas are always running; automatically replace failed pods (core HA mechanism); require the pod template's `restartPolicy` to be set to `Always`.

## Comparisons
| Policy | Description |
|---|---|
| Always | The kubelet always restarts a terminated container (default) |
| OnFailure | The kubelet restarts a terminated container only if it exited with a non-zero exit code |
| Never | The kubelet never restarts a terminated container |

## Exam Tips / Gotchas
- `restartPolicy` default value is **Always**.
- Deployment/StatefulSet controllers **require** the pod template's `restartPolicy` to be set to `Always`.
- A pod that fails without crashing continues running, but the cluster stops routing requests to it — the cluster can only detect and act on this with appropriate health probes.
- Not all database-dependent applications need a health check tied to DB reachability — this is a developer decision, not a hard requirement.

## Glossary
- **HA**: High Availability.
- **restartPolicy**: pod spec field controlling kubelet's container restart behavior (Always/OnFailure/Never).
