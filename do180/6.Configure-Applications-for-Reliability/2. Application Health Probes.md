## Quick Summary
Covers Kubernetes health probes (startup, readiness, liveness), the three test types (HTTP GET, container command, TCP socket), timing/threshold configuration, and how to add probes via YAML, the `oc set probe` CLI command, or the web console.

## Key Concepts
- **Health probes** — enable the cluster to determine app status by repeatedly probing for a response; affect crash mitigation, failover/load balancing, monitoring, and scaling decisions.
- **Probe endpoint authoring** — developers code these during app development; endpoints must perform quickly (probes are called often) — no complicated DB queries or many network calls.
- **Startup probe** — determines when an app's startup process is complete; not called again after it succeeds (unlike liveness); if it doesn't succeed within a configurable timeout, the pod restarts per its restartPolicy; useful for apps with long start times, keeping the liveness probe short/responsive.
- **Readiness probe** — determines if the app is ready to serve requests; on failure, Kubernetes removes the pod's IP from the service resource (stopping traffic); keeps running even after failure — if it succeeds again, the pod's IP is added back to the service; addresses temporary issues (e.g. initial connections, cache loading, long batch jobs) to improve availability.
- **Liveness probe** — determines if the app container is in a healthy state; runs throughout the app's lifetime, after initial startup completes (unlike startup probe); if it fails enough times, the cluster restarts the pod per its restart policy.
- **HTTP GET test** — sends an HTTP GET to a specified endpoint; success = response code 200–399; other responses = failure.
- **Container command test** — runs a specified command in the container; exit code 0 = success; other codes = failure.
- **TCP socket test** — attempts to open a socket to the container on a specified port; success only if the connection is established.
- **periodSeconds** — how often, in seconds, the probe runs.
- **failureThreshold** — how many failed attempts are required before the probe itself is considered failed.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc set probe deployment/front-end --readiness --failure-threshold 6 --period-seconds 10 --get-url http://:8080/healthz` | Adds/modifies a probe on a resource | `--readiness` (or presumably `--liveness`/`--startup`), `--failure-threshold`, `--period-seconds`, `--get-url` = HTTP probe endpoint |

## Config / YAML Snippets
Deployment with a liveness probe:
```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
      - name: web-server
        livenessProbe:            # Defines a liveness probe
          failureThreshold: 6        # How many failures before mitigating
          periodSeconds: 10           # How often the probe runs
          httpGet:                     # Probe test type: HTTP request
            path: /health                # HTTP path to send the request to
            port: 3000                    # Port to send the HTTP request over
```

## Comparisons
| Aspect | Startup Probe | Readiness Probe | Liveness Probe |
|---|---|---|---|
| Purpose | Determines when startup process is complete | Determines if app is ready to serve requests | Determines if app container is healthy |
| Called after success | No — not called again once it succeeds | Yes — continues running throughout app lifetime | Yes — continues running throughout app lifetime |
| Timing relative to startup | Runs during startup | Runs throughout lifetime | Runs after initial startup completes |
| Failure action | Pod restarts per restartPolicy after configurable timeout | Pod's IP removed from service (traffic stopped); pod not restarted | Pod restarted per restart policy after enough failures |
| Best used for | Apps with long start times, to keep liveness probe short | Detecting temporary unavailability (caching, batch jobs, etc.) | Detecting unhealthy containers needing restart |

| Test Type | How it works | Success condition |
|---|---|---|
| HTTP GET | Sends HTTP GET to specified endpoint | Response code 200–399 |
| Container command | Runs specified command in container | Exit code 0 |
| TCP socket | Attempts to open socket on specified port | Connection established |

## Exam Tips / Gotchas
- Startup probe is **not called again** after it succeeds — this differs from readiness/liveness probes which run continuously.
- A **failed readiness probe** removes the pod's IP from the service (no restart) — a **failed liveness probe** (enough times) triggers a pod restart.
- Probe endpoints must be fast — no heavy DB queries or excessive network calls, since the cluster calls them often.
- Example timing math: failure threshold of 3 with periodSeconds of 5 → probe can fail up to 3 times before overall failure → issue can persist **at least 10 seconds** before mitigation begins.
- Running probes too often wastes cluster resources — balance frequency against responsiveness.
- `oc set probe` is **exclusive to RHOCP and oc** (not available in plain kubectl).
- Probes are defined on the pod template, so they can be added to any workload resource that uses one (e.g. deployments) via YAML update, `oc edit`, or `oc set probe`.

## Glossary
- **Startup probe**: Kubernetes probe checking whether app startup has completed.
- **Readiness probe**: Kubernetes probe checking whether an app can currently serve requests.
- **Liveness probe**: Kubernetes probe checking whether an app container remains healthy.
- **periodSeconds**: probe field defining how often the probe runs.
- **failureThreshold**: probe field defining how many failures trigger probe failure.
