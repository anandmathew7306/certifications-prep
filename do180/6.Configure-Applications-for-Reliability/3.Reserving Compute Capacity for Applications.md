# Reserving Compute Capacity for Applications

## Outline
- Objectives
- Kubernetes Pod Scheduling

## Quick Summary
Covers how the RHOCP pod scheduler places pods (filter → prioritize → select), how to configure CPU/memory resource requests for containers, and how cluster administrators inspect node/pod compute resource usage and allocatable capacity.

## Key Concepts
- **Pod scheduler** — determines pod placement onto nodes via a three-step process: filtering, prioritizing, selecting.
- **Filtering (scheduling step)** — narrows eligible nodes using node selectors (label matching) and predicates (e.g. resource requests for CPU/memory/storage); if all nodes are filtered out, pod can't be scheduled until a suitable node is available; generates a `FailedScheduling` event if all nodes are filtered out.
- **Prioritizing (scheduling step)** — scheduler computes a weighted score per eligible node using multiple priority criteria; higher scores = better candidates.
- **Selecting (scheduling step)** — scheduler selects the highest-scoring node (round-robin if tied); generates a `Scheduled` event after selection.
- **Resource request** — specifies the minimum compute resources required to schedule a pod; scheduler seeks a node with enough available resources to satisfy it.
- **Millicore** — a CPU core (virtual or physical) split into 1000 units; `1000m` = one full CPU core; fractional values also usable (e.g. `0.1` = `100m`; `1.0` = `1000m`).
- **Memory measurement** — measured in bytes (e.g. `1Gi`).
- **resources: {} (empty)** — shown in container spec when no resource requests are defined.
- **Allocatable** — the compute resources available to schedule pods on a node; formula: `[Node Capacity] - [system-reserved] - [Hard-Eviction-Thresholds]`.
- **System-reserved resources** — OpenShift automatically reserves CPU/memory for node components (kubelet, kube-proxy) and system components (sshd, NetworkManager); smaller nodes get a higher reservation percentage, larger nodes a lower percentage.
- **Tiered memory reservation formula** — 1 GiB flat for the first 8 GiB, 6% of the next 120 GiB (up to 128 GiB total), 2% of memory above 128 GiB.
- **CPU reservation enforcement** — enforced via cgroup controls; during CPU contention, system daemons get their reserved share and workload pods get the remainder; when not under CPU pressure, system processes can use unused CPU beyond their reserved share.
- **Scheduling limit** — when the sum of resource requests from all pods on a node reaches the allocatable limit, the scheduler stops placing additional pods on that node.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc set resources deployment hello-world-nginx --requests cpu=100m,memory=1gi` | Sets CPU/memory resource requests on a deployment | `--requests cpu=...,memory=...`; works with any resource with a pod template (e.g. Deployment, Job) |
| `oc describe node master01` | Shows node capacity, allocatable resources, and allocated/requested resources | — |
| `oc adm top pods -n openshift-dns` | Shows compute resource usage per pod in a project | `-n`/`--namespace` = project (defaults to current project if omitted) |
| `oc adm top node master01` | Shows resource usage of a specific cluster node | — |

## Config / YAML Snippets
Deployment container with resource requests:
```yaml
spec:
  containers:
  - image: quay.io/redhattraining/hello-world-nginx:v1.0
    name: hello-world-nginx
    resources:
      requests:
        cpu: "100m"          # 100 millicores of CPU
        memory: "1Gi"          # 1 gibibyte of memory
```

## Exam Tips / Gotchas
- If all nodes are filtered out during scheduling, a **FailedScheduling** event is generated for the pod.
- After a node is selected, the cluster generates a **Scheduled** event.
- `oc edit` requires correct YAML indentation — mistakes can silently prevent the editor from saving changes; `oc set resources` is a safer alternative.
- Tiered memory reservation example given: on a node with 16 GiB memory, OpenShift reserves **approximately 1.5 GiB** for node/system components.
- When resource requests from all pods on a node reach the allocatable limit, the scheduler **stops placing additional pods** on that node — even if raw capacity technically remains (due to reservations).
- `Total limits may be over 100 percent, i.e., overcommitted` — noted directly in `oc describe node` output regarding Allocated resources.
- Customizing the scheduler for advanced scheduling scenarios is **outside the scope of this course**.

## Glossary
- **Millicore**: 1/1000th of a CPU core; unit for CPU resource requests (e.g. `100m`).
- **Allocatable**: compute resources on a node available for scheduling pods, after system/eviction reservations.
- **FailedScheduling event**: generated when no node passes the filtering step for a pod.
- **Scheduled event**: generated when the scheduler selects a node for a pod.
