# Limit Compute Capacity for Applications

## Outline
- Objectives
- Setting Memory Limits
- Setting CPU Limits
- Viewing Requests, Limits, and Actual Usage

## Quick Summary
Covers the difference between resource requests (used for scheduling) and resource limits (used to cap consumption), how memory limits trigger the OOM killer while CPU limits throttle rather than kill, in-place pod resizing (RHOCP 4.22+), and how to view requests/limits/actual usage via CLI and web console.

## Key Concepts
- **Resource requests vs limits** — requests help the scheduler pick a node but do NOT restrict actual usage (e.g. a 1 GiB memory request doesn't cap consumption); limits actually prevent applications from consuming too many resources.
- **Overcommitment** — setting requests lower than peak usage overcommits node resources; if all apps on a node exceed their requested values simultaneously, the node can run out of memory/CPU. Red Hat recommends setting requests to the application's peak usage.
- **Memory limit** — specifies max memory a container can use across all its processes; memory cannot be reclaimed from a running process (unlike CPU) — when the limit is reached, the compute node selects and kills a process in the container.
- **cgroups v2** — Linux kernel mechanism RHOCP uses to implement resource limits and kill processes exceeding memory limits; starting RHOCP 4.19, cgroups v1 is removed and v2 is the only supported implementation.
- **OOM killer (Out-of-Memory killer)** — Linux kernel subsystem triggered when a container reaches its memory limit; selects and kills a process.
- **Runtime cgroups v2 awareness** — some runtimes rely on cgroups to detect available memory/CPU; older runtime versions may misread cgroups v2 resources, causing excess memory use and triggering OOMKilled; minimum versions with full cgroups v2 support: Java OpenJDK 8u372+, Node.js 22+, .NET 5+; upgrading the base image to a modern runtime is the safest fix.
- **Memory leak** — application bug where memory is used but not freed; in an infinite service loop, memory usage grows unbounded, potentially consuming all node memory; a memory limit mitigates this by enabling OpenShift to restart the app when it hits the limit.
- **lastState / OOMKilled** — when RHOCP restarts a pod due to an OOM event, the pod's `lastState` attribute is updated with reason `OOMKilled` (and exit code 137).
- **CPU limit** — CPU is a compressible resource; reaching the limit causes RHOCP to throttle the container's processes (slower, but not terminated) — unlike memory, exceeding a CPU limit never kills the container.
- **No CPU limit set** — container can consume as much CPU as available on the node; under CPU pressure, the kernel shares CPU among containers according to their CPU **requests** values.
- **CPU limit use case** — needed for consistent application behavior across clusters/nodes with differing hardware/configuration (e.g. dev vs prod); limits mitigate — but don't fully eliminate — differences like unequal clock speeds between otherwise similar CPUs.
- **In-place pod resizing** — starting RHOCP 4.22, generally available; allows changing CPU/memory requests and limits on a running container without re-creating/restarting the pod (previously required pod re-creation); controlled via a resize policy per resource: `NotRequired` or `RestartContainer`.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc set resources deployment/hello --limits memory=1Gi` | Sets a memory limit on a deployment's container | `--limits memory=` |
| `oc get pod hello-67645f4865-vvr42 -o yaml` | Views pod status including `lastState`/`OOMKilled` info after an OOM restart | `-o yaml` |
| `oc set resources deployment/hello --limits cpu=200m` | Sets a CPU limit on a deployment's container | `--limits cpu=` |
| `oc edit --subresource resize ...` / `oc patch --subresource resize ...` | Resizes a running pod's CPU/memory requests/limits without restart (RHOCP 4.22+) | `--subresource resize` |
| `oc describe node master01` | Shows per-pod CPU/memory requests and limits, plus a summary (allocated resources) | — |
| `oc adm top nodes` | Shows resource usage for cluster nodes (admin only) | — |
| `oc adm top pods -n openshift-console` | Shows resource usage per pod in a project (admin only) | `-n` = namespace |

## Config / YAML Snippets
Deployment with both requests and limits:
```yaml
apiVersion: apps/v1
kind: Deployment
spec:
    containers:
    - image: registry.access.redhat.com/ubi9/nginx-120:1-86
      name: hello
      resources:
        requests:
          cpu: 100m           # Minimum CPU needed to schedule the pod
          memory: 500Mi         # Minimum memory needed to schedule the pod
        limits:
          cpu: 200m             # Max CPU before throttling
          memory: 1Gi             # Max memory before OOM kill
```

Pod status showing an OOMKilled event:
```yaml
status:
  containerStatuses:
  - containerID: cri-o://806b...9fe7
    image: registry.access.redhat.com/ubi9/nginx-120:1-86
    lastState:
      terminated:
        containerID: cri-o://bbc4...9eb2
        exitCode: 137                    # Standard OOM exit code
        finishedAt: "2023-03-08T07:56:06Z"
        reason: OOMKilled                # Indicates the OOM killer terminated the process
        startedAt: "2023-03-08T07:51:43Z"
    name: hello
    ready: true
    restartCount: 1
```

## Comparisons
| Aspect | Memory Limit | CPU Limit |
|---|---|---|
| Resource type | Non-compressible — cannot be reclaimed from a running process | Compressible — can be throttled |
| Behavior on limit reached | Node selects and kills a process in the container; pod restarted per restartPolicy | Container's processes are throttled; app continues, but slower |
| Container terminated? | Yes (process killed, may cause pod restart) | No — never terminated for exceeding CPU limit |
| Mechanism | cgroups v2 + Linux OOM killer | cgroups v2 throttling |

## Exam Tips / Gotchas
- Resource **requests do not restrict actual usage** — only requests-based node selection; limits are what actually cap consumption.
- Starting **RHOCP 4.19**, cgroups v1 is removed — cgroups v2 is the only supported implementation.
- Runtimes older than **Java OpenJDK 8u372+, Node.js 22+, .NET 5+** may not fully support cgroups v2 and can misread available resources, risking unexpected OOMKilled events.
- **OOMKilled** status appears in `lastState.terminated.reason` with **exit code 137**.
- Memory limits are essential for mitigating **memory leaks** — restarts free the leaked memory when the limit is hit.
- CPU limit exceeded → **throttling only**, never container termination (unlike memory).
- Without a CPU limit, the kernel shares CPU among contending containers based on their **CPU requests** values.
- Clusters can differ in hardware beyond what limits observe (e.g. equal core count but different clock speeds) — requests/limits don't account for this; consider appropriateness across environments.
- **In-place pod resizing** (RHOCP 4.22+) removes the previous requirement to re-create pods when changing limits; resize policy per resource can be `NotRequired` or `RestartContainer`.
- `oc describe node` and `oc adm top nodes`/`oc adm top pods` must be run **as a cluster administrator**.
- Note in `oc describe node` output: "Total limits may be over 100 percent, i.e., overcommitted."

## Glossary
- **cgroups v2**: Linux kernel mechanism (control groups v2) used by RHOCP to implement/enforce resource limits.
- **OOM killer**: Linux kernel subsystem that kills a process when a container exceeds its memory limit.
- **OOMKilled**: pod status reason indicating the OOM killer terminated a container process.
- **Compressible resource**: a resource (like CPU) that can be throttled without terminating the process.
- **Non-compressible resource**: a resource (like memory) that cannot be reclaimed from a running process without killing it.
- **In-place pod resizing**: RHOCP 4.22+ feature allowing resource request/limit changes without pod re-creation.
- **Resize policy**: pod spec setting (`NotRequired` or `RestartContainer`) controlling restart behavior during in-place resize.
