# Automatic Image Updates with OpenShift Image Change Triggers

## Outline
- Objectives
- Using Triggers to Manage Images
- Configuring Image Triggers for Deployments
- Rolling out Deployments
- Rolling Back Deployments
- Managing Image Stream Tags

## Quick Summary
Covers how OpenShift image change triggers automatically roll out (or roll back) Deployment objects when their referenced image stream tag changes, how to configure/enable/disable these triggers, and how to manage image stream tags including aliases for controlled, testable image promotion.

## Key Concepts
- **Image stream tag immutability + trigger gap** — an image stream tag always points to an immutable image (via SHA ID); updating the tag to a new image does NOT automatically roll out a Deployment using it, unless an image trigger is configured.
- **Image trigger** — configuration on a Deployment (or other workload) causing automatic rollout when its watched image stream tag changes; also enables automatic rollback if the tag is reverted.
- **Trigger-supporting workloads** — Deployment, Pod, CronJob, and Job objects all support image triggers.
- **Prerequisites for image triggers** — (1) image stream object exists in the same project as the Deployment, (2) local lookup policy enabled via `oc set image-lookup`, (3) Deployment references the image stream tag by short name (e.g. `keycloak:26`), not the fully qualified source registry name.
- **Container-level triggers** — image triggers apply per container; a Deployment with multiple containers can have a separate trigger for each.
- **image.openshift.io/triggers annotation** — JSON-formatted annotation OpenShift adds to a Deployment to store trigger config, including the `fieldPath` (JSONPath expression) locating the container image field to update.
- **Configuration trigger vs image trigger** — the `config` trigger type rolls out the deployment on config changes (env vars, readiness probe, etc.); the `image` trigger type watches an image stream tag for changes. Both show under `TYPE` in `oc set triggers` output with an `AUTO` column indicating enablement.
- **Pausing/resuming to control config trigger** — `oc rollout pause` disables the configuration trigger; `oc rollout resume` re-enables it.
- **Manual vs auto image trigger** — `--manual` disables an image trigger; `--auto` re-enables it; `--remove-all` removes triggers from all containers.
- **Automatic rollout on tag change** — a Deployment with an image trigger rolls out automatically whenever its watched image stream tag changes — whether changed manually or via scheduled refresh (`--scheduled` on `oc tag`).
- **Automatic rollback** — reverting the image stream tag to a previous image causes triggered Deployments to roll out again using that previous image (effectively rolling back).
- **oc create istag** — creates an image stream (if needed) and an image stream tag; can only be used for **initial creation**, not for updating an existing tag.
- **oc import-image / oc tag** — both can be rerun to update an existing image stream tag to point to a new source image version.
- **Image stream tag alias** — created via `oc tag --alias SOURCE-TAG NEW-TAG`; makes one tag point to the same image as another, similar in concept to a floating tag; commonly used to promote a tested image version by re-pointing a stable alias (e.g. `keycloak:26`) to a new specific version tag (e.g. `keycloak:26.7`) after testing — this pattern enables controlled promotion and rollback via triggers.

## Commands
| Command | What it does | Key flags/options |
|---|---|---|
| `oc get deployment mykeycloak -o wide` | Retrieves container names in a Deployment | `-o wide` |
| `oc set triggers deployment/mykeycloak --from-image keycloak:26 --containers keycloak` | Configures an image trigger for a container | `--from-image`, `--containers` |
| `oc get deployment mykeycloak -o jsonpath='{.metadata.annotations.image\.openshift\.io/triggers}' \| jq .` | Views the raw trigger annotation JSON | `-o jsonpath` |
| `oc set triggers deployment/mykeycloak` | Shows a summary table of configured triggers (TYPE, VALUE, AUTO) | — |
| `oc rollout pause` / `oc rollout resume` | Disables/re-enables the configuration trigger | — |
| `oc set triggers deployment/mykeycloak --manual --from-image keycloak:26 --containers keycloak` | Disables an image trigger | `--manual` |
| `oc set triggers deployment/mykeycloak --auto --from-image keycloak:26 --containers keycloak` | Re-enables an image trigger | `--auto` |
| `oc set triggers deployment/mykeycloak --remove-all` | Removes triggers from all containers in a Deployment | `--remove-all` |
| `oc create istag keycloak:26.6 --from-image quay.io/keycloak/keycloak:26.6` | Creates an image stream (if needed) + image stream tag (initial creation only) | `--from-image` |
| `oc import-image keycloak:26.6 --from quay.io/keycloak/keycloak:26.6 --confirm` | Creates/updates an image stream tag from a source image | `--from`, `--confirm` |
| `oc tag quay.io/keycloak/keycloak:26.6 keycloak:26.6` | Creates/updates an image stream tag | — |
| `oc tag --alias keycloak:26.6 keycloak:26` | Creates an alias tag pointing to the same image as another tag | `--alias` |
| `oc describe is keycloak` | Shows image stream tag details, including which tags point to the same image | — |

## Comparisons
| Aspect | oc create istag | oc import-image / oc tag |
|---|---|---|
| Initial creation | Yes | Yes |
| Updating an existing tag | **Not supported** | Supported — can be rerun to update the tag to a new source image |

| Trigger Type | Purpose | Enabled/disabled via |
|---|---|---|
| config | Rolls out deployment on config changes (env vars, probes, etc.) | `oc rollout pause` / `oc rollout resume` |
| image | Rolls out deployment when watched image stream tag changes | `--manual` / `--auto` on `oc set triggers` |

## Exam Tips / Gotchas
- Updating an image stream tag does **NOT** automatically roll out a Deployment unless an **image trigger** is configured.
- `oc create istag` can **only** be used for initial creation — **cannot** update an existing tag (use `oc tag` or `oc import-image` instead for updates).
- The `AUTO` column value `true` in `oc set triggers` output indicates the trigger is **enabled**.
- Reverting an image stream tag to a previous image causes Deployment objects with a configured trigger to **automatically roll back**.
- Image triggers apply at the **container level** — multi-container Deployments can have separate triggers per container.
- An alias tag (`oc tag --alias`) works like a floating tag conceptually — re-pointing it to a new specific-version tag (after testing) triggers rollout of all Deployments watching the alias; resetting it back rolls back those deployments.
- The `fieldPath` JSONPath in the `image.openshift.io/triggers` annotation identifies exactly which container's image field OpenShift updates on tag change.

## Glossary
- **Image trigger**: Deployment (or other workload) configuration causing automatic rollout when a watched image stream tag changes.
- **image.openshift.io/triggers**: annotation storing image trigger configuration in JSON format.
- **fieldPath**: JSONPath expression within the trigger annotation identifying the container image attribute to update.
- **Alias tag**: an image stream tag created via `oc tag --alias` that points to the same image as another tag, enabling controlled re-pointing for promotion/rollback.
