## Quick Summary
Covers how OpenShift updates applications with minimal downtime using deployment strategies (RollingUpdate vs Recreate), how to pause/resume rollouts to batch changes, how ReplicaSet objects are created/managed per deployment revision, and how to monitor, roll back, and inspect rollout history.

## Key Concepts
- **Externalized config/data** — modern apps load configuration and data from external sources (ConfigMaps, Secrets, volumes) rather than hardcoding them, enabling deployment across environments without code changes.
- **CI/CD pipeline** — typically builds a new image from source code and pushes it to a container registry when application code changes.
- **Deployment strategy** — controls how an app is changed/upgraded to minimize impact; set via `.spec.strategy.type` on the Deployment object; main types: RollingUpdate and Recreate.
- **RollingUpdate strategy** — replaces instances one at a time; both old and new versions run simultaneously; scales down old version only once new version is ready; requires version compatibility between old/new; **default strategy** if none is specified; supports continuous deployment with no downtime.
- **maxSurge** — RollingUpdate parameter specifying how many pods can be created above the normal replica count (percentage or number).
- **maxUnavailable** — RollingUpdate parameter specifying how many pods can be removed below the normal replica count (percentage or number).
- **Readiness probe importance during rolling update** — without one, OpenShift sends traffic to new pods as soon as they're running, even if the app inside isn't ready yet, causing failed requests.
- **Recreate strategy** — stops all instances of an app first, then starts new ones; causes downtime (no instances available during the gap); not recommended for high-availability applications; useful when different code versions can't run simultaneously, or for data migrations before new code starts.
- **Rollout pause/resume** — pausing a deployment lets you apply multiple changes (image, env vars, probes) without triggering a rollout for each one individually; resuming then triggers a single rollout with all changes applied.
- **Scale-to-zero deployment creation** — creating a deployment with `--replicas 0` lets you configure it (e.g. add a readiness probe) before any pods run, then scale up to trigger a single rollout.
- **ReplicaSet** — created by OpenShift when a Deployment rolls out; responsible for creating/monitoring pods (recreates failed pods); uses the pod template copied from the Deployment.
- **ReplicaSet immutability on update** — updating a Deployment does NOT update the existing ReplicaSet; instead OpenShift creates a **new** ReplicaSet with the new pod template, and both old/new ReplicaSets coexist/coordinate during a rolling update.
- **revisionHistoryLimit** — Deployment attribute specifying how many old ReplicaSet objects OpenShift retains; extras are automatically deleted; deleting a Deployment deletes all its associated ReplicaSets.
- **ReplicaSet naming** — uses the Deployment name as a prefix (e.g. `myapp2-574968dd59`); the suffix (`pod-template-hash`) links a revision to its ReplicaSet.
- **Rollback** — `oc rollout undo` reverts to the preceding deployment version using the retained ReplicaSet; OpenShift does NOT automatically roll back on rollout failure (e.g. bad image name, failing readiness probe) — manual `oc rollout undo` is required.
- **kubernetes.io/change-cause annotation** — user-defined message stored per rollout, shown in the CHANGE-CAUSE column of `oc rollout history`.
- **Floating tags and rollback risk** — if floating tags are used, the image a rollback retrieves might have changed in the registry since the original deployment, so the rolled-back deployment might not run the exact original image; OpenShift image streams are recommended instead to avoid this issue.

## Config / YAML Snippets
Deployment with Recreate strategy:
```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  progressDeadlineSeconds: 600
  replicas: 10
  revisionHistoryLimit: 10          # How many old ReplicaSets are retained
  selector:
    matchLabels:
      app: myapp2
  strategy:
    type: Recreate                    # Stops all old pods before starting new ones
  template:
```

Deployment with RollingUpdate strategy and surge/unavailable settings:
```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  progressDeadlineSeconds: 600
  replicas: 10
  revisionHistoryLimit: 10
  selector:
    matchLabels:
      app: myapp2
  strategy:
    rollingUpdate:
      maxSurge: 25%                    # Max pods allowed above normal replica count
      maxUnavailable: 50%               # Max pods allowed below normal replica count
    type: RollingUpdate                  # Default strategy if unspecified
  template:
```

## Comparisons
| Aspect | RollingUpdate | Recreate |
|---|---|---|
| Downtime | None (if versions are compatible) | Yes — all instances stopped before new ones start |
| Version coexistence | Both old and new versions run simultaneously during rollout | No — old fully stopped before new starts |
| Requirement | Requires compatibility between old/new versions | No compatibility requirement between versions |
| Default | Yes, if no strategy specified | No |
| Best for | Most standard applications, continuous deployment | High-consistency needs, data migrations, apps that can't run mixed versions; NOT recommended for high-availability apps |

## Exam Tips / Gotchas
- **RollingUpdate is the default strategy** if `.spec.strategy.type` is not specified.
- Without a **readiness probe**, OpenShift sends traffic to new pods as soon as they start running — even if the app inside isn't actually ready — causing failed requests during rolling updates.
- Updating a Deployment does **not** modify the existing ReplicaSet — OpenShift always creates a **new** ReplicaSet with the updated pod template.
- Do **not** directly change or delete ReplicaSet objects — they are managed via their associated Deployment.
- `revisionHistoryLimit` controls how many old ReplicaSets OpenShift retains; excess ones are auto-deleted; deleting the Deployment deletes all associated ReplicaSets.
- On a **failed rollout** (bad image name, failing readiness probe), OpenShift does **NOT** automatically roll back — you must run `oc rollout undo` manually.
- `oc rollout undo` by default rolls back to the **immediately preceding** version — use `--to-revision` to target a specific earlier revision.
- Pausing a rollout (`oc rollout pause`) before applying multiple changes prevents OpenShift from triggering a separate rollout for each individual change.
- Using **floating tags** risks rolling back to a *different* image than originally deployed, since the tag may have been reassigned in the registry — use **OpenShift image streams** to avoid this.
- The `pod-template-hash` attribute (in rollout history) is the suffix used to identify the associated ReplicaSet object.

## Glossary
- **ReplicaSet**: object responsible for creating/monitoring a deployment's pods per revision; created new (not reused) on each Deployment update.
- **revisionHistoryLimit**: Deployment field controlling how many old ReplicaSets are retained.
- **maxSurge**: RollingUpdate parameter for extra pods allowed above the replica count during update.
- **maxUnavailable**: RollingUpdate parameter for pods allowed to be removed below the replica count during update.
- **pod-template-hash**: label suffix linking a pod/ReplicaSet to a specific revision's pod template.
- **change-cause**: annotation (`kubernetes.io/change-cause`) storing a user-defined description of a rollout revision.
