## Quick Summary
Covers OpenShift image streams — an abstraction layer decoupling app definitions from specific image locations/versions — including image stream tags, how they track image ID history (enabling rollback and isolation from registry changes), creating/importing/tagging image streams, periodic refresh, pull-through caching, and using image streams in Deployments/Jobs/CronJobs/Pods.

## Key Concepts
- **Image stream** — OpenShift abstraction layer decoupling app definitions from specific image location/version; enables robust CI/CD, simplifies image promotion across environments, enhances security by controlling available images; one of the main differentiators between OpenShift and upstream Kubernetes.
- **Floating vs non-floating tag reproducibility problem** — a pod referencing an image tag isn't guaranteed to retrieve the same image on restart, since tags can be reassigned; image streams resolve this and provide rollback capability.
- **OpenShift resources referencing image streams** — build configurations reference image streams directly; Kubernetes-native resources (e.g. Deployments) are extended via annotations to use image streams.
- **Image stream tag (ISTag)** — represents one stream of container images; an image stream can have multiple image stream tags referencing images from different registries/repositories; provides default config for a stream, can override most of the parent image stream's config; stores metadata (including SHA image ID) about the current image, enabling faster search/inspection without contacting the source registry.
- **Image stream local caching** — an image stream tag can be configured to store source image layers in OpenShift's internal container registry (local cache), avoiding repeated fetches from the source registry; consumers reference the internal registry as the source.
- **SHA image ID** — SHA-256 hash uniquely identifying an immutable container image; images can't be modified, only replaced with a new ID under the same textual name.
- **Image stream tag history** — keeps a history of the latest image IDs fetched from a registry; enables rollback to a previous image if a new one causes deployment errors.
- **Isolation from registry changes** — updating an image in an external registry does NOT automatically update an image stream tag; the tag keeps referencing the last fetched image ID — this isolates OpenShift/scaling operations from unexpected upstream changes (new pods use the same image ID as existing ones).
- **Manual vs scheduled tag updates** — by default, OpenShift does not monitor external registries for image ID changes; must explicitly update the tag, or configure periodic checking (`--scheduled`).
- **Image promotion pattern** — CI/CD builds an image tagged e.g. `myapp:latest-dev`; after tests pass, the same immutable digest is tagged into `myapp:qa-stable`; after QA, tagged as `myapp:prod-v1.2` to trigger production deployment — ensures the same artifact is tested and promoted (traceability/consistency).
- **Registry-agnostic flexibility** — image streams let you swap to an alternative vendor's compatible image (e.g. switching to a Red Hat-hardened image) without changing app-level references.
- **lookupPolicy.local** — controls whether an image stream can satisfy short image names in pod specs within the same project.
- **Image pull-through** — caches images from the source registry in OpenShift's internal registry on first pull, mitigating slow/failed pulls from internet-based registries with bandwidth throttling; activated via `--reference-policy local`.
- **Local lookup policy** — must be enabled on an image stream for it to be used by a Deployment via a short name; OpenShift only considers image streams with this policy enabled when resolving short names; if no matching image stream is found, OpenShift looks for a regular container image in allowed registries.

## Config / YAML Snippets
ImageStream definition excerpt:
```yaml
apiVersion: image.openshift.io/v1
kind: ImageStream
metadata:
  name: keycloak                      # Name of the ImageStream object
  namespace: openshift                 # Project where the image stream resides
spec:
  lookupPolicy:
    local: false                        # Controls if this stream can satisfy short image names in the same project
  tags:                                  # Intended state: each tag and its source image
  - annotations: null
    from:
      kind: DockerImage
      name: quay.io/keycloak/keycloak:19.0
    generation: 6
    importPolicy:
      importMode: Legacy
    name: "19.0"
    referencePolicy:
      type: Source
status:
  dockerImageRepository: image-registry.openshift-image-registry.svc:5000/openshift/keycloak   # Path to this stream in the internal registry
  tags:                                    # Current state: history of image digests per tag
  - items:
    - created: "2026-07-20T07:41:44Z"
      dockerImageReference: quay.io/keycloak/keycloak@sha256:40cc...ffde   # Immutable digest imported for the tag
      generation: 6
      image: sha256:40cc...ffde
    tag: "19.0"
```

## Comparisons
| Aspect | Container image tag (registry-level) | Image stream tag (OpenShift) |
|---|---|---|
| Mutability | Can be reassigned to a new image by the vendor at any time | Fixed after creation — does not change unless explicitly updated (or scheduled refresh enabled) |
| History | No built-in history tracking | Keeps a history of fetched image IDs, enabling rollback |
| Isolation | Pod restart may pull a different image if tag was reassigned | Isolates deployments from upstream registry changes — new pods use the same image ID as existing ones |
| Rollback | Not directly supported by tag alone | Supported via image ID history |

## Exam Tips / Gotchas
- Updating an image in an **external** registry does **not automatically update** an image stream tag — manual update or `--scheduled` refresh is required.
- By default, OpenShift **does not monitor** external registries for image changes; scheduled refresh checks every **15 minutes by default** (configurable by cluster admins).
- To use an image stream in a Deployment: (1) create the image stream in the **same project**, (2) **enable local lookup policy**, (3) reference the tag by **short name** (e.g. `keycloak:25.0`), not the full external registry name.
- OpenShift only considers image streams **with local lookup policy enabled** when resolving short image names; if no match, it falls back to searching allowed container registries.
- Image pull-through (`--reference-policy local`) caches images in the internal registry after first pull, mitigating slow/unreliable pulls from public/internet registries.
- The asterisk (`*`) in `oc describe is` output marks the **current** image ID for a tag — usually the latest import and first entry listed.
- Image promotion pattern (dev → qa → prod tagging) relies on tagging the **same immutable image digest** across environments to ensure the tested artifact is what gets deployed.
- Red Hat provides hardened, supported drop-in replacement images (e.g. MariaDB) — using image streams makes switching to such alternatives easier without changing app-level image references.

## Glossary
- **Image stream**: OpenShift abstraction layer providing a stable reference to one or more container image tags, decoupled from a specific registry/version.
- **Image stream tag (ISTag)**: a named reference within an image stream tracking a history of image IDs for a specific stream of images.
- **SHA image ID**: SHA-256 digest uniquely and immutably identifying a container image.
- **Local lookup policy**: image stream setting controlling whether it can satisfy short image names for pod specs in its project.
- **Image pull-through**: caching mechanism storing pulled images in OpenShift's internal registry to speed up/reduce reliance on external registries.
- **dockerImageReference**: field in an image stream tag's status recording the immutable digest of the imported image.
