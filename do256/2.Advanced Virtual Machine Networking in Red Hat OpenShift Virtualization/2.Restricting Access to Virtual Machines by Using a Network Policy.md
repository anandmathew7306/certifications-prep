# 2.3 Restricting Access to Virtual Machines by Using a Network Policy

- By default any pod or VM can reach any other, even across namespaces. Network policies add segmentation using labels.
- Two kinds:
  - `NetworkPolicy` (NP) - namespaced, for developers and project admins.
  - `AdminNetworkPolicy` (ANP) - cluster-wide, set by cluster admins, cannot be overridden by NPs.
- OVN-Kubernetes uses ACL tiers: tier 1 checks ANPs first. A match with Allow/Deny ends it; no match or a `Pass` drops to tier 2 (NPs).
- NPs are additive: allowed traffic is the union of all matching policies.
- Common first step: a default-deny policy with `podSelector: {}` and `policyTypes: [Ingress, Egress]` but no rules.
- Then add narrow allow policies:
  - Target a VM with label `vm.kubevirt.io/name: <vm>`.
  - `from`/`to` with `namespaceSelector` and/or `podSelector` (both in one item = AND).
  - Restrict `ports`, e.g. TCP 5432.
  - Remember an egress rule to `openshift-dns` so DNS still works.
  - Monitoring namespaces can be matched by `network.openshift.io/policy-group: monitoring`.
- Label a namespace: `oc label namespace <ns> name=<value>`.
- Web console: Networking > NetworkPolicies, Form or YAML view; form has deny-all checkboxes.
- UDN limits: policies work only on the primary UDN interface; policies between namespaces on different primary UDNs do nothing, as there is no path.
- ANP extra fields:
  - `subject` - which namespaces/pods it applies to.
  - `priority` 0-99, lower number wins.
  - `action`: `Allow`, `Deny`, or `Pass` (hand off to lower-priority ANPs or NPs).
