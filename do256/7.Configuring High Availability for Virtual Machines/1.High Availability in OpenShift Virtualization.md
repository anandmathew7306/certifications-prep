# 7.1 High Availability in OpenShift Virtualization

- HA = keep services running and recover from failures quickly.
- Classic hypervisors mostly restart or move VMs to another host; app monitoring and load balancing need extra setup.
- Fencing: isolate a node in an unknown state so a VM never runs on two hosts at once (disk corruption). Recover the VM only after that.
- KubeVirt runs KVM VMs inside pods and adds live migration and resource balancing.
- HA building blocks:
  - Run strategy (`spec.runStrategy` or `spec.running`): decides if a deleted VMI or `virt-launcher` pod comes back.
  - Readiness probe: on failure the VM leaves the service endpoints.
  - Liveness probe: on failure the VMI is recreated.
  - Watchdog: watches the guest OS only, not the app.
  - Live migration: moves VMs off a node being drained.
  - Machine health checks (Machine API) and node health checks: detect bad hosts and trigger remediation.
  - Fencing operators: SNR (watchdog reboot), FAR (out-of-band power control), MDR (delete and reprovision machine).
- Load balancer services need platform support; bare metal uses the MetalLB operator.
- Sticky sessions keep one client on the same endpoint. Routes use a cookie.
  - Default cookie name is random; set one with the route annotation `router.openshift.io/cookie_name`.
  - A known name lets the app delete the cookie to move the client elsewhere.
  - If the endpoint dies, a new cookie is issued and the session may be lost.
