# 1.1 The OpenShift OAuth Server and Identity Providers

- Authentication answers "who are you"; authorization (RBAC) answers "what can you do".
- Plain Kubernetes checks a token or a client certificate signed by a trusted CA.
  - Cert CN becomes the username, O becomes the group.
  - Bad credentials get `401 Unauthorized`.
  - No credentials means user `system:anonymous`, group `system:unauthenticated`; RBAC then decides.
- OpenShift adds a built-in OAuth server, run by the Authentication Operator. Two ways in:
  - X.509 client certificates (same as Kubernetes).
  - OAuth access tokens issued by the internal OAuth server.
- `oc login` flow:
  - User gives username and password.
  - OAuth server checks them against an identity provider (IdP).
  - OAuth server issues a token, saved in the kubeconfig (default `~/.kube/config`).
  - Web console works the same but keeps the token in browser memory.
- At least one IdP must be set; several can be listed in the `OAuth` custom resource.
- Supported IdPs: Basic auth, HTPasswd (`htpasswd` file), GitHub (can limit to orgs), GitLab, Google, Keystone, LDAP, OpenID Connect, Request header (auth proxy).
- Key resource types:
  - `User`: a person using the API; gets roles directly or via groups.
  - `Identity`: links a successful IdP login to a `User`.
  - `ServiceAccount`: API access for apps and cluster components.
  - `Group`: set of users, so permissions can be granted once for many.
  - Role: allowed API operations on resource types; bound to users, groups or service accounts.
