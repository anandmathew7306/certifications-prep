# 1.3 Defining and Applying Permissions with RBAC

- Building blocks: rule (allowed verbs on resources), role (set of rules), binding (ties users or groups to a role).
- Scope:
  - Cluster roles and cluster role bindings apply to every project.
  - Local roles and role bindings apply to one project.
  - Local bindings can use cluster or local roles; cluster bindings only cluster roles.
- Default cluster roles:
  - `cluster-admin`: anything, anywhere.
  - `admin`: project resources plus roles and bindings; not quotas or the project.
  - `edit`: change most objects, not roles or bindings.
  - `view`: read-only, minus roles and bindings.
  - `self-provisioner`: create projects, becomes `admin` of them.
  - `kubevirt.io:admin` / `:edit` / `:view`: virtualization resources only (VMs, VMIs, instance types); only admin changes runtime config.
- Gotcha: `kubevirt.io:*` roles skip pods and services; `admin`, `edit`, `view` already include kubevirt resources.
- User types: `User`, system users (`system:` prefix), service accounts (`system:serviceaccount:<ns>:<name>`, no roles by default).
- Only cluster admins create cluster role bindings.
- CLI:
  - `oc adm policy add-cluster-role-to-user` / `remove-cluster-role-from-user`
  - `oc adm policy who-can <verb> <resource>`
  - `oc policy add-role-to-user view dev -n <project>` (cluster role, scoped to one project)
  - `oc adm groups new <group>`, `oc adm groups add-users <group> <user>`
  - `oc policy add-role-to-group` / `remove-role-from-group`
- Cross-namespace VM clone fails by default; give the destination's `default` service account rights in the source:
  - `oc create clusterrole datavolume-cloner --verb=create --resource=datavolumes/source`
  - `oc policy add-role-to-user -n <source> datavolume-cloner system:serviceaccount:<dest>:default`
