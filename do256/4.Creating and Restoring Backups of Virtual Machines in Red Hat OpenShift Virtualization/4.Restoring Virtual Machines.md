# 4.7 Restoring Virtual Machines

- A `Restore` CR in `openshift-adp` with `spec.backupName` starts a restore.
- Flow: Velero recreates resources; Data Mover fills a temp PVC in `openshift-adp`, then rebinds that PV to the app PVC (which waits in `Pending`).
- Existing resources in the target are not overwritten. Use `namespaceMapping` (CLI `--namespace-mappings old:new`) to restore elsewhere.
- Some kinds (events, nodes, Velero CRs) are excluded by default; change with `excludedResources`.
- Phases: `New`, `InProgress`, `WaitingForPluginOperations`, `Completed`.
- Restored objects get `velero.io/restore-name` and `velero.io/backup-name` labels.
- CLI: `velero create restore <name> --from-backup <backup>`, `velero get restore`, `velero restore describe`, `velero restore logs`.
- VM-specific labels on the Restore:
  - `velero.kubevirt.io/clear-mac-address: "true"`: new MAC, avoids a conflict when the original VM is still running.
  - `velero.kubevirt.io/generate-new-firmware-uuid: "true"`: new firmware UUID (licensing, identity).
  - `velero.kubevirt.io/run-strategy: "Halted"`: control power state; values match `spec.runStrategy`. Default is the state at backup time.
- `labelSelector` (or `-l`) restores one VM from a multi-VM backup. Label the VM and its PVCs alike or the disks are left out.
- Restore from another cluster: add a second backup location in the DPA with its own secret, `default: false`, same bucket and prefix. Filter with `-l velero.io/storage-location=<name>`.
- Storage class mapping: a ConfigMap in `openshift-adp` labelled `velero.io/plugin-config: ""` and `velero.io/change-storage-class: RestoreItemAction`, data `old-sc: new-sc`. Volume mode must match.
- Temp resources stay after restore; clean up with `velero delete restore <name>`.
