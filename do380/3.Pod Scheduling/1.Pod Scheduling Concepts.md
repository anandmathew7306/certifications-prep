## 1. Default Scheduler Mechanics

Scheduling = deciding which node hosts a pod. Scheduler creates a **binding**, does not modify the pod.

**3-step algorithm:**
1. **Filtering** — eliminates nodes via *predicates* (CPU/mem fit, free ports, volume availability, taints).
2. **Prioritizing** — scores surviving nodes 0–10 via weighted scoring functions.
3. **Selection** — highest score wins; ties broken randomly.

**⚠️ Gotcha:** No `resources.requests` on a pod → scheduler can't score it properly → may land on an
already-full node → risk of OOM kill / poor performance.

## 2. Scheduler Profiles

Cluster-wide scheduling behavior, set on a singleton object.

```bash
oc edit scheduler cluster
# modifies spec.profile
```

| Profile | Behavior | Trade-off |
|---|---|---|
| `LowNodeUtilization` | Spreads pods evenly | **Default.** Favors resilience |
| `HighNodeUtilization` | Packs pods onto fewest nodes | Saves node count, ↑ per-node load |
| `NoScoring` | Disables scoring plug-ins | Fastest decisions, worst placement quality |

**⚠️ Gotcha:** `NoScoring` disables *scoring*, not *filtering* — hard constraints (resource fit, taints)
still apply.

## 4. Affinity / Anti-affinity — Core Definitions

| Term | Meaning |
|---|---|
| **Affinity** | Pod's *preference* for a node (pull toward) |
| **Anti-affinity** | Pod's *restriction* against a node (push away) |
| **Node affinity** | Relative to **node** labels |
| **Pod affinity/anti-affinity** | Relative to **other pods'** labels |

**⚠️ Gotcha:** Anti-affinity (pod-side, relative) ≠ Taint (node-side, absolute exclusion). Scenarios
often need both together (e.g., dedicated infra nodes = taint + node selector/affinity; HA spread =
pod anti-affinity).

---

## 5. Node Affinity

More flexible node selector — supports logical operators.

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disktype
            operator: In
            values: ["fast"]
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: zone
            operator: In
            values: ["us-east-1a"]
```

- **Required** → hard constraint; unmet = pod stays `Pending`.
- **Preferred** → soft constraint; scheduler tries, still places pod elsewhere if unmet. Supports
  `weight` (1–100) across multiple preferred terms.
- Operators: `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`

**⚠️ Gotcha:** `...IgnoredDuringExecution` = rule only checked at **scheduling time**. If node labels
change later, running pods are NOT evicted or re-evaluated.

**⚠️ Note:** Field is `spec.affinity` on the pod spec (not `spec.config.affinity` as some course text
implies).

## Quick Decision Table (Scenario → Feature)

| Requirement | Feature |
|---|---|
| Hard requirement, simple label match | Node selector |
| Hard/soft requirement, conditional logic (In/NotIn) | Node affinity |
| Co-locate pods that talk to each other | Pod affinity |
| Spread replicas across nodes/zones for HA | Pod anti-affinity |
| Keep general workloads OFF dedicated/reserved nodes | Taints + tolerations |
| Dedicate nodes to ONLY one workload | Taint (exclude others) + node selector/affinity (attract target) |
| Guarantee N pods stay up during maintenance/updates | Pod Disruption Budget |
| Protect against node crash/failure | **None of the above** — PDBs and affinity don't cover involuntary disruption |

---

## Resolved Doubts

- **PDB in plain terms:** A rule for *planned* disruptions only (like telling a restaurant manager
  "you can send at most 2 chefs home for training at once"). Doesn't cover someone getting sick
  unexpectedly (= node failure, out of scope for PDBs).
