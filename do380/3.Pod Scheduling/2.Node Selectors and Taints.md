## Core Mental Model

- **Node selectors = pull.** Pod declares "place me on a node with label X." No selector → schedulable anywhere.
- **Taints/tolerations = push (repel).** Node declares "don't schedule here unless tolerated." A toleration only unlocks eligibility — it does **not** attract a pod to that node. To pin a pod to a specific tainted node you need **both** a selector/affinity (destination) **and** a toleration (permission).
- If no node satisfies a selector, the pod does not error — it sits **Pending** indefinitely. `oc describe pod` events distinguish "no matching selector/affinity" vs "untolerated taint" — check both independently.

## Node Labels

```bash
# Add label(s)
oc label node <node-name> key1=value1 key2=value2

# Remove label(s)
oc label node <node-name> key1- key2-

# View labels as columns
oc get no -L key1,key2
```

**Gotcha:** On clusters using MachineSets, labels must be set via the MachineSet, not directly on the node. Direct labels on machine-set-managed nodes are lost when OpenShift deletes/recreates that node (scaling, replacement, etc.).

## Pod Node Selectors

Defined in the pod template (`spec.template.spec` for a Deployment):

```yaml
spec:
  template:
    spec:
      nodeSelector:
        key1: value1
        key2: value2
```

- Pure equality matching, implicit AND across keys. No OR logic (unlike NodeAffinity).

**Verify:**
```bash
oc describe pod <pod-name>
# Node-Selectors:  key1:value1
#                  key2:value2
```

---

## Cluster-wide Node Selectors

Set on the Scheduler CR (cluster-admin only):

```bash
oc edit scheduler cluster
```

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: key1=value1,key2=value2
```

- Applies as default to *any new pod* cluster-wide unless overridden by a project selector.
- After editing, `openshift-kube-apiserver` pods redeploy.
- **Risk:** a bad/nonexistent label here can make all future pods cluster-wide unschedulable.

## Project Node Selectors

Namespace-level default (cluster-admin only):

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: <project-name>
  annotations:
    openshift.io/node-selector: key3=value3,key4=value4
```

- Syntax: comma-separated string annotation, **not** a YAML map (different from pod-level).
- Injected into every pod created in that namespace **at creation time only** — does not retroactively affect already-running pods. Requires a new rollout to pick up a changed project selector.

**Verify (project level):**
```bash
oc describe project <name>
# Node Selector:  cpu=standard
```

**Verify (pod level — selector gets baked into the actual pod spec):**
```bash
oc describe pod <pod-name>
# Node-Selectors:  cpu=standard
```

## Precedence Rules (memorize this table)

| Combination | Result |
|---|---|
| Project + cluster-wide both set | **Project wins outright** — cluster-wide is dropped, not merged |
| Pod + project both set | **Additive** — pod gets both merged |
| Pod + cluster-wide both set | **Additive** — pod gets both merged |

**Hard rule:** Same key, different value, across pod vs. project (or cluster-wide) → **conflict**. OpenShift does not pick a winner — it **fails to create the pod**.

## Node Taints

Taint = `key=value:effect` on a **node**.

- key: up to 253 chars
- value: up to 63 chars
- effect: one of three options

| Effect | New pods without toleration | Existing pods on node |
|---|---|---|
| `NoSchedule` | Blocked | Untouched, keep running |
| `PreferNoSchedule` | Scheduler tries to avoid, may still place | Untouched |
| `NoExecute` | Blocked | **Evicted** unless tolerated |

```bash
# Apply
oc adm taint nodes <node-name> key1=value1:NoSchedule

# Remove (trailing hyphen)
oc adm taint nodes <node-name> key1=value1:NoSchedule-

# Verify
oc describe nodes <node-name> | grep Taints
```

**Gotcha:** `NoSchedule` never evicts existing pods — only blocks new scheduling. `NoExecute` is the only effect that evicts already-running pods. This is the #1 confusion point on this topic.

## Pod Tolerations

```yaml
spec:
  tolerations:
  - key: "type"
    value: "mission-critical"
    operator: "Equal"
    effect: "NoSchedule"
```

| Operator | Matches when | value field |
|---|---|---|
| `Equal` (default) | key, value, effect all match | required |
| `Exists` | key + effect match, value ignored | must be blank |

**tolerationSeconds** (only relevant with `NoExecute`): time a pod may remain on a node after that node receives a `NoExecute` taint, before eviction.

```yaml
tolerations:
- key: "key1"
  operator: "Equal"
  value: "value1"
  effect: "NoExecute"
  tolerationSeconds: 3600
```

**Verify:**
```bash
oc describe pod <pod-name>
# Tolerations:  key1=value1:NoSchedule
```

**Gotcha:** A matching toleration only makes a tainted node *eligible* — it doesn't force placement there. If other untainted nodes also satisfy the pod's selector/affinity, the scheduler can still choose those instead. Toleration = eligibility; selector/affinity = destination.

## Built-in Node-Condition Taints (auto-applied by OpenShift)

| Taint | Condition | Effect |
|---|---|---|
| `node.kubernetes.io/not-ready` | `Ready=False` | **NoExecute** |
| `node.kubernetes.io/unreachable` | `Ready=Unknown` | **NoExecute** |
| `node.kubernetes.io/memory-pressure` | `MemoryPressure=True` | NoSchedule |
| `node.kubernetes.io/disk-pressure` | `DiskPressure=True` | NoSchedule |
| `node.kubernetes.io/pid-pressure` | `PIDPressure=True` | NoSchedule |
| `node.kubernetes.io/network-unavailable` | — | NoSchedule |
| `node.kubernetes.io/unschedulable` | via `oc adm cordon` | NoSchedule |
| `node.cloudprovider.kubernetes.io/uninitialized` | cloud controller not yet init | removed after init |

- Only `not-ready` and `unreachable` use `NoExecute` — everything else is `NoSchedule`.
- OpenShift auto-injects a default 300s toleration for `not-ready`/`unreachable` on every pod, so a brief node blip doesn't cause instant eviction.
- `oc adm cordon <node>` = applying `node.kubernetes.io/unschedulable:NoSchedule` under the hood. `oc adm drain` = cordon + evict pods.

## Project Tolerations (cluster-admin only)

```yaml
metadata:
  annotations:
    scheduler.alpha.kubernetes.io/defaultTolerations: >-
      [{"operator":"Equal","effect":"NoSchedule","key":"key1","value":"value1"}]
```

- JSON-array-string format (different syntax from both pod YAML list and project node-selector's comma string).
- Project + pod tolerations are **additive** (not override — don't confuse with the project-vs-cluster-wide selector override rule).

---

## Wildcard Toleration (tolerate everything)

```yaml
spec:
  tolerations:
  - operator: "Exists"
```

- No key/value + `Exists` = matches every taint on every node.
- Not evicted even from `NoExecute`-tainted nodes — true blanket exemption.
- Typical use: cluster infrastructure/daemon pods that must run everywhere regardless of taints. Rarely appropriate for ordinary application workloads.

```bash
oc adm cordon <node-name>

oc describe project <project-name>
```

## Quick Verification Field Cheat Sheet

| What you're checking | Command | Field to look for |
|---|---|---|
| Pod's node selectors | `oc describe pod <name>` | `Node-Selectors:` |
| Project's node selector | `oc describe project <name>` | `Node Selector:` |
| Node's taints | `oc describe node <name>` | `Taints:` |
| Pod's tolerations | `oc describe pod <name>` | `Tolerations:` |
| Why a pod is Pending | `oc describe pod <name>` or `oc get events` | `FailedScheduling` message — check both "didn't match node affinity/selector" and "untolerated taint" |

## Exam Traps Summary

1. `NoSchedule` never evicts existing pods; `NoExecute` does. Don't mix these up.
2. Toleration ≠ attraction. It only removes repulsion — you still need a selector/affinity for actual placement.
3. Conflicting node-selector values (same key, different value) between pod and project/cluster-wide → **pod creation fails**, not "highest level wins."
4. Project node selector wins over cluster-wide outright (override); pod-level selectors are additive with either.
5. Project-level changes (selector or toleration) only apply to pods created **after** the change — existing pods are unaffected until redeployed.
6. Direct node labels are fragile on MachineSet-managed clusters — lost on node recreation.
7. A bare `operator: "Exists"` toleration with no key/value tolerates *everything*, including `NoExecute`.
