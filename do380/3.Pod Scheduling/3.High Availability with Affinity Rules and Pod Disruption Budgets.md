## Core Concept

Two separate mechanisms work together for HA during planned maintenance:

- **Pod anti-affinity** → controls **where** pods land (spread across failure domains)
- **Pod Disruption Budget (PDB)** → controls **how fast** pods can be evicted during a voluntary disruption

They solve different halves of the same problem. Anti-affinity alone doesn't protect you during a drain; a PDB alone doesn't fix bad initial placement.

---

## Pod Affinity vs. Anti-Affinity

| Type | Meaning |
|---|---|
| **Affinity** | Schedule pod *near* pods matching a label (same node/domain) — reduces latency |
| **Anti-affinity** | Schedule pod *away from* pods matching a label — improves resilience |

- **Required** (`requiredDuringScheduling...`) — hard rule; pod stays unscheduled if unmet.
- **Preferred** (`preferredDuringScheduling...`) — soft rule (with a `weight` 1–100); scheduler tries, but schedules anyway if no good node exists.
- **`...IgnoredDuringExecution`** — rule is checked **only at pod creation**. If conditions change later (labels, node status), already-running pods are *not* moved or evicted to re-satisfy it.

**Gotcha:** With few failure domains and many replicas, `required` anti-affinity can leave pods **Pending**. `preferred` keeps the app deployable even with imperfect spread — usually the safer real-world choice.

---

## Topology Keys

A topology key is just a **node label** the scheduler uses to define "how close is too close."

- Default keys: `kubernetes.io/hostname` (per-node), `topology.kubernetes.io/zone` / `.../region` (cloud-only, often absent on-prem)
- **Custom key**: any label an admin applies to represent a real failure domain (e.g. `rack`), referenced in the affinity rule via `topologyKey: rack`
- Kubernetes doesn't validate that the key is "topology-related" — it's just a string matching a node label. The name is convention, not magic.

**Analogy:** Default behavior = "don't double up in the same *room* (node)." Custom topology key = "don't double up on the same *floor* (rack)" — because the floor, not the room, is your real blast radius.

## Pod Disruption Budget (PDB)

- Resource kind: `PodDisruptionBudget`, API group `policy/v1` — a **separate resource**, not a Deployment field. Connects via label `selector`.
- Protects against **voluntary** disruptions only (`oc adm drain`, cordon). **Cannot** help with **involuntary** disruptions (node crash/hardware failure) — nothing can stop a dead node from losing its pods.
- Define with **one of**:
  - `minAvailable` — minimum pods that must stay running (count or %)
  - `maxUnavailable` — maximum pods that can be down at once (count or %)

### Why PDB matters (step-by-step mechanics)

Without a PDB, `oc adm drain` evicts **all pods on the node at once**. Replacement pods take time to become Ready (pull image, start, pass readiness probe) — during that gap, available replica count dips below your app's real minimum, even though "everything eventually reschedules fine."

With a PDB (`minAvailable: 5` out of 6 pods → `Allowed disruptions: 1`):

1. Evict pod #1 → allowed (5 remain, meets minAvailable)
2. Evict pod #2 → **blocked** (would drop to 4) → retries every 5s
3. Scheduler creates replacement for pod #1 elsewhere
4. Once replacement is Ready → back to 6 available → pod #2 eviction now allowed
5. Repeats one pod at a time until node is fully drained

**Trade-off:** PDB makes `oc adm drain` slower on purpose — availability over speed. The drain command itself blocks/retries until eviction succeeds; it's not async, don't mistake a "stuck" drain for failure — check `oc get pdb` in a second terminal to confirm progress via `Allowed disruptions`.

## Key Commands

```bash
# Verify failure-domain labels on nodes
oc get nodes -L rack

# Apply anti-affinity deployment
oc apply -f deployment-affinity.yaml

# Apply the PDB
oc apply -f pod-disruption-budget.yaml

# Inspect PDB status (Allowed disruptions is the live, recalculated number)
oc describe pdb <name>
oc get pdb,deployments,pods -o wide

# Simulate a voluntary disruption
oc adm drain node/<name> --ignore-daemonsets --delete-emptydir-data

# Undo the cordon after maintenance
oc adm uncordon node/<name>

# Cleanup
oc label node --all rack-
oc adm uncordon -l node-role.kubernetes.io/worker
```

## YAML Reference

**Pod anti-affinity (preferred, custom topology key):**
```yaml
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        topologyKey: rack
        labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values:
            - <app-label-value>
```

**Pod Disruption Budget:**
```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: <name>
spec:
  minAvailable: 80%
  selector:
    matchLabels:
      app: <app-label-value>
```

## Doubts Resolved

**Q: Does DaemonSet use pod anti-affinity?**
No — unrelated mechanisms. DaemonSet has its own built-in controller logic: "one pod per node, automatically." No labels, topology keys, or scheduler negotiation involved. The `--ignore-daemonsets` drain flag just tells `oc adm drain` to skip evicting DaemonSet pods (they'd just respawn when the node returns) — it's a drain-behavior flag, not related to affinity at all.

**Q: Why is it called `topologyKey` and not just `labelKey`?**
Because its *purpose* is to define failure-domain layout — but mechanically it's just a string matched against an existing node label. Any label key works (`rack`, `zone`, `environment`, etc.); the name signals intent to future readers, it isn't a special reserved field.

## Exam Gotchas

- Affinity rules only apply **at pod creation** — no live re-balancing if conditions change later.
- `required` anti-affinity + limited failure domains → risk of `Pending` pods. Prefer `preferred` unless strict enforcement is explicitly required.
- PDB `selector` must exactly match pod labels — mismatch fails silently (no error, just no protection).
- PDB only guards **voluntary** disruptions — know this distinction cold, it's a common test point.
- `--delete-emptydir-data` on drain = accepting loss of node-local `emptyDir` volume data (it can't migrate with the pod).
- Red Hat does not recommend stretched (multi-site) clusters — topology keys are for failure-domain awareness *within* a supported cluster, not a justification for spanning sites.
