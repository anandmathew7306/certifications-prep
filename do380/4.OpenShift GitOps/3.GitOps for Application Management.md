## 1. Argo CD Instances

- Default instance auto-created in `openshift-gitops` namespace → has **cluster-wide** manage permissions.
  - **Rule of thumb:** use the default instance for admin purposes only; create separate, scoped instances for regular app teams.
- New Argo CD instances manage **only their own namespace** by default.
- To let an instance manage a *different* namespace, label the target namespace:

```bash
oc label namespace <target-ns> \
  argocd.argoproj.io/managed-by=<argocd-instance-namespace>
```

**⚠️ Gotcha:** the label **value** is the Argo CD instance's *namespace*, not its resource name. Easy to mix up.

## 2. Argo CD Authentication (Dex / SSO)

- Argo CD doesn't maintain its own user store by default — **Dex** delegates login to OpenShift's built-in OAuth server.
- This is *why* OpenShift group membership (e.g. custom groups you create) is visible to Argo CD RBAC.
- Manual SSO config pattern (rarely need to write this yourself if GitOps operator already sets it up):

```yaml
spec:
  sso:
    provider: dex
    dex:
      openShiftOAuth: true
```

**⚠️ Gotchas (exam-favorite):**
- GitOps 1.18 does **not** natively support Keycloak SSO — only via a self-managed generic OIDC config.
- On the *default* instance, only the local `admin` user + `cluster-admins` group get **write** access out of the box — everyone else is read-only until RBAC says otherwise.

## 3. Argo CD Permissions (built-in roles)

Two predefined roles only:

| Role | Access |
|---|---|
| `role:readonly` | read on everything |
| `role:admin` | read + write on everything |

Basic RBAC block shape:

```yaml
rbac:
  defaultPolicy: ''      # '' = no access unless explicitly granted (safe default)
  policy: |
    g, <group-name>, role:admin
  scopes: '[groups]'
```

**Why it matters:** the built-in two roles are coarse — real-world setups (e.g. one team needs full app control, another needs read-only) usually need **custom** roles → see Topic 4.

**⚠️ Gotcha:** always set `defaultPolicy` explicitly — don't leave it unset.

## 4. Fine-Grained RBAC (custom roles)

Permission line syntax:

```
p, role/user/group, resource, action, target
```

- **Resources:** applications, applicationsets, projects, clusters, repositories, accounts, certificates, exec, extensions, gpgkeys, logs.
- **Actions:** get, create, delete, update (+ sync/override/action-name for `applications`).
- **Target format:**
  - `applications`, `applicationsets`, `logs`, `exec` → `project/object` (two-part, since these live inside a project)
  - everything else → just `object`

Pattern to build a custom role:

```yaml
rbac:
  defaultPolicy: ''
  policy: |
    g, <openshift-group>, role:<custom-role-name>
    p, role:<custom-role-name>, applications, get, */*, allow
    p, role:<custom-role-name>, projects, get, *, allow
    p, role:<custom-role-name>, clusters, get, *, allow
  scopes: '[groups]'
```

**⚠️ Gotcha:** the `applications` target is two-part (`project/object`) — wrong slash placement or missing `*` wildcard is a common, easy-to-test mistake.

**Reverse gap note:** `scopes: '[groups]'` shows up in every example but isn't explained in depth — it tells Argo CD to read **group** claims (not username) from the login token for RBAC matching. Needed for any group-based policy to work at all.

## 5–6, 8, 10–11 (fast/no-mapping topics — condensed, revisit before exam)

- **Monorepo vs Polyrepo:** one repo for everything (simpler, less secure/isolated) vs. separate repos per concern (better isolation, more coordination overhead).
- **Organizing apps by environment:** prefer directories over branches per environment; Kustomize (overlays) or Helm (values files) avoid duplicating manifests. Kustomize is out of scope for this course (covered in DO280).
- **Application Validation/Rollback (intro):** framing only — real content is in Topic 9/Rollback below.
- **Argo CD Rollback:** manual rollback via History-and-Rollback button in UI. **⚠️ Enabling automatic sync disables rollback** — Argo CD just re-syncs to latest Git commit. To roll back: temporarily disable auto-sync, or revert the Git commit.
- **Argo Rollouts:** separate controller/CRDs for progressive delivery (canary-style traffic shifting, auto-rollback on failure). Not used in this exercise.

## 6. Managing Sensitive Data in GitOps

- Never store credentials/secrets in Git — repo access = access to everything in it, permanently (via history).
- Standard pattern: create `Secret` objects **directly in the cluster**, outside Argo CD's Git-managed scope.
- Argo CD-deployed apps just reference the secret name; Argo CD doesn't need to "see" the secret contents.

**⚠️ Gotcha:** creating secrets outside Git doesn't fully protect them — anyone who can create a pod in that namespace can read any secret in it, and cluster-admins can see all secrets everywhere. RBAC is the real control, not secret *location*.

- For stronger protection: third-party secret managers (e.g. Secrets Store CSI Driver → mounts secrets from Azure Key Vault / AWS Secrets Manager / HashiCorp Vault as volumes).

## 7. Argo CD Resource Hooks

Hooks = extra one-off Jobs tied to sync lifecycle stages, marked via annotation (no special CRD needed):

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  generateName: <name>
  annotations:
    argocd.argoproj.io/hook: PreSync   # or Sync / Skip / PostSync / SyncFail
```

| Hook | Fires |
|---|---|
| `PreSync` | before manifests are applied |
| `Sync` | alongside main manifests, after PreSync succeeds |
| `Skip` | tells Argo CD to leave this resource alone during sync |
| `PostSync` | after Sync hooks succeed and app is healthy |
| `SyncFail` | only if sync failed |

Optional cleanup annotation:

```yaml
argocd.argoproj.io/hook-delete-policy: HookSucceeded   # or HookFailed, BeforeHookCreation
```

**Why this matters:** common patterns are PreSync = migrate/backup DB before deploy, PostSync = smoke-test the app after deploy (e.g. curl check).

**⚠️ Gotcha:** without a `hook-delete-policy`, old hook Job objects pile up in the namespace after every re-sync — expected behavior, not a bug, if you see multiple old backup/test Jobs lying around.

## Quick Reference — RBAC Policy Line Cheatsheet

```
g, <group>, role:<role-name>              # assign group to role
p, role:<role-name>, applications, get, */*, allow     # read all apps in all projects
p, role:<role-name>, applications, *, */*, allow       # full control, all apps, all projects
p, role:<role-name>, projects, get, *, allow           # read all projects
p, role:<role-name>, clusters, get, *, allow           # read all clusters
```
