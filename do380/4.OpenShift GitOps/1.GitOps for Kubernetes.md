## Core Concept

GitOps = **declarative resource management** (describe desired state as text, not as a sequence of imperative commands) + storing that state in **Git** as the single source of truth + a controller continuously reconciling the live cluster to match it.

- **Drift** = the gap between the intended state (what's in Git) and the actual state (what's running in the cluster).
- Because a single process (the GitOps controller) applies changes, admins get a reliable audit trail and a way to reproduce environments (e.g., spin up a test cluster from the same definition used for production).

---

## Why Plain `kubectl apply` GitOps Breaks Down

Kubernetes resources mix two things in one object:

- **spec** — the actual definition (what GitOps cares about)
- **status** — runtime info (replica counts, conditions, timestamps) that changes on its own and should be ignored when diffing

Other complicating factors:
- Some fields get auto-added by the cluster (`creationTimestamp`, defaulted `strategy` values) and aren't meaningful to track in Git.
- Creation order sometimes matters (namespace before its resources; CRDs before the custom resources that depend on them).
- Mutating admission webhooks can modify resources after creation, adding more complexity.

This is why a dedicated tool (Argo CD) exists instead of relying on raw `kubectl apply` scripting.

## OpenShift GitOps Architecture

- **Delivered as an Operator.** It manages Argo CD instances on the cluster — it isn't a Helm chart, a Kustomization, or a base OpenShift component.
- Installing it auto-creates a **default Argo CD instance in the `openshift-gitops` namespace**, with elevated/cluster-scoped permissions — intended for cluster administrators managing the cluster itself.
- Admins can also create **additional scoped Argo CD instances**, restricted to specific namespaces with specific user access — this lets dev teams manage their own app deployments autonomously without broad cluster access.
- **Argo CD "Application"** = a custom resource pointing at a Git repo/path of manifests, with a sync policy (manual or automatic). The Argo CD web console visualizes both the defined resources and their derived resources (e.g., Deployment → ReplicaSet → Pods) along with sync/health status.

**How GitOps helps control cluster changes:**
- Restricts direct API access, since changes are expected to flow through Git instead.
- Lets Argo CD validate/detect drift and gives admins a place to implement approval/review policies before changes land.
- *Not* about GitOps managing Git repo permissions, and *not* mainly about multiple Argo CD instances as an access-control mechanism — those are distractor answers.

## CI/CD Terminology (Red Hat's framing)

| Term | Meaning |
|---|---|
| Continuous Integration (CI) | Integrate/test changes frequently; often now means automated testing gating merges |
| Continuous Delivery | Every change is a potential release; team *can* deploy anytime |
| Continuous Deployment | Every change *automatically* deploys — maximizes release frequency |

- **OpenShift GitOps (Argo CD) covers CD (delivery/deployment) — not CI.**
- **OpenShift Pipelines** (Tekton-based) covers the CI side: validating changes, building updated container images from source.
- Red Hat recommends **OpenShift Pipelines + OpenShift GitOps** together over Jenkins for OpenShift-native CI/CD — Jenkins is a generic tool that needs extra effort to replicate these functions.

**Typical combined workflow:** dev pushes → PR opened → Pipelines runs checks + deploys to test env via Argo CD → team reviews → merge → Pipelines builds new image → Argo CD syncs production.

## Security Note (flag for exam — compliance is a recurring DO380 theme)

- Git is not automatically secure. If sensitive data (secrets, tokens) is pushed to a repo, removing it from Git history afterward is hard/expensive.
- Better response to a leak: **rotate/invalidate the credential** (e.g., disable the leaked token) rather than relying on scrubbing history.
- **Git hooks** can be used to block sensitive data from being pushed in the first place.

## Quiz Answer Key (GitOps for Kubernetes)

1. **Purpose of GitOps** → *Storing Kubernetes resource definitions in Git repositories*
2. **Two direct benefits of GitOps** → *Applying version control techniques to cluster admin* + *Improving control/audit/approval tooling for cluster changes* (not "automated testing" or "team alignment" — those are DevOps-adjacent, not direct GitOps benefits)
3. **How OpenShift GitOps is delivered** → *An operator*
4. **Two ways OpenShift GitOps controls cluster changes** → *Limits direct API access (changes go through Git)* + *Validates changes, enabling change-prevention policies*
5. **Practice OpenShift GitOps relates to** → *Continuous delivery and deployment*
6. **"Drift" in GitOps** → *The difference between the intended state (in Git) and the actual state of the cluster*

## Gotchas / Common Traps

- Don't conflate "GitOps" (Q1) with "CD/automated deployment after review" — the *definition* tested here is about Git being the source of truth, not the deployment automation outcome itself.
- OpenShift GitOps does **not** manage Git repository permissions (access control) or use multiple Argo CD instances as a permissions mechanism — those are plausible-sounding wrong answers.
- Remember: GitOps (Argo CD) ≠ CI. If a question mentions validating/testing source code or building images, that's OpenShift Pipelines' job, not GitOps'.
