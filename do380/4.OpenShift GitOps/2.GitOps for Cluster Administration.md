## 1. GitOps Operator Basics

- Installed from OperatorHub like any other operator (channels: `latest`, or version-pinned like `gitops-1.18`).
- Operator itself runs in `openshift-gitops-operator` namespace.
- The operator's job: watch `ArgoCD` custom resources and manage the Argo CD workloads they describe.

**Why it matters:** Don't confuse operator namespace (`openshift-gitops-operator`) with the *default Argo CD instance's* namespace (`openshift-gitops`) — easy mix-up on the exam.

---

## 2. Argo CD Custom Resources & Multiple Instances

- `ArgoCD` CRD lets you declaratively create **multiple** Argo CD instances with different permission levels (principle of least privilege).
- **Security note:** anyone who can push to an app's Git repo effectively has that Argo CD instance's permissions — even without direct cluster/API access. Treat Git repo access control as seriously as cluster RBAC.

---

## 3. The Default Argo CD Instance

- Auto-created on operator install: instance name `openshift-gitops`, namespace `openshift-gitops`.
- Red Hat guidance: reserve this instance for **cluster administration only**; create separate low-privilege instances for regular app deployment.
- Web console reachable via the `openshift-gitops-server` route, or via the OpenShift console's application-switcher menu.

**Why it matters:** Default instance ships minimal — expect to customize (RBAC, certs) before real use.

## 4. Configuring Argo CD RBAC

Argo CD has its **own** RBAC system — separate from OpenShift/Kubernetes RBAC. OpenShift cluster-admin means nothing to Argo CD unless explicitly granted.

Key fields under `spec.rbac` in the `ArgoCD` resource:

```yaml
spec:
  rbac:
    defaultPolicy: ""      # role for any authenticated user with no matching rule
    policy: |
      g, system:cluster-admins, role:admin
      g, cluster-admins, role:admin
      g, <your-group>, role:admin
    scopes: '[groups]'
  sso:
    dex:
      openShiftOAuth: true  # enables "Log in via OpenShift" button
```

- `defaultPolicy: ""` → users can log in, but have **zero** permissions unless a `policy` rule matches their group.
- `policy` lines use format: `g, <group-name>, role:<role-name>`.
- Local `admin` user also exists by default (password stored in a Secret in the `openshift-gitops` namespace) — fine for test setups, but real deployments should wire up OpenShift SSO instead.

**Exam gotchas:**
- `defaultPolicy: ""` ≠ "can't log in." It means "logged in, but powerless." Don't conflate login access with permissions.
- Argo CD RBAC only controls access **through Argo CD's own UI/CLI/API** — it does **not** block direct Kubernetes API access to the same resources. Use real Kubernetes RBAC for that.

**Command used:**
```bash
oc project openshift-gitops
oc edit argocd openshift-gitops
```

## 5. Trusted Certificates for Git Access (CA Injection)

Argo CD's **repo server** component only trusts HTTPS Git repos whose cert chain it recognizes. For private/internal CAs, you must inject trust manually.

**Two-step trick to auto-populate a CA bundle:**

```bash
oc create configmap cluster-root-ca-bundle
oc label configmap cluster-root-ca-bundle \
  config.openshift.io/inject-trusted-cabundle=true
```
→ OpenShift detects the label and auto-fills the configmap with the cluster CA bundle under the `ca-bundle.crt` key.

**Mount it into the repo server:**

```yaml
spec:
  repo:
    volumeMounts:
      - mountPath: /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
        name: cluster-root-ca-bundle
        subPath: ca-bundle.crt
    volumes:
      - configMap:
          name: cluster-root-ca-bundle
        name: cluster-root-ca-bundle
```

**Exam gotchas:**
- Remember the label name exactly: `config.openshift.io/inject-trusted-cabundle=true` — this is what triggers auto-population; don't manually fill the CA bundle when this label does it for you.
- The mount path (`/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem`) is fixed/expected by the repo server — not arbitrary.
- `subPath` pulls a single key out of a multi-key configmap — general Kubernetes knowledge, easy to blank on under pressure.

## 6. The Argo CD Web Interface

- Login page: **"Log in via OpenShift"** (SSO, see Topic 4) or local username/password.
- Post-login home: **Applications** page — shows all apps + health/sync status.
- App details view: resource tree, showing app resources + related resources; can collapse nodes to reduce clutter.
- **User Info** page: useful for debugging auth/identity issues.

**Why it matters:** For large apps, the UI can get cluttered — fall back to `oc`/`kubectl` for reliable inspection at scale.

## 7. Creating Applications

Fields on the Argo CD "Create Application" form:

| Field | Meaning |
|---|---|
| Application Name | Name of the Argo CD `Application` resource |
| Project Name | Argo CD's own grouping/access-control concept (use `default` unless told otherwise) |
| Sync Policy | `Automatic` = auto-sync on Git changes; `Manual` = you trigger sync yourself |
| Retry | Auto-retry failed syncs (useful with sync waves / slow dependencies) |
| Repository URL | Git repo source (must be HTTPS-trusted — see Topic 5) |
| Path | Folder within the repo treated as this app's source |
| Cluster URL | Target cluster API; use the well-known local-cluster value to deploy to the same cluster Argo CD runs on |

- Supported app source formats beyond plain YAML: Helm charts, Kustomize, Jsonnet, plugin-supported tools.

**Exam gotcha:** `OutOfSync` is not an error — it just means Git and cluster don't currently match. Know the local-cluster API URL value by heart (easy to blank on).

## 8. Sync Waves & Retries *(condensed — conceptual)*

- `argocd.argoproj.io/sync-wave: "N"` annotation controls order; lower numbers sync first; a wave only starts once all lower waves are healthy. No annotation = wave `0`.
- Dry-run can fail if a resource type doesn't exist yet (e.g., CRD not installed). Fix with:
  ```
  argocd.argoproj.io/sync-options: SkipDryRunOnMissingResource=true
  ```
- **Retries** exist because sync waves alone aren't always enough for complex apps (e.g., operators). Configure retry when sync waves aren't sufficient — but don't over-retry (clutters logs, hides real problems).

**Exam gotcha:** `sync-wave` (ordering) and `sync-options` (behavior flags) are two different annotation keys — don't conflate them.

---

## 9. Eventual Consistency *(condensed — conceptual)*

- Kubernetes changes don't propagate instantly across the cluster — a deliberate tradeoff for scalability/reliability.
- This is *why* retries matter: a dependent resource/operation might not be "ready" the instant you expect it to be.

## 10. Server-Side Apply (Patching Existing Cluster Resources)

**Use case:** administering a cluster with GitOps sometimes means **patching** an existing singleton resource (e.g., cluster `Console`, `OAuth` config) rather than creating something new.

**Problem with default (client-side) apply:** it needs a reasonably complete resource definition to diff against the current state — awkward for a one-field tweak.

**Server-side apply:** submit only the fields you want changed; the API server merges them in.

**Enable via two sync-option flags together:**
```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: ServerSideApply=true,Validate=false
```
- `ServerSideApply=true` → use patch-only merge behavior.
- `Validate=false` → allow submission even though your YAML is deliberately incomplete (skips required-field validation).

**Shape of a patch manifest (conceptual):**
```yaml
apiVersion: operator.openshift.io/v1
kind: Console
metadata:
  name: cluster
  annotations:
    argocd.argoproj.io/sync-options: ServerSideApply=true,Validate=false
spec:
  customization:
    customProductName: <value>
```

**Exam gotchas:**
- Both flags are needed together — `ServerSideApply=true` alone isn't enough if the patch is incomplete.
- This technique is specifically for **pre-existing, singleton cluster resources** — not a normal pattern for deploying new apps.
- Server-side apply is "less disruptive to concurrent changes" (e.g., cluster upgrades) since it only touches specified fields — good phrase to recall if asked *why* prefer it.

## General Exercise Command Flow (sanitized, generic form)

```bash
# Log in and locate console
oc login -u <admin-user> -p <password> <cluster-api-url>
oc whoami --show-console

# Switch to gitops namespace and edit the default instance
oc project openshift-gitops
oc edit argocd openshift-gitops        # RBAC rule, CA volume mount

# CA trust setup
oc create configmap cluster-root-ca-bundle
oc label configmap cluster-root-ca-bundle config.openshift.io/inject-trusted-cabundle=true

# Prepare Git content (generic Git workflow — not GitOps-specific)
git clone <repo-url>
cd <repo-dir>
git add <file>
git commit -m "<message>"
git push

# Verify after sync
oc get groups
```
