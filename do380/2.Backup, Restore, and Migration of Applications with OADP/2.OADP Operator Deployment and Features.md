## Why OADP instead of manual export/import
OADP (built on Velero) automates resource export/clean/import, image-adjacent
data movement, and PV snapshotting into two declarative CRDs: `Backup` /
`Schedule` and `Restore`. No manual `yq` field-stripping, no throwaway pods.

| Concern | Manual approach | OADP approach |
|---|---|---|
| Resource export/clean/import | `oc get -o yaml` + `yq` + `oc apply` | Declared via `includedResources` + label selectors |
| App consistency during backup | Scale deployment to 0 | **Hooks** — pre/post exec commands while app keeps running |
| PV data capture | Manual VolumeSnapshot → PVC → pod → `oc cp` | CSI snapshot + Data Mover, automatic |
| Recurring backups | Not applicable | `Schedule` CRD (cron syntax) |
| One-off backup trigger | N/A | `velero backup create --from-schedule <name>` |

---

## Core OADP objects
- **DataProtectionApplication (DPA)** — cluster-level OADP config: enables
  plugins (`openshift`, `aws`, `csi`), enables CSI snapshot + Data Mover.
- **BackupStorageLocation** — where backups land (e.g. S3 bucket). Check with:
  ```
  oc get -n openshift-adp BackupStorageLocations
  ```
- **Schedule** — cron-based recurring backup definition. Use `paused: true`
  while testing to avoid unwanted runs.
- **Backup** — a single backup run, either scheduled or manually triggered.
- **Restore** — restores a named backup into a target namespace (can remap
  namespace names).
