> The first three exam objectives (export/import app, export/import images, deploy OADP) are independently testable — not just setup for OADP. Manual mechanics need the same command fluency as OADP itself.

---

## Phase 1 — Baseline Check
Connect to the live app, note some identifiable piece of data to verify
restore later. No CLI needed — usually done via the app's UI.

## Phase 2 — Inventory
```
oc get all
oc get pvc,secret,configmap
```
`oc get all` skips PVCs, Secrets, and ConfigMaps — always check separately.

## Phase 3 — Export Resources
```
oc get <type>/<name> -o yaml > <file>.yaml
```

## Phase 4 — Clean Resources
Strip server-assigned fields so YAML is portable to a new project.

Universal fields (strip from every resource type):
```
yq -i '
  del(.metadata.annotations) |
  del(.metadata.creationTimestamp) |
  del(.metadata.resourceVersion) |
  del(.metadata.uid) |
  del(.metadata.namespace) |
  del(.status)
' <file>.yaml
```

Type-specific extras:

| Resource type | Also strip |
|---|---|
| Deployment | `.metadata.generation` |
| Service | `.spec.clusterIP`, `.spec.clusterIPs` |
| Route | `.spec.host` |
| PVC | `.metadata.finalizers`, `.spec.volumeName` |

## Phase 5 — Expose Internal Registry *(only if moving images outside the cluster)*
```
oc edit configs.imageregistry.operator.openshift.io/cluster
```
Add under `spec:`
```yaml
spec:
  defaultRoute: true
```
Wait for rollout to settle:
```
watch -n10 oc get co openshift-apiserver
```
Undo at cleanup by setting `defaultRoute: false` again.

## Phase 6 — Export Images
```
oc describe is <imagestream-name>
# read the "Image Repository:" line manually
oc image mirror <image-repository-value> file://<local-name>
```
One command per imagestream — all tags come along automatically.

## Phase 7 — Snapshot + Export Data
```
oc get pvc
oc get storageclass <storageclass-name>
oc get volumesnapshotclasses
oc scale deployment/<name> --replicas 0
oc get pods                              # confirm none running
oc apply -f volumesnapshot.yaml
oc get volumesnapshot
oc scale deployment/<name> --replicas 1
oc apply -f pvc-from-snapshot.yaml
oc get pvc <new-pvc-name>                # confirm Bound
oc apply -f pod-mount.yaml
oc cp <pod-name>:/<mountpath> ./local-data
oc delete pod/<pod-name>
```

## Phase 8 — Import (mirror of 3–7, reversed)
```
oc new-project <new-project-name>
oc image mirror --dir=<local-name> file://<local-name> \
  <new-registry-route>/<new-project-name>/<image-name>

oc apply -n <new-project-name> -f <pvc>.yaml
oc apply -f pod-restore.yaml
oc rsync ./local-data/ <pod-name>:/<mountpath>/
oc delete pod/<pod-name>

oc apply -f <deployment>.yaml
oc apply -f <service>.yaml
oc apply -f <route>.yaml
```
App must not be running against the volume during data import.

## Phase 9 — Verify
```
oc get route
```
Check the identifiable data from Phase 1 is present.

## Phase 10 — Cleanup
```
oc edit configs.imageregistry.operator.openshift.io/cluster   # defaultRoute: false
oc delete project <new-project-name>
```

## Key Gotchas (exam traps)

- `oc get all` never shows PVCs, Secrets, or ConfigMaps — check explicitly.
- Service export needs `spec.clusterIP`/`clusterIPs` stripped or creation fails
  ("IP already allocated").
- Route export needs `spec.host` stripped or it tries to reuse the old host.
- `VolumeSnapshotClass` driver must match the source PVC's StorageClass
  provisioner.
- New PVC from a snapshot must request storage size ≥ original snapshot size.
- Never run the live app against a volume while importing/restoring data into
  it — risk of corruption.
- Exposing the internal registry (`defaultRoute: true`) triggers an apiserver
  rollout — can take several minutes, and must be undone at cleanup.

## Terminology / CLI Quick Reference

Finding a resource's fully-qualified name when unsure:
```
oc api-resources | grep -i <keyword>
```
Pattern to build the FQDN from the output:
```
<NAME column>.<APIVERSION column without the trailing /vX>
```
Example: `NAME=configs`, `APIVERSION=imageregistry.operator.openshift.io/v1`
→ `configs.imageregistry.operator.openshift.io`

Short names (`co` for clusteroperator, `svc` for service, etc.) work for quick
checks, but prefer fully-qualified names in graded/scripted steps to avoid
ambiguity.
