## 1. Core Concepts

| Term | Meaning |
|---|---|
| **Alerting rule** | PromQL condition + metadata. Required: `alert` (name), `expr` (PromQL). Optional: `for`, `keep_firing_for`, `labels`, `annotations`. |
| **Alert** | A firing instance of a rule's condition. States: `Firing`, `Pending`, `Silenced`, inactive (`-`). |
| **Receiver** | Notification destination: Email, PagerDuty, Slack, Webhook. |
| **Silence** | Time-boxed mute on alerts matching a label selector. Stops *notifications*, not the alert (shows as "Silenced" in UI). |
| **Alertmanager** | Prometheus-stack component that owns routing/notification logic. Config lives in the `alertmanager-main` Secret (`openshift-monitoring` ns). Requires cluster-admin. |

**`for` vs `keep_firing_for`:**
- `for` → delay before alert **starts** firing (condition must hold this long first).
- `keep_firing_for` → delay before alert **stops** firing after condition clears (anti-flap).

### Console navigation
- View rules/alerts/silences → `Observe → Alerting` (tabs: Alerts / Silences / Alerting rules)
- Configure Alertmanager via GUI → `Administration → Cluster Settings → Configuration tab → Alertmanager`

## 2. Key Gotchas (exam-relevant)

- **No default routing.** Out of the box, the monitoring stack sends alerts to **no receiver**. Routing must be explicitly configured.
- **Filters hide things.** `Alerts` page auto-applies `Source: Platform` + `Alert State: Firing` filters. A resolved/silenced alert won't show until filters are cleared — don't assume "empty list" means failure.
- **Silences match labels, not names.** `alertname` is just a label like any other — silence scope can be broader/narrower than "this one alert."
- **`continue:` in routing tree** — default `false` (alert stops at first matching child route). Set `continue: true` on a matching node to let the alert **also** match subsequent sibling routes. Forgetting this is the #1 way an alert silently only reaches one receiver when you wanted two.
- **Timing fields, don't confuse:**
  - `group_wait` — initial buffer before first notification of a new alert group.
  - `group_interval` — delay before notifying about *new* alerts added to an already-notified group.
  - `repeat_interval` — how often to resend if still firing.
  - **If `repeat_interval` < `group_interval`** → Alertmanager logs a warning; notifications won't actually repeat until the next `group_interval` elapses. (Observed live in lab logs — expected behavior, not a bug.)
- **`oc set data`, not `oc apply`/`oc create secret`** — pushing edited Alertmanager config back into the secret uses `oc set data`. Using `oc create secret --from-file` risks conflict/overwrite of other keys.
- **Silent config failures.** A bad config (e.g., unreachable SMTP host) does **not** crash the pod or error on push — it only surfaces later as `"Notify attempt failed"` warnings in logs when an alert actually tries to fire. Always check `oc logs` for `"Completed loading of configuration file"` after any config change — never assume success from a clean `oc set data` output.
- **Built-in receivers exist by default**: `Default`, `Watchdog`, `Critical` are pre-defined. `Watchdog` is a permanent heartbeat alert (always firing) confirming the alerting pipeline is alive — not a real problem.

## 3. GUI vs CLI — Are They Equivalent?

**Yes.** Both edit the *same* object: the `alertmanager-main` Secret's YAML content (`global` / `receivers` / `route` sections). The GUI forms are just a form-based editor over the identical extract → edit → push cycle used manually via CLI.

- If a task doesn't specify a method → either is valid; exam grades end-state, not tool used.
- GUI: faster for simple, single-receiver/single-matcher changes.
- CLI: necessary for precise `continue:` ordering across multiple sibling routes, scripting, or when console access is explicitly restricted.
- **No merge** — last write (GUI or CLI) wins; re-extracting shows whatever was pushed most recently.

## 4. CLI Workflow (exercise used GUI only — this is the CLI-equivalent path)

```bash
# 1. Confirm the secret exists
oc get secret/alertmanager-main -n openshift-monitoring

# 2. Extract current config to local file
oc extract secret/alertmanager-main -n openshift-monitoring --to . --confirm

# 3. Strip cosmetic quoting for readability (optional)
sed -i 's/"//g' alertmanager.yaml

# 4. Edit alertmanager.yaml (see structure below)

# 5. Push edited config back into the secret
oc set data secret/alertmanager-main -n openshift-monitoring --from-file alertmanager.yaml

# 6. Verify it loaded successfully
oc logs -f statefulset.apps/alertmanager-main -c alertmanager -n openshift-monitoring
# Look for: "Completed loading of configuration file"

# 7. Verify the resolved routing tree directly (no need to trigger a real alert)
oc exec alertmanager-main-0 -n openshift-monitoring -- \
  amtool config routes show --alertmanager.url http://localhost:9093
```

> **Reverse gap:** the guided exercise never uses `amtool`. It verifies purely by waiting for a real notification email. `amtool config routes show` is the fast way to confirm routing logic without waiting for an alert to fire.

### YAML structure reference

```yaml
global:
  smtp_from: <default-from-address>
  smtp_smarthost: '<smtp-host>:<port>'
  smtp_hello: <hostname>
  smtp_auth_username: <username>
  smtp_auth_password: <password>
  smtp_require_tls: false

receivers:
- name: Default
- name: Watchdog
- name: Critical
- name: team-admins
  email_configs:
  - to: <recipient-address>
    from: <sender-address>
    smarthost: '<smtp-host>:<port>'
    require_tls: false
    send_resolved: true      # whether to notify when alert resolves

route:
  group_by: ['namespace']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h
  receiver: Default
  routes:
  - matchers:
    - alertname = PersistentVolumeUsageNearFull
    receiver: team-admins
    continue: true            # allows falling through to sibling routes below
  - matchers:
    - alertname = Watchdog
    receiver: Watchdog
  - matchers:
    - severity = critical
    receiver: Critical
```
