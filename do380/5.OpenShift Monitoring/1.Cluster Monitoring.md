## 1. Observability Portfolio (orientation only)

| Component | One-liner | Upstream project |
|---|---|---|
| Logging for Red Hat OpenShift | Centralizes pod/node logs | — |
| **OpenShift Monitoring** | Metrics + alerts for cluster/core components (this chapter) | Prometheus |
| Network Observability | Analyzes network traffic / connectivity | — |
| Distributed Tracing Platform | Distributed trace collection | Grafana Tempo |
| Red Hat build of OpenTelemetry | Vendor-neutral telemetry collection | OpenTelemetry |
| Power Monitoring | Power usage per project | Kepler |

RHACM = multi-cluster observability layer on top of all this.

**Why it matters:** exam may ask "which upstream project backs X" — Tempo↔tracing, Kepler↔power.

## 2. OpenShift Monitoring — Key Facts

- Installed **by default** in `openshift-monitoring`, no setup needed for platform monitoring.
- **Cluster Monitoring Operator (CMO)** owns the stack — deploys it, keeps it updated, **reverts manual edits**.
- Default stack covers **all namespaces + core platform components** (etcd, kube-apiserver, etc.) but **not custom app metrics**.
- Custom metrics/alerts for your own apps require **User Workload Monitoring (UWM)** — opt-in, separate stack.
- **Persistent storage** for Prometheus/Alertmanager is optional and **off by default** — needed to retain history across pod restarts.

**Gotcha:** Editing/creating `ServiceMonitor`, `PodMonitor`, `PrometheusRule` directly inside `openshift-monitoring` is **unsupported** — CMO resets it. Custom monitoring config belongs in `openshift-user-workload-monitoring` (via UWM) instead.

## 3. Monitoring Stack Architecture

**Platform stack** → namespace `openshift-monitoring` (always on):

| Component | Role |
|---|---|
| CMO | Top-level operator |
| Prometheus Operator | Deploys/configures Prometheus + Alertmanager; manages scrape targets |
| Prometheus | Monitoring server (scrapes + stores time-series) |
| Metrics Server | Feeds Kubernetes metrics API (`kubectl top`, HPA) — **not** the same as Prometheus |
| Alertmanager | Groups/routes firing alerts to receivers |
| kube-state-metrics | Generic K8s object → metrics |
| openshift-state-metrics | OpenShift-specific object metrics (e.g. image registry) |
| node-exporter | Low-level host/node metrics |
| Thanos Querier | Multitenant query interface — aggregates platform + user workload metrics; backs dashboards/Metrics page |
| Telemeter Client | Sends subset of metrics to Red Hat for remote health monitoring |

**User workload stack** → namespace `openshift-user-workload-monitoring` (opt-in):
Prometheus Operator, Prometheus, **Thanos Ruler** (rule evaluation), Alertmanager.

**Gotchas:**
- Metrics Server (K8s API) ≠ Prometheus (monitoring/alerting engine) — commonly confused.
- Thanos **Querier** = reads/aggregates (platform side). Thanos **Ruler** = evaluates alert/recording rules (user workload side).
- Metric name style hints at source agent: generic K8s object → kube-state-metrics; OpenShift-flavored object → openshift-state-metrics; raw host metric → node-exporter.

## 4. User Workload Monitoring (UWM) — condensed

- Opt-in via ConfigMap (`cluster-monitoring-config` in `openshift-monitoring`, `enableUserWorkloadMonitoring: true`).
- Lets you define **custom metrics + custom alerts** scoped to your own projects.
- Deploys its own Prometheus Operator, Prometheus, Thanos Ruler, Alertmanager in `openshift-user-workload-monitoring`.

⚠ **Reverse-gap note:** theory only points to external docs for the actual enablement steps/YAML — if a later lab expects this cold, review the linked "Configuring User Workload Monitoring" doc beforehand.

## 5. Prometheus Data Model

- Every sample = **timestamp + numeric value + labels (key-value pairs)**.
- Labels are what dashboard table columns (namespace, node, endpoint, job...) actually represent.
- Labels are the filtering mechanism in PromQL (`{key="value"}`).

## 6. Web Console Navigation Map

`Observe` menu has 4 subsections:

| Subsection | Purpose |
|---|---|
| Alerting | Firing/pending alerts, silences, alerting rules |
| Metrics | Free-form PromQL query box + predefined queries |
| Dashboards | Pre-built dashboards (kubernetes-mixin family + etcd/API performance/networking) |
| Targets | Scrape target health (up/down) — use this to debug "is Prometheus even reaching this endpoint" |

**Bridge mechanic:** clicking **Inspect** on any dashboard panel jumps into `Observe → Metrics` with that panel's underlying PromQL pre-filled. Key technique for going from graph → raw query.

## 8. PromQL Cheat Sheet

```promql
# Bare metric name → all time series for that metric
metric_name

# Label filter (exact match)
metric_name{label="value"}

# Label filter (regex — lets you match multiple values)
metric_name{label=~"value1|value2"}

# Comparison operators FILTER the result set (drop non-matching series)
metric_name{label="value"} == 1
metric_name > 0.5

# Arithmetic across two metrics (e.g. percentage pattern)
metric_a / metric_b * 100 < 50
```

**Built-in functions:**

| Function | Does |
|---|---|
| `sum()` | Adds values across matched series |
| `rate()` | Per-second average change over a time range (for counters) |
| `count()` | Counts matched series/samples |
| `max()` | Max value among matched series |

**Gotchas:**
- `=` = exact match, `=~` = regex — easy typo, silently wrong/empty results.
- `_status_` / `_phase` style metrics are usually **one-hot encoded**: value is `1` for the currently-true label combination, `0` for all others of the same series family. Always expect `== 1` filtering with these.
- `rate()` only makes sense on **counter** metrics with a range vector (`[5m]`) — using it on a gauge is meaningless.

## 9. Dashboards Cheat Sheet

**Naming pattern = scope × breakdown dimension.** Same panel layout everywhere; only the slicing changes.

| Dashboard | Scope | Broken down by |
|---|---|---|
| Compute Resources / Cluster | Whole cluster | — (totals only) |
| Compute Resources / Namespace (Pods) | One namespace | Individual pods |
| Compute Resources / Namespace (Workloads) | One namespace | Workload (deployment/daemonset/statefulset) |
| Compute Resources / Node (Pods) | One node | Pods on that node |
| Compute Resources / Pod | One pod | Its containers |
| Compute Resources / Workload | One workload | Its pods |
| Node Exporter / USE Method / Cluster | All nodes side by side | Utilization / Saturation / Errors |
| Networking / Cluster, Namespace (Pods), Pod | Same scope pattern as Compute Resources | Network traffic instead of CPU/memory |
| etcd, API Performance | Specialized, component-specific | — |

**Mechanics:**
- Table column headers (e.g. "CPU Usage") are **sortable** — click to toggle ascending/descending.
- **% Requests / % Commitment** columns = (usage ÷ requested) × 100. >100% = using more than requested — the actual anomaly signal to look for.
- **Inspect** on a panel → jumps to Metrics page with pre-loaded PromQL.

**Gotchas:**
- Don't confuse cluster-wide "which namespace is the problem" dashboards with within-namespace "which workload is the problem" dashboards — different scope, similar name.
- Usage **below** requests is normal — the real signal is usage **exceeding** requests/quota, or a workload showing **erratic/spiking** patterns vs flat constant usage.
- Dashboard data can lag; a browser reload is sometimes genuinely needed (documented UI quirk, not a real fault).
- The Dashboards dropdown lists many entries because OpenShift ships the full **kubernetes-mixin** family (tagged `kubernetes-mixin`, `etcd-mixin`, `networking-mixin`, etc.) — same panel layouts, differing only in **scope** (cluster/namespace/node/pod/workload) and **metric domain**.

**Node health PromQL** (one-hot `kube-state-metrics` pattern):
```promql
kube_node_status_condition{condition="Ready", status=~"unknown|false"} == 1
```

## Consolidated Exam Gotchas

- CMO resets manual edits to `ServiceMonitor`/`PodMonitor`/`PrometheusRule` in `openshift-monitoring` — customizations go through UWM instead.
- Metrics Server ≠ Prometheus.
- Thanos Querier (read/aggregate, platform) ≠ Thanos Ruler (rule evaluation, user workload).
- `=` vs `=~` in PromQL — regex vs exact match.
- `_status_`/`_phase` metrics are one-hot encoded; expect `== 1` filters.
- "Namespace (Pods)" vs "Namespace (Workloads)" dashboards — same scope, different breakdown.
- Anomaly signal = usage **exceeding** requests, or **erratic** patterns — not just "high" in isolation.
- UWM enablement config lives in a ConfigMap in `openshift-monitoring`, but the components it deploys live in `openshift-user-workload-monitoring`.
