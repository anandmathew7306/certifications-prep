## 1. Service Accounts (SA) — Fundamentals

- SA = identity for a **component** (pod/controller/external app) to talk to API server. Uses signed JWTs.
- **Namespace-scoped** — SA only exists inside the project it was created in. Cannot be shared across projects.
- Full identity string:
  ```
  system:serviceaccount:<project>:<sa-name>
  ```
- Built-in groups every SA belongs to:

| Group | Scope |
|---|---|
| `system:serviceaccounts` | ALL SAs, cluster-wide |
| `system:serviceaccounts:<project>` | ALL SAs in one specific project |

**Why this matters:** Bind roles to `system:serviceaccounts:<project>` to grant a permission to every current *and future* SA in that project, instead of binding SAs one-by-one.

### Users & Groups — contrast
| Object | Scope |
|---|---|
| User | **Cluster-wide** identity (from IdP) |
| Group | **Cluster-wide** |
| Service Account | **Namespace-scoped** |

Users/Groups get different access per-project via **RoleBindings** (their identity itself never changes). SAs' identity *itself* is tied to the namespace.

**Gotcha:** Pod failing to auth as expected? Check `serviceAccountName:` in the pod spec actually exists **in that same namespace**.

## 2. Default Service Accounts (auto-created per project)

| SA | Purpose | Default Role |
|---|---|---|
| `builder` | Build pods | `system:image-builder` (push images to any image stream via internal registry) |
| `deployer` | Deployment pods | `system:deployer` (view/modify RCs & pods) — **only relevant for `DeploymentConfig`, not plain `Deployment`** |
| `default` | Any pod without explicit `serviceAccountName` | No elevated perms |

**Gotcha:** Pod can't push images / manage RCs? Check if it's silently running as `default` because `serviceAccountName` was never set.

## 3. Bound Service Account Tokens

- Modern replacement for legacy non-expiring secret-based tokens. **Time-limited + bound to an object** — invalidated when that object (e.g. pod) is deleted.
- Default token auto-mounted into every pod automatically via TokenRequest API + kubelet — **no YAML needed** for basic in-cluster API access.
- Custom YAML needed only when overriding defaults (custom expiry, custom audience for e.g. Vault integration, custom mount path):

```yaml
spec:
  serviceAccountName: build-robot        # which SA
  volumes:
  - name: vault-token
    projected:
      sources:
      - serviceAccountToken:
          path: vault-token               # relative path under mountPath
          expirationSeconds: 7200         # default = 3600 (1 hour)
          audience: vault                 # default = API server identifier
```

**Key defaults/numbers to remember:**
- Default `expirationSeconds` = **3600** (1 hr)
- Kubelet auto-rotates token at **80% of TTL**, or if **older than 24h**
- Default `audience` = the API server itself — set explicitly when token is meant for an external system (e.g. Vault), or that system will reject it

## 4. Manual Bound Tokens (external clients) + JWT structure

```bash
oc create token my-sa
oc create token my-sa --duration=24h     # override default 1hr lifetime
```

- Used as: `Authorization: Bearer <token>` header
- **No auto-rotation** — you must manually refresh before expiry (unlike pod-mounted tokens)

**Decoded JWT — fields to recognize:**
```json
{
  "aud": ["https://kubernetes.default.svc"],
  "exp": 1765671322,
  "iat": 1765667722,
  "kubernetes.io": {
    "namespace": "test",
    "serviceaccount": { "name": "my-sa" }
  },
  "sub": "system:serviceaccount:test:my-sa"
}
```
`sub` = the exact identity string RBAC evaluates against. Debug denied auth by checking `sub`, `exp`, `aud` first.

## 5. Client Certificate Authentication

- Alt to tokens. Uses OpenShift's **internal CA**. Main use: `system:admin` backdoor if IdP fails.
- **CN** in cert → username. **O** (repeatable) → group(s).
- **Red Hat recommends SAs over certs** for automation — certs **cannot be individually revoked** (would require invalidating the whole CA).

### Full CSR workflow (memorize sequence):

**1. Generate CSR + key:**
```bash
openssl req -noenc -newkey rsa:4096 -keyout key_filename \
  -subj "/O=group1/O=group2/CN=username" -out csr_filename
```

**2. CSR manifest:**
```yaml
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: csr_name
spec:
  signerName: kubernetes.io/kube-apiserver-client   # built-in signer for client auth
  expirationSeconds: 604800   # default = 30 days (NOT 1hr — different from SA tokens!)
  request: $(base64 -w0 csr_filename)
  usages:
  - client auth      # mandatory for client-cert use case
```

**3. Submit:**
```bash
oc apply -f csr.yaml
```

**4. Review & approve:**
```bash
oc describe csr csr_name
oc adm certificate approve csr_name
```

**5. Retrieve signed cert:**
```bash
oc get csr csr_name -o jsonpath='{.status.certificate}' | base64 -d > certificate_filename
```

**6. Distribute** cert + private key to client.

**Gotchas:**
- Default expiry = **30 days** (vs bound SA token's 1 hour — don't mix up)
- `usages: [client auth]` is mandatory
- `signerName` must be `kubernetes.io/kube-apiserver-client` for this use case

## 6. kubeconfig File Structure

| Section | Contains |
|---|---|
| `clusters` | `server` (API URL), `certificate-authority` |
| `users` | EITHER `token` OR `client-certificate` + `client-key` (never both) |
| `contexts` | combo of `cluster` + `user` + `namespace` |

```yaml
apiVersion: v1
clusters:
- cluster:
    server: https://api.ocp4.prod.com:6443
    name: production
users:
- name: admin-production
  user:
    token: REDACTED
contexts:
- context:
    cluster: production
    namespace: prod-app
    user: admin-production
  name: prod-app/api-ocp4-prod-com:6443/admin-production
current-context: prod-app/api-ocp4-prod-com:6443/admin-production
kind: Config
```

```bash
oc config view          # token shown truncated
oc config view --raw    # shows actual token value
```

**File lookup priority (highest wins):**
1. `--kubeconfig` flag
2. `KUBECONFIG` env var
3. Default `~/.kube/config`

**Gotcha:** If edits seem "ignored," check whether `KUBECONFIG` env var is silently pointing elsewhere.

## 7. Configuring CLI Profiles — `oc config` subcommands

| Subcommand | Edits |
|---|---|
| `set-cluster` | `clusters:` |
| `set-credentials` | `users:` |
| `set-context` | `contexts:` |
| `use-context` | `current-context` |

- `--kubeconfig=<file>` → maintain a separate kubeconfig file instead of touching default
- **Gotcha:** These are pure CRUD writes to YAML — **no validation against the cluster**. A bad token/URL "succeeds" silently; failure only shows up later when you actually run a command.

## 8. User Impersonation

**Admin testing another user's RBAC access:**
```bash
oc auth can-i <verb> <resource> --as <user> --as-group <group>
oc auth can-i --list --as <user>     # dump all permissions
```
`-n <project>` for one project, `-A` for all.

**Granting a regular user impersonation rights — custom ClusterRole:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: sudo-admin
rules:
- apiGroups: [""]              # core API group = empty string
  resources: ["users"]
  verbs: ["impersonate"]
  resourceNames: ["admin"]     # restricts WHO can be impersonated
```
```bash
oc create clusterrolebinding binding_name \
  --clusterrole sudo-admin --user regularuser
```
Usage:
```bash
oc get nodes --as admin
```

**Gotchas:**
- `apiGroups: [""]` — empty string = core group, not omitted/named
- `resourceNames: ["admin"]` restricts impersonation to just that identity — omitting it = impersonate *anyone* (much bigger privilege grant)
- To impersonate an SA: `--as system:serviceaccount:<project>:<sa-name>`
- Impersonation denial just shows as standard `Forbidden` — check the impersonate ClusterRoleBinding exists before assuming a syntax bug

## Lab Command Log (this session)

```bash
oc adm policy add-cluster-role-to-user cluster-reader \
  -z health-robot -n auth-tls
```
**Why this matters / doubt resolved:**
- `-z` works with `add-cluster-role-to-user`, not just `add-role-to-user` — same `oc adm policy` family.
- `-z` only supplies the **short SA name**; namespace resolution depends on **current project context** unless `-n <project>` is explicitly passed.
- **Gotcha:** Running `-z` from the wrong current project either binds the wrong SA (if one with that name exists there) or errors — silently produces wrong result if you're not paying attention to context. Since `add-cluster-role-to-user` creates a **ClusterRoleBinding** (cluster-scoped) referencing a **namespace-scoped** SA, getting `-n` right matters even more.

## Quick-Reference: Default Values Cheat Table

| Item | Default |
|---|---|
| Bound SA token (volume projection) expiry | 3600s (1 hr) |
| Token auto-rotation trigger | 80% of TTL, or >24h old |
| `oc create token` default duration | 1 hour |
| CSR `expirationSeconds` (client cert) | 30 days (604800s) |
| Pod with no `serviceAccountName` | uses `default` SA (no elevated perms) |
