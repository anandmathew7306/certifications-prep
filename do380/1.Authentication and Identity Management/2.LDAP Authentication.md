## 1. Core Concept
LDAP is a **query protocol**, not a directory product. AD, Red Hat IdM, and 389-ds/RHDS all *expose* an LDAP interface. OpenShift's OAuth server speaks LDAP to authenticate users against whichever directory sits behind it.

**Auth flow:**
1. User submits username/password.
2. OAuth server binds to LDAP using the configured **service account** (`bindDN` + `bindPassword`).
3. Searches for a **unique match** using `basedn` + `filter` (built from the CR's `url`).
4. Match found → user's actual password is verified against that entry → `Identity`/`User` binding created.
5. No match / multiple matches → **auth fails outright**, no fallback, no partial binding.

> ⚠️ **Auth ≠ Authorization.** Successful LDAP login only proves identity. RBAC roles must be granted separately (`oc adm policy add-role-to-user ...`) or the user gets "forbidden" everywhere despite logging in fine.

> ⚠️ Group sync (mirroring LDAP groups into OpenShift `Group` objects via a cron job) is a **separate, additional** configuration — not covered by IdP setup alone.

## 2. LDAP URI Syntax
```
ldap://host:port/basedn?attribute?scope?filter
```

| Component | Meaning | Default |
|---|---|---|
| `ldap`/`ldaps` | Protocol (ldaps = SSL) | Red Hat recommends **StartTLS over plain ldap** |
| `host:port` | Server address | `ldap`→389, `ldaps`→636 |
| `basedn` | Root of the search | required, no default |
| `attribute` | What to return | `uid` |
| `scope` | `one` or `sub` | `sub` |
| `filter` | Narrows results | `(objectClass=*)` |

**Example:**
```
ldap://ldap.example.com:389/dc=example,dc=com?givenName,sn,cn?(uid=paula.tomcheck)
```

### Distinguished Name (DN) — the "full path" to one entry
Read **right to left**, general → specific:
```
uid=ptomchek,ou=users,dc=ocp4,dc=redhat,dc=com
```
| Piece | Meaning |
|---|---|
| `dc` | Domain Component (root, e.g. split of ocp4.redhat.com) |
| `ou` | Organizational Unit (a "folder"; not mandatory — only present if that layer exists in the real tree) |
| `cn` | Common Name (display/entry name — may not be unique) |
| `uid` | User ID (meant to be unique, login-style identifier) |

> 💡 A DN has exactly as many layers as that entry's real location in the tree — no `ou` doesn't mean it's wrong, it means that entry sits directly under the domain.

## 3. `ldapsearch` — CLI validation tool
Package: **`openldap-clients`**. Use this to confirm credentials/query logic *before* wiring into the OAuth CR — same basedn/filter/attributes will go into the CR's `url` later.

```bash
ldapsearch -x -D bind_dn -H ldap_host_URI -b search_base \
  --filter filter --requestedAttribute attributes -W
```

| Flag | Meaning |
|---|---|
| `-x` | Simple authentication |
| `-D` | Bind DN (service account identity) |
| `-W` | Prompt for password interactively (safe, not in shell history) |
| `-w password` | Inline password (used in lab — visible in history/process list, fine for quick testing only) |
| `-H` | LDAP server URI |
| `-b` | Search base |
| `--filter` / `--requestedAttribute` | Narrow the query |

### Reading `ldapsearch` output (from lab)
```
numEntries: 3   ← total entries returned, NOT necessarily "users"
```
A subtree search (`sub`, the default) returns:
- The **base/container entry itself** (e.g. `ou=people,...`, objectClass `organizationalUnit`)
- Any **user entries** (objectClass `account`/`posixAccount`; `uid=...`)
- Any **group entries** (objectClass `groupOfUniqueNames` with `uniqueMember`, or `groupOfNames` with `member`, or POSIX `posixGroup` with `memberUid`)

`memberOf` on a user = reverse-linked group membership (RHDS/389-ds feature via `nsMemberOf` objectClass) — useful to eyeball group assignment without a separate group query.

`userPassword:: <base64>` — the `::` is standard LDIF notation for base64-encoded values, not a special flag.

`result: 0 Success` = query ran fine; doesn't mean "user found" — check `numEntries` and actual `dn:` lines.

## 4. Supporting Resources (namespace: `openshift-config`)

### bindPassword Secret
Stores the service account's password so it's never inline in the OAuth CR.
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: ldap-secret
  namespace: openshift-config
type: Opaque
data:
  bindPassword: <base64-encoded-password>
```
Ad-hoc equivalent:
```bash
oc create secret generic ldap-secret \
  --from-literal=bindPassword=<password> \
  -n openshift-config
```
> ⚠️ Cluster admins can read this secret. Use a **limited-permission LDAP service account**, not a full directory admin, as the bind identity.

### CA ConfigMap (only if using ldaps/StartTLS with a private CA not in default trust store)
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ca-config-map
  namespace: openshift-config
data:
  ca.crt: |
    <CA_certificate_PEM>
```
Public info (CA cert) → **ConfigMap**, not Secret. Sensitive info (password) → **Secret**.

> Only the **keys** (`bindPassword`, `ca.crt`) are fixed. Resource **names** are arbitrary but must match what the OAuth CR references.

## 5. OAuth CR — LDAP IdP Block
```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster              # singleton — always this name
spec:
  identityProviders:         # ⚠️ LIST — append, never replace
  - name: ldapidp             # shown on login screen
    mappingMethod: claim      # auto-creates User on first login
    type: LDAP
    ldap:
      attributes:
        id:
        - dn                 # required — unique identity key
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - uid                # becomes the OpenShift username
      bindDN: 'cn=administrator,dc=example,dc=com'
      bindPassword:
        name: ldap-secret     # must match Secret name in openshift-config
      ca:
        name: ca-config-map   # must match ConfigMap name (omit if not needed)
      insecure: false
      url: "ldaps://ldaps.example.com/ou=users,dc=acme,dc=com?uid"
```

### Field cheat-sheet
| Field | Notes |
|---|---|
| `metadata.name: cluster` | Only ever one OAuth CR — you edit it, never create new |
| `identityProviders` | **Additive list** — replacing it risks locking yourself out |
| `mappingMethod: claim`/`add` | Auto-creates `User` object on first successful login (still 0 permissions) |
| `attributes.id` | Required, ≥1 non-empty value or auth fails |
| `bindDN` + `bindPassword` | Paired — must both be set unless anonymous bind allowed |
| `ca.name` | Only used when `insecure: false` |
| `insecure: true` | No TLS at all — **contradiction** if `url` uses `ldaps://` (ldaps always attempts TLS) |
| `url` | Combined with user-entered username at login to build the search filter |

## 6. Exam Gotchas — Quick Recall List
- Default ports: `ldap`→**389**, `ldaps`→**636**
- Default scope: **`sub`** (not `one`) if omitted
- Default filter: **`(objectClass=*)`** if omitted
- Red Hat recommends **StartTLS over plain ldap** (not "always use ldaps")
- `insecure: true` + `ldaps://` url = **invalid/contradictory config**
- `identityProviders` in OAuth CR is **additive** — never blindly overwrite
- No unique LDAP match → **flat auth failure**, no partial state — debug via `ldapsearch` with same basedn/filter, not RBAC
- Successful LDAP login ≠ cluster permissions — RBAC is a **separate manual step**
- Group sync (cron-based) is **not** part of basic IdP config — separate section
- `-W` (prompt, safe) vs `-w password` (inline, visible in history) — know the difference
- `ou=` in a DN is **not mandatory** — DN just reflects the real tree depth for that entry
- Secret → sensitive data (`bindPassword`); ConfigMap → non-sensitive data (`ca.crt`) — both live in `openshift-config`

## 7. Lab Commands Actually Used
```bash
ldapsearch -D "cn=Directory Manager" \
  -w redhatocp \
  -H ldaps://rhds.ocp4.example.com \
  -b "ou=people,dc=example,dc=com"
```
Confirmed: 1 container (`ou=people`) + 1 user (`kristendelgado`, member of `administrators` group) + 1 group (`administrators`) = 3 entries total — validated directory connectivity and structure before OAuth CR configuration.
