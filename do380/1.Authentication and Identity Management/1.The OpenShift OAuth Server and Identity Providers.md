## 1. Why OpenShift Needs Its Own OAuth Server
- Kubernetes can **validate** a cert/token but has **no login mechanism** — no way to issue credentials.
- OpenShift bolts on an internal **OAuth server** (run by the **authentication operator**) to fill that gap.
- Two independent ways into a cluster:
  - **X.509 client certs** — identical to vanilla K8s, needs HTTPS to API server.
  - **OAuth access tokens** — OpenShift-specific; issued after authenticating against a configured IdP.
- OAuth server only supports a **fixed list of IdP types** (LDAP, OIDC, htpasswd, GitHub, etc.) — can't plug in arbitrary custom IdPs.

**Why this matters:** Cert-auth completely bypasses OAuth. A user can be "authenticated" two totally different ways — this distinction resurfaces in system groups and in `system:admin` vs `kubeadmin`.

## 2. `oc login` Flow (5 steps)
1. User runs `oc login -u user -p pass https://api.cluster:6443`
2. `oc` sends creds to the **internal OAuth server**
3. OAuth server checks creds against configured **IdP**
4. OAuth server issues an **OAuth access token**
5. Token stored in **kubeconfig** (`~/.kube/config` by default)

- Two separate endpoints involved: **API server** + **OAuth server route** — this is why the web console makes you accept two certs on first login.
- Debug the two endpoints: `oc login ... --loglevel 7`
- Skip OAuth server entirely with an existing token:
  ```
  oc login --token=<TOKEN>
  ```
- Console stores token in **browser memory**; CLI persists it to **kubeconfig on disk**.

## 3. The `OAuth` Custom Resource
```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster              # singleton — always "cluster"
spec:
  identityProviders:
    - name: htpasswd-idp-name
      mappingMethod: claim
      type: HTPasswd
      htpasswd:
        fileData:
          name: htpasswd-secret   # actual creds live in a Secret, not inline
    - name: ldap-idp-name
      mappingMethod: claim
      type: LDAP
      ldap:
        ...
```
- `identityProviders` = array → multiple IdPs supported (common: htpasswd break-glass admin + LDAP for real users).
- `name` → prefixes the identity's username to form the full **identity name**; also used to build the redirect URL.
- `type` → determines expected sub-block (`htpasswd:`, `ldap:`, etc.)

**Gotchas:**
- Editing this CR triggers an **OAuth pod rollout** via the authentication operator — expect delay, not instant effect.
- Only ever **one** `OAuth` CR (`name: cluster`) — same pattern as `Ingress`, `Network` CRs.

## 4. User / Group / Identity Resources (OpenShift-only)
> Plain Kubernetes has **no persisted objects** for users/groups — just strings read live off certs/tokens per-request. (ServiceAccount is the one exception — that IS a real K8s object.)

OpenShift adds three real, stored API resources:

| Resource | What it is | Auto-created on login? |
|---|---|---|
| `User` | The account | Yes (any IdP) |
| `Identity` | Record linking an external IdP login → internal User | Yes (any IdP) |
| `Group` | Named collection of Users | **OIDC: yes** / **LDAP & most others: no — manual** |

- **IdP ≠ Identity.** IdP = external system doing the check (config inside the `OAuth` CR). Identity = internal OpenShift resource recording a successful check against that IdP.

**Why this matters:** LDAP not auto-creating Groups is *the entire reason* "LDAP Group Synchronization" exists as its own topic/exercise later. If group-based RBAC isn't working after LDAP login → check group sync first, not RBAC bindings.

## 5. System Groups (built-in, virtual — not `Group` objects)

| System group | Meaning |
|---|---|
| `system:unauthenticated` | No valid cert/token presented |
| `system:authenticated` | **Any** successful auth, any method |
| `system:authenticated:oauth` | Successful auth **specifically via OAuth token** (narrower than above) |
| `system:masters` | Full cluster-admin, no exceptions |

**Exam trap:** `system:authenticated` vs `system:authenticated:oauth` — a client-cert or ServiceAccount-authenticated request is `system:authenticated` but **NOT** `system:authenticated:oauth`. Check which one an RBAC binding actually references.

## 6. `mappingMethod` — Handling Multi-IdP Username Collisions

| Value | Auto-creates User? | On username collision |
|---|---|---|
| `claim` (**default**) | Yes | **Fails** |
| `add` | Yes | **Merges** into existing user |
| `lookup` | No | Nothing automatic — admin must pre-provision |

- Forgetting to set it → silently defaults to `claim` → unexpected login failures when you actually wanted `add`-style merging.
- `add` merges purely by **username string match** — no identity verification, it's a trust decision the admin makes.
- Directly the mechanism behind the later **"Solve User Sync Conflicts"** guided exercise.

## 7. Cluster Bootstrap Auth: `kubeadmin` vs `system:admin`

| | `kubeadmin` | `system:admin` |
|---|---|---|
| Auth method | OAuth (password) | Client certificate |
| Lifespan | Temporary — delete after setup | Permanent break-glass |
| Where creds live | Random password from install output | kubeconfig file from install |
| Exists on ROSA/OSD? | **No** (cloud console handles admin access) | — |

**Safe removal sequence:**
1. Configure a real IdP in `OAuth` CR
2. Confirm a user gets `cluster-admin` through that IdP
3. Only then:
   ```
   oc delete secrets kubeadmin -n kube-system
   ```
4. Keep `system:admin` kubeconfig safe as permanent recovery path.

**Gotcha:** Deleting `kubeadmin` before step 2 = **irreversible**, may require full cluster reinstall. ROSA/OSD scenarios mentioning `kubeadmin` = likely a distractor (doesn't exist there).

## Quick Command Reference
```bash
# Login with verbose endpoint debug
oc login -u user -p password https://api.ocp4.example.com:6443 --loglevel 7

# Login with existing token (skips OAuth server contact)
oc login --token=<TOKEN>

# List OpenShift-specific auth resources
oc get users
oc get groups
oc get identities

# Remove kubeadmin (ONLY after real admin IdP user confirmed)
oc delete secrets kubeadmin -n kube-system
```
