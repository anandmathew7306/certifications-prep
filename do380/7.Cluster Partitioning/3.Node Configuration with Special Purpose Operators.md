## Core Concept

Special purpose operators handle higher-level, specialized node configuration that the Machine Config Operator (MCO) doesn't cover well. The **Node Tuning Operator (NTO)** manages the `tuned` daemon as a **daemonset** (one pod per node), running in the `openshift-cluster-node-tuning-operator` namespace.

Config flow: you write a **Tuned CR** → NTO watches it → matches nodes by label → applies the specified TuneD profile to those nodes.

---

## Key Commands

```bash
# Recon
oc get nodes                          # check node role labels
oc project openshift-cluster-node-tuning-operator
oc get daemonsets                     # tuned daemonset (one pod/node)
oc get pods -o wide                   # confirm pod-per-node spread
oc get profile                        # applied TuneD profile per node
oc get tuned default -o yaml          # default recommend rules

# Check a kernel setting live on a node
oc debug node/<nodename> -- cat /sys/kernel/mm/transparent_hugepage/enabled

# Apply a custom Tuned profile
oc apply -f <file>.yaml
```

## Custom Tuned CR Template

```yaml
apiVersion: tuned.openshift.io/v1
kind: Tuned
metadata:
  name: <profile-name>
  namespace: openshift-cluster-node-tuning-operator
spec:
  profile:
  - name: <custom-profile-name>
    data: |
      [main]
      summary=<description of what this profile does>
      include=openshift-node        # base profile to inherit from
      [vm]
      transparent_hugepage=never    # example tunable, under the vm plug-in
  recommend:
  - match:
    - label: <node-role-label-to-target>
    priority: 30                    # lower number = higher precedence
    profile: <custom-profile-name>
```

---

## Why This Matters

- **`include=`** — always base custom profiles on an existing one (`openshift-node` / `openshift-control-plane`) instead of writing from scratch. You inherit the base settings and only override what you need.
- **Priority** — when a node matches multiple Tuned profiles, the **lowest priority number wins**. A custom profile's priority must be *lower* than whatever it's currently matching, or it silently loses.
  - Defaults: control-plane/infra nodes → `openshift-control-plane` (priority 30); everything else → `openshift-node` (priority 40).
- **`match.label`** — this matches a **node label**, not a pod NodeSelector. Easy to conflate the two under exam pressure.
- **`oc debug node/<x> -- cat ...`** output format — the currently active value is shown in `[brackets]` (e.g. `always madvise [never]`).

---

## Exam Gotchas

- Namespace name is long and easy to fat-finger: `openshift-cluster-node-tuning-operator`.
- Priority logic is **inverted** from intuition — lower number = takes precedence, not higher.
- Forgetting `include=` means the custom profile won't inherit sane defaults from the base profile.
- Forgetting to lower the priority below the currently-applied profile means the Tuned CR gets created but never actually applies.

## Other Special Purpose Operators (overview only)

- **Node Feature Discovery (NFD) Operator** — `openshift-nfd` namespace. Auto-labels nodes with detected hardware info (CPU architecture, PCI devices, GPUs, etc.) so workloads can target nodes with specific hardware via labels.
- **Kernel Module Management (KMM) Operator** — `openshift-kmm` namespace. Builds/signs/deploys out-of-tree kernel modules via a `Module` CR, packaged in container images. Common for AI/ML custom driver workloads. Security-sensitive — kernel modules run with full host privilege.
- **Vendor-provided operators** — hardware vendors (NVIDIA, Intel, IBM, etc.) sometimes ship their own OperatorHub operators for their specific hardware. Availability varies by vendor/cluster.
