## Core Idea

OpenShift nodes run RHCOS. You should never manually edit OS-level config on a
node (SSH + edit file) — the MCO will detect it as drift and fight you.
Everything OS-level goes through the MCO as a declarative object.

## The Two Objects

Think mail-merge:

- **MachineConfig (MC)** — the letter content. "Change this file / kernel arg /
  systemd unit to this."
- **MachineConfigPool (MCP)** — the mailing list. "These nodes should receive
  MCs with this label."

They connect purely through **labels**:
- MC carries a label, e.g. `machineconfiguration.openshift.io/role: worker`.
- MCP selects MCs by that label (`machineConfigSelector`) **and** selects
  nodes by a node label (`nodeSelector`).
- MCP merges all matching MCs into one **rendered config** and pushes it to
  its nodes.

MC alone does nothing — it just sits there labeled. MCP is what activates it.

## MCO Components (quick reference)

| Component | Role |
|---|---|
| MCO deployment | Main operator, manages the rest |
| MCD (daemon, per node) | Detects change → drains pod → applies → reboots |
| MCC | Orchestrates rollout from control plane |
| MCS | Serves Ignition config to nodes at boot |

## Butane

Just a convenience compiler: write plain YAML, it produces the real MC
(handles base64 encoding of file contents for you). Not a new concept —
just tooling.

```
butane <file>.bu -o <file>.yaml
oc create -f <file>.yaml
```

## Rollout Lifecycle

1. MCP notices a matching MC changed → re-renders combined config.
2. Nodes in that pool get a new "desired config."
3. MCD drains the node, applies, reboots.
4. Node reports back done.

Check progress via node annotations:
- `currentConfig` vs `desiredConfig` — mismatch = mid-update (`state: Working`)
- Match = `state: Done`

## Custom MachineConfigPools

Default pools: `master`, `worker`. Create a **custom pool** when a subset of
workers needs *extra* config beyond the baseline.

**Key rule:** the custom pool's MC selector must include **both** `worker`
AND your custom label — not just custom. Otherwise those nodes stop getting
baseline worker MCs (kubelet, container runtime, etc.) entirely.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: custom
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values: [worker, custom]   # both, not just custom
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/custom: ""
```

**Exam gotchas:**
- A worker node can belong to only **one** custom pool at a time.
- A master node can **never** belong to a custom pool.
- Breaking either rule does *not* throw a loud CLI error — MCO silently
  skips it; check MCC pod logs to catch this.
- MCs are read alphanumerically `00-*` to `99-*`. Higher number wins on
  conflict. Same number → last alphabetically wins.

## Configuration Drift

**Drift** = the file on disk no longer matches what the currently rendered
MC says it should be.

Checked at: node boot, whenever an MC-managed file changes outside MCO, or
right before applying a new MC.

On detection, MCO does **not** auto-heal — it flags and stops:
- Logs an error + fires a Kubernetes event
- Marks node **and** pool `Degraded`
- Stops further drift checks on that node until fixed

Node stays online/operational while degraded — it just won't accept new
updates.

**Two remediation paths:**

| Method | What it does | Reboot? |
|---|---|---|
| **Rewrite** | Manually fix the file back to match the MC | No — no downtime |
| **Generate** (force file) | Drop `/run/machine-config-daemon-force` on node → skips validation, reapplies current MC | Yes — riskier |

## Useful Commands Learned

```bash
# Run one command inside a node's real filesystem without a full shell
oc debug node/<node> -- chroot /host <command>

# Watch MCO events for a specific MC/MCP
oc get events -n openshift-machine-config-operator \
  --sort-by='{.lastTimestamp}' \
  --field-selector involvedObject.name=<name>

# List MCs / MCPs
oc get machineconfig --selector machineconfiguration.openshift.io/role=<role>
oc get mcp
```

## MCO-related CRs (fast pass — not deep-dived this round)

- **KubeletConfig** — edit kubelet params (e.g. `maxPods`, `podPidsLimit`)
  via a supported API instead of raw MC. Auto-restores default if deleted.
- **ContainerRuntimeConfig** — edit CRI-O settings (`logLevel`, `overlaySize`,
  `defaultRuntime`) similarly.
- Both target an MCP via `machineConfigPoolSelector` label match.
