## Core Concept

Logging for OpenShift collects and aggregates logs from pods and nodes, then can forward them
to an external aggregator (syslog, Splunk, Kafka, CloudWatch, etc.) or store them internally.
Forwarding offloads cluster disk/compute and satisfies long-term storage / compliance needs.

**Architecture (3 components, deployable independently):**

| Component | Tool | Notes |
|---|---|---|
| Collector | **Vector** (replaced Fluentd) | Runs as a DaemonSet — one pod per node, incl. control-plane (tolerates the master `NoSchedule` taint by default) |
| Log Store | **Grafana Loki** (replaced Elasticsearch) | Optional — skip it entirely if only forwarding externally |
| Visualization | Cluster Observability Operator console plugin | Separate operator from cluster-logging; only relevant if using internal Loki |

> **Why this matters:** you can deploy the collector *alone*, with no internal store — a
> perfectly valid architecture (this is what the guided exercise does: syslog-only, no Loki).

---

## Log Categories (built-in inputs — no need to declare them)

| Input name | Contains |
|---|---|
| `infrastructure` | Container logs from `openshift-*`, `kube*`, `default` namespaces + node system/journal logs |
| `audit` | Kubernetes API audit logs, OpenShift API audit logs, **and** Linux (`auditd`) logs from nodes — all in one input/pipeline. **Not stored by default**, must be explicitly forwarded. |
| `application` | All container logs from user projects |

> **Gotcha:** node-level Linux audit events (e.g. SSH `USER_LOGIN`) and Kubernetes API audit
> events both flow through the same `audit` input — expect mixed JSON shapes in one stream,
> not two separate pipelines.

## Install & RBAC

Operator install (OperatorHub or OLM via `oc`) creates the cluster-logging operator in
`openshift-logging`. The operator does nothing until you supply a `ClusterLogForwarder` CR —
installing it just makes the CRD available.

Collector needs a dedicated **ServiceAccount** bound to logging-specific ClusterRoles
(provided by the operator, not authored by you):

```bash
oc create serviceaccount log-collector

oc adm policy add-cluster-role-to-user collect-audit-logs -z log-collector
oc adm policy add-cluster-role-to-user collect-infrastructure-logs -z log-collector
oc adm policy add-cluster-role-to-user collect-application-logs -z log-collector
```

> **Why this matters:** least-privilege design — bind only the roles matching the inputs your
> pipelines actually reference. Missing role + referenced input = CR reports `ClusterRoleMissing`.

## ClusterLogForwarder Anatomy

Single CR (`observability.openshift.io/v1`) describing the whole pipeline. Applying/editing it
triggers the operator to (re)deploy the Vector DaemonSet — **same name as the CR**.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: <forwarder-name>
  namespace: openshift-logging
spec:
  managementState: Managed        # tells operator to actively reconcile this CR
  serviceAccount:
    name: <sa-name>
  inputs:      # optional — only needed for filtered/custom subsets
    - name: <custom-input-name>
      type: application
      application:
        selector:
          matchLabels:
            <label-key>: <label-value>
  outputs:
    - name: <output-name>
      type: <output-type>         # syslog | splunk | lokiStack | cloudwatch | kafka ...
      <type>:
        url: <destination-url>
        # ...type-specific auth/config
  pipelines:
    - name: <pipeline-name>
      inputRefs:
        - <input-name-or-builtin>
      outputRefs:
        - <output-name>
```

- **inputs** — *what* to collect. Use built-ins (`audit`, `infrastructure`, `application`)
  directly by name, or declare a custom input to filter.
- **outputs** — *where* to send it.
- **pipelines** — *routing* from input(s) to output(s). Multiple pipelines allowed in one CR.

## Syslog Output (plain-language + fields)

Syslog = a universal, decades-old "send a log line to a listening server" protocol — the
lowest common denominator that virtually every logging tool can ingest. No auth required,
unlike Splunk (token-based) or cloud-native outputs.

```yaml
outputs:
  - name: <output-name>
    type: syslog
    syslog:
      url: tcp://<syslog-host>:<port>   # tcp:// or udp:// — must match receiver's protocol
      msgId: <tag>                      # receiver commonly routes/files logs by this tag
      appName: <app-tag>                # optional
      facility: local0                  # optional
      procId: <proc-tag>                # optional
      severity: informational           # optional
      rfc: RFC5424                      # RFC5424 = structured modern format, RFC3164 = legacy
```

Other output types follow the same skeleton (`name` / `type` / type-specific block), just
swap auth style:
- **Splunk** — HEC token via `secretName`, for orgs with existing Splunk dashboards.
- **Kafka** — logs land in a topic; a downstream consumer processes them further (streaming pipeline, not a viewer).
- **CloudWatch / Google Cloud Logging** — cloud-native destinations, useful if cluster runs on that cloud.
- **lokiStack (internal)** — no external system, plugs straight into the OpenShift console.

> **Gotcha:** protocol mismatch (`tcp://` vs receiver expecting UDP) validates fine in the CR
> but silently drops logs — always confirm with collector pod logs, not just CR status.

## Filtering — Custom Inputs

Default `application` input = every user project. Scope it down with a custom input:

```yaml
inputs:
  - name: critical-apps
    type: application
    application:
      selector:
        matchLabels:
          <label-key>: <label-value>
      includes:                 # optional — further restrict to specific namespaces
        - namespace: <ns-1>
        - namespace: <ns-2>
```

> **Gotcha:** a custom input **replaces** the generic `application` input for that pipeline —
> it doesn't add to it. `matchLabels` needs an exact, case-sensitive match; a typo'd label
> value silently forwards nothing, with no CR error.

## Event Router (Kubernetes Events)

Kubernetes events (pod scheduled, image pulled, etc.) live in the API, not container stdout —
Vector can't collect them natively. Event Router bridges this: watches the event API, re-emits
events as its own container's stdout, which Vector then collects normally.

```bash
oc process -f eventrouter.yaml | oc apply -f -
```

- **Not operator-managed** — independent lifecycle from the `ClusterLogForwarder` CR (deleting one doesn't affect the other).
- Because Event Router's pod lives in `openshift-logging` (an `openshift-*` namespace), its
  output automatically falls under the **`infrastructure`** log category — no dedicated
  input/pipeline needed for Kubernetes events.

## Troubleshooting Log Forwarding

Two-step diagnostic order:

```bash
# 1. Check CR status — is it Ready? If not, why?
oc -n openshift-logging describe clusterlogforwarder/<name>

# 2. If Ready but no data arrives — check the collector itself
oc -n openshift-logging logs daemonset/<name>
```

| Status message | Reason | Fix |
|---|---|---|
| `refs not found: outputs[...]` | `ValidationFailure` | Typo/missing output name in pipeline — pure YAML consistency bug |
| `insufficient permissions ... not authorized to collect [...]` | `ClusterRoleMissing` | Missing `oc adm policy add-cluster-role-to-user` binding |
| CR is Ready, no errors, but no data at destination | — | Check collector pod logs for Vector healthcheck errors (`Connection refused` etc.) — network/protocol issue, not CR config |

> **Why this matters:** matching the **Reason** field to the right fix category is faster
> than guessing — `ValidationFailure` ≠ RBAC problem ≠ network problem.

## Condensed — Topics Not in the Guided Exercise

- **Loki (internal log store)** — optional, referenced via `type: lokiStack` output, needs
  target name/namespace + service-account token auth + `service-ca.crt` for TLS.
- **Visualization plugin** — provided by the *Cluster Observability Operator*, a **separate**
  operator from cluster-logging. Installing logging alone does not give you console log search.
- **Collector DaemonSet tuning** — add tolerations under `spec.collector.tolerations` to run
  the collector on dedicated infra nodes (beyond the default master-taint toleration).
- **Audit filters (`kubeAPIAudit`)** — drop noisy/low-value audit events before forwarding.
  Same rule syntax as native Kubernetes audit policy (`level`, `namespaces`, `userGroups`,
  `users`, `verbs`, `resources`). Applied to a pipeline via `filterRefs`.
- **Monitoring dashboard** — enable via `openshift.io/cluster-monitoring: true` label on
  `openshift-logging`; view forwarding rate / per-app log rate under **Logging / Collection**.
  Optional `LogFileMetricExporter` CR adds a "Produced Logs" panel for spotting noisy apps.

## Exam Gotchas — Consolidated

- Old docs/UI may still say "OpenShift Logging" / Fluentd / Elasticsearch — current stack is Vector + Loki (know both names).
- Namespace is always `openshift-logging` — hardcoded everywhere (SA, CR, DaemonSet).
- Audit logs are **not stored by default** — must be explicitly forwarded.
- Node-level Linux audit + Kubernetes API audit share **one** `audit` input — not split.
- Priority/logic aside — for CLF, a **custom application input replaces**, doesn't add to, the built-in one.
- `matchLabels` is exact-match only, case-sensitive — silent zero-match on typo, no CR error.
- Syslog protocol (`tcp://` vs `udp://`) mismatch = silent drop, only visible in collector pod logs.
- Event Router lifecycle is fully decoupled from the CLF CR.
- `ValidationFailure` (bad YAML refs) vs `ClusterRoleMissing` (bad RBAC) vs silent network failure = three distinct failure domains, diagnosed differently.
