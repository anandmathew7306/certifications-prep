## 1. Why Centralized Logging Exists

- Kubernetes pod logs live on local node disk → **ephemeral**. Lost on pod GC or node restart (e.g. after updates).
- Centralized logging decouples log lifetime from pod lifetime.
- **Gotcha:** "~1 week" is informal guidance for retention. **Hard supported ceiling: 30 days max** for Loki-stored logs, regardless of what `retention.days` is set to.

## 2. Architecture — 3 Separate Operators, 3 Separate CRs

| Concern | Operator | Key CR |
|---|---|---|
| Storage | Loki Operator | `LokiStack` |
| Collection / routing | Cluster Logging Operator | `ClusterLogForwarder` |
| Visualization (console UI) | Cluster Observability Operator (COO) | `UIPlugin` |

- Cluster Logging Operator does **not** auto-deploy Loki — install separately.
- COO ≠ default Cluster Monitoring Operator (CMO). COO is optional/pluggable; only the logging plug-in is used here.
- **Loki design point:** indexes only a few fixed labels at ingestion, compresses log content into chunks in object storage. This is why LogQL queries filter by label first, then content — and why S3-compatible storage is mandatory, not optional.

**Dependency chain:** `UIPlugin` → `LokiStack` → (bucket secret → S3 bucket). `ClusterLogForwarder` → `LokiStack` (separately). Break any link, nothing shows in the console.

## 3. Object Storage for Loki (ODF example)

```bash
oc apply -f objectbucket.yaml          # kind: ObjectBucketClaim
oc get obc                              # verify Bound phase
```

ODF/NooBaa auto-creates, from the OBC name:
- **ConfigMap** → `BUCKET_HOST`, `BUCKET_NAME`, `BUCKET_PORT`, region fields
- **Secret** → `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`

```bash
oc extract secret/<obc-name> --to - -n openshift-logging   # quick dump of creds
```

**Repackage into the secret Loki actually expects** (field names differ!):

```bash
oc create secret generic logging-loki-odf \
  --from-literal=access_key_id=<ACCESS_KEY_ID> \
  --from-literal=access_key_secret=<SECRET_ACCESS_KEY> \
  --from-literal=bucketnames=<BUCKET_NAME> \
  --from-literal=endpoint=https://<BUCKET_HOST>:<BUCKET_PORT>
```

**Gotchas:**
- `AWS_ACCESS_KEY_ID` (OBC secret) ≠ `access_key_id` (Loki secret) — mismatch = auth failure, unhelpful crash loops.
- `bucketnames` is **plural**.
- `endpoint` needs full scheme + port, not just host.
- OBC storage class (`openshift-storage.noobaa.io`) is **not** the same as the `LokiStack.spec.storageClassName` used later (block storage, e.g. `ocs-external-storagecluster-ceph-rbd`) — two different storage purposes.

## 4. LokiStack CR

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  limits:                                  # optional — controls retention
    global:
      retention:
        days: 20
        stream:
          - days: 4
            priority: 1
            selector: '{kubernetes_namespace_name=~"test.+"}'
  size: 1x.demo                            # 1x.demo / 1x.small / 1x.medium — real CPU/mem/replica impact
  storage:
    secret:
      name: logging-loki-odf               # from Section 3
      type: s3
    tls:
      caName: openshift-service-ca.crt     # ODF/internal endpoint trust
  storageClassName: ocs-external-storagecluster-ceph-rbd   # Loki's own WAL/local storage, NOT the bucket
  tenants:
    mode: openshift-logging                # ties Loki into OpenShift RBAC — required for view-role RBAC (Sec. 7)
```

```bash
oc apply -f lokistack.yaml
watch oc get pods     # compactor, distributor, gateway, ingester, querier, query-frontend, index-gateway
```

**Why this matters:** central point of failure to check first if logs don't flow — bad secret ref or storage class here breaks everything downstream silently.

**Gotchas:**
- Retention has **two independent knobs**: `LokiStack.spec.limits.global.retention` vs S3 bucket lifecycle policy. Red Hat recommends the **object-storage-level** policy for efficiency.
- **By default Loki prunes nothing** — no cleanup unless one of the two above is configured.
- 30-day support ceiling applies regardless of configured value.
- Exam lab YAML often **omits `limits` entirely** — understand it conceptually, but don't assume every task requires it.

## 5. Collector Service Account + Cluster Roles

```bash
oc create serviceaccount log-collector

oc adm policy add-cluster-role-to-user collect-audit-logs -z log-collector
oc adm policy add-cluster-role-to-user collect-infrastructure-logs -z log-collector
oc adm policy add-cluster-role-to-user collect-application-logs -z log-collector
oc adm policy add-cluster-role-to-user logging-collector-logs-writer -z log-collector
```

- First three = permission to **gather** each log type.
- Last one = permission to **write** to Loki.
- **Do not confuse with the `-view` roles (Section 7)** — collection roles (write-side, bound to SA) vs view roles (read-side, bound to users/groups) are separate authorization boundaries.
- Missing one collect-role = partial silent log loss (e.g. audit logs missing, no obvious error).

## 6. ClusterLogForwarder CR

```yaml
apiVersion: observability.openshift.io/v1     # new decoupled API (Logging 6.x) — not the old logging.openshift.io/v1 ClusterLogging monolith
kind: ClusterLogForwarder
metadata:
  name: to-loki
  namespace: openshift-logging
spec:
  serviceAccount:
    name: log-collector
  outputs:
    - name: loki
      type: lokiStack                         # built-in type for talking to an in-cluster LokiStack CR
      lokiStack:
        authentication:
          token:
            from: serviceAccount              # Vector authenticates using the SA's own token
        target:
          name: logging-loki
          namespace: openshift-logging
        tls:
          ca:
            configMapName: openshift-service-ca.crt
            key: service-ca.crt
  pipelines:
    - name: to-loki
      inputRefs:                              # fixed keywords, no config needed
        - infrastructure
        - audit
        - application
      outputRefs:
        - loki
```

```bash
oc apply -f clusterlogforwarder.yaml
oc get daemonset to-loki    # daemonset name == CLF metadata.name; one collector pod per node
```

**Gotchas:**
- `inputRefs` are fixed strings (`infrastructure`/`audit`/`application`) — typo = silent no logs of that type.
- DaemonSet name follows the CLF's name, not a fixed name like `collector`.
- `type: lokiStack` (reference an in-cluster LokiStack) vs `type: loki` (raw endpoint URL) — know both exist.

## 7. Console Log Viewing (Cluster Observability Operator)

Install COO via OperatorHub (standard OLM flow, no new mechanics).

```yaml
apiVersion: observability.openshift.io/v1alpha1
kind: UIPlugin
metadata:
  name: logging
spec:
  type: Logging
  logging:
    lokiStack:
      name: logging-loki      # ties back to Section 4
    logsLimit: 20             # caps entries per query — NOT a retention setting
    timeout: 60s
```

```bash
oc apply -f uiplugin.yaml
```

- Console menu appears at **Observe → Logs**. May need a reload / wait for "Web console update is available" banner (plug-ins load dynamically).
- `logsLimit` too low can look like "no logs are flowing" when they're just truncated — a troubleshooting angle, not just a config value.

## 8. LogQL Query Cheat Sheet

**Structure:** `{ stream selector } | parser | filter expression`

Stream selector operators (inside `{ }`, or on parsed fields after `| json`):
`=` equals · `!=` not equals · `=~` regex match · `!~` regex not-match

Filter expression operators (line/content level, after a `|`):
`|=` contains · `!=` not contains · `|~` regex match · `!~` regex not-match

`| json` — parses the JSON log line and **promotes fields to queryable labels**. Without it, you can only match pre-indexed labels (mainly `log_type`).

```logql
{ log_type="application", kubernetes_namespace_name="intranet-front" } | json

{ log_type="audit" } | json | hostname=~"worker.*"

{ log_type="audit" } | json |= "error" != "warning" |~ "status [45]03"

{ log_type="infrastructure" } | json | systemd_u_SYSLOG_IDENTIFIER="sshd"
```

**Vector-injected metadata fields (queryable after `| json`):**

| Field | Meaning |
|---|---|
| `hostname` | node running the pod |
| `kubernetes_container_name` | container name |
| `kubernetes_namespace_name` | project/namespace |
| `kubernetes_pod_name` | pod name |
| `level` | log level |
| `message` | log message |

- Real journald/infra logs carry **many more fields** than this table (e.g. `systemd_u_SYSLOG_IDENTIFIER`) — **discover unknown field names by expanding a log entry in the console UI**, not from a reference doc.
- **#1 syntax trap:** `=` is a label matcher (inside `{}` or post-`json`); `|=` is a line-content filter. Don't mix them up.

## 9. Log Access RBAC

| Cluster role | Grants read on |
|---|---|
| `cluster-logging-application-view` | application logs |
| `cluster-logging-infrastructure-view` | infrastructure logs |
| `cluster-logging-audit-view` | audit logs |

- By default **only admins** can view logs — regular users get nothing until bound.
- Bind via normal `RoleBinding` (namespace-scoped) or `ClusterRoleBinding` (cluster-wide) — standard RBAC, role ≠ scope; the **binding** decides scope.
- Requires `LokiStack.spec.tenants.mode: openshift-logging` (Section 4) to function at all.
- Granting one `-view` role does **not** imply the others — a user with `application-view` still gets Forbidden on infra/audit until separately granted.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: view-application-logs
  namespace: <target-namespace>
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-logging-application-view
subjects:
  - kind: Group
    name: <group-name>
    apiGroup: rbac.authorization.k8s.io
```

```bash
oc apply -f <rolebinding>.yaml
```

**Doubt resolved during practice:** `ClusterLogForwarder` alone does not solve log retention — it's only the routing/pipeline layer (Vector config). `LokiStack` is the actual durable storage backend. Both are required together; a forwarder with no working Loki target still loses logs on pod/node cycling.

## 10. End-to-End Build Order (quick reference)

1. Install Loki Operator (OperatorHub)
2. Create `ObjectBucketClaim` → extract creds → repackage into Loki-format secret
3. Create `LokiStack` CR → wait for pods Running
4. Create collector SA + 4 cluster roles
5. Create `ClusterLogForwarder` CR → verify daemonset
6. Install Cluster Observability Operator (OperatorHub)
7. Create `UIPlugin` CR → verify Observe → Logs in console
8. Query via LogQL; verify pod-deleted logs still retrievable from Loki
9. Grant `cluster-logging-*-view` roles to groups/users as needed
